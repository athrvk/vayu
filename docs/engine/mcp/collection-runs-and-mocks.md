# MCP collection runs, OAuth and local services

- **`run_collection_smoke`** runs each saved request once and returns a structured pass/fail matrix (2xx–3xx status + all tests passing = pass).
  Each request is composed exactly as the app's **Send** would (see [Request composition](request-composition.md#request-composition)), and sent buffered even when its Event stream setting is on (#3561): a row is judged by its exchange, and a stream answers with a run id instead.
  A request whose scripts asserted anything carries a `tests` node - `total`, `failed`, and the failing `name: message` lines (issue #733) - so a row that fails on its tests says which, rather than leaving an agent with `ok: false` beside a `200`.
  Both scripts count, and a pre-request assertion's line is prefixed `[pre-request]` (issue #810): it failed before the request went out, which is a different thing to go and look at.
  An assertion from a script the request inherits is prefixed with its level first - `[collection]` or `[folder]`, so `[folder] [pre-request] name: message` (issue #2522) - because the request's own scripts are the wrong place to go looking for it; the request's own assertion carries none.
  The list is cut at ten, the number the engine caps a schema verdict's failures at, while `failed` stays the true count.
  A response that ran no assertions carries no `tests` node: none ran is not all passed.
  A request the engine could not complete (`status: 0`, a timeout, DNS or TLS failure) carries the engine's own account as `error`, `"<errorCode>:
  <errorMessage>"` (issue #3552), the field a thrown send already uses, masked
  with the rest of the row; an answer with no `errorCode` leaves it unset.
  A stored `mcp` request is runnable here as it is by `run_request` with its `requestId`, and its own failure rides the row as `mcp` `{errorClass, code?, message}` (issue #3809): `tool` is the call that answered HTTP 200 with `isError: true`, `protocol` carries the JSON-RPC `code`, `transport` is a reply that never came as a JSON-RPC answer.
  A reply that succeeded, a request that is not `mcp`, and an exchange the engine could not complete (already `error`) carry no `mcp`; `message` is masked with the rest of the row.
  For a collection **bound to an OpenAPI document** each row also carries a `schema` verdict (issue #681) and folds it into `ok` the way `testResults` folds: a response the document declares a schema for and that does not match it fails the request, with the failing JSON Pointers listed so an agent need not re-run to learn where.
  `failOnSchemaError: false` unfolds it (issue #720): the verdict still rides every row, it just stops deciding `ok` - useful against a document known to lag its API.
  It defaults to **true** here, where the same-named flag on `POST /runs` defaults to false, because this tool has folded since #681 and an agent reading its matrix would otherwise start seeing contract failures pass.
  `run_collection` offers the same flag with the engine's default (issue #766, [*Scenario runs*](request-composition.md#request-composition)); one schema fragment words both, so the two can differ only in the unit they judge and the way they default.
  Only a *checked* verdict can fail a row - `checked: false` (no declared schema for the status or content type, a body that is not JSON) is reported and never counted against the run, and a collection bound to nothing carries no `schema` field at all.
  Requests whose host still can't be verified after resolution (e.g. a variable did not resolve and allow-all is off) are skipped, not sent.
  It runs a collection's **direct requests** unless `recursive: true`: `GET /requests?collectionId=` serves direct requests only, while collections nest via `parentId`, so a run on a parent folder tests none of its descendants.
  The result appends a note naming the sub-collections it left out (and says so explicitly if the collection list could not be read), because a matrix whose `total` silently excludes nested folders reads as a whole-collection pass.
  The note names both ways out: `recursive: true` here, and `run_collection` with `recursive: true` (preferred for a large tree: one stored run with a run id).
  `recursive: true` walks the tree through the same function `run_collection`'s pre-flight does (`walkCollectionRequests`, `scenario-runs.ts`), so the rows come in the sidebar's order (#2535) and each names its `folder`, the collection names from the root down joined by ` / `;
  a recursive run has nothing left out, so it carries no note, and a failed `GET /collections` is the engine error, with nothing sent.
  An OpenAPI import files its operations under sub-collections (grouped by tag or by path, per `meta.folderStrategy`), so a direct-only smoke of its root answers `total: 0`; `import_document`'s caveat says how many sub-collections hold the requests and names the recursive path.
  Requests run serially, so a collection takes as long as its requests do added together, and each one is real traffic: past about 25 requests or against a slow API the description steers an agent to `run_collection` (one stored run with a run id, read with `get_run_report`), leaving the smoke for a bounded pass/fail matrix.
  **A call runs one page** (#2451): `limit` requests (default 25, max 100; a larger value is refused, not clamped, like every bound in this registry) starting at `offset`.
  The list - the direct requests, or the whole expansion of a `recursive` run - is read once in the engine's stable order and then sliced `[offset, offset + limit)`, so a collection edited between two calls shifts the window under the second one (the description says so).
  `total`, `passed`, `failed` and `skipped` keep their meaning as the counts of the rows run **in this call**; the result adds `requestTotal` (the list's size, before the cut), `hasMore`, and - only while `hasMore` is true - `next: {offset}`, the `offset` that resumes.
  Whenever the call did not run everything in scope the result's own `note` field says so in a sentence (`Ran 25 of 140 requests, starting at offset 0; call again with offset: 25 for the rest.`), in the structured content and so in the JSON text block alike: a default of 25 that cut a collection quietly would read as a whole-collection pass.
  An `offset` at or past `requestTotal` runs nothing and the note says so (`hasMore` false).
  A call that ran everything carries `requestTotal` and `hasMore: false` and no note.
  Progress (below) counts the page, not the collection.
  **A cancellation returns what finished.**
  When the call's signal aborts mid-run the loop stops and the result carries the rows completed so far with `cancelled: true`, `hasMore: true` and `next.offset` set to `offset` plus the rows returned.
  The abort is told from a row's own send error by the signal, not by the error: an aborted fetch rejects like any other failure, but a send that fails with the signal still live stays a failed row and the run goes on.
  The request in flight at the abort is not a row, and `next.offset` points at it, so resuming sends it again; the note warns it may already have reached the API.
  The masking reads that follow the loop run without the aborted signal, since one that fails closes the call and would discard the rows.
  The SDK itself sends no response to a request whose signal aborted (a `notifications/cancelled` for it, or the connection closing; on 2025-era HTTP the host answers a cancelled stream already under way with an error instead, see [What is live on each transport](transports.md#what-is-live-on-each-transport)), so the partial result is what a caller that reads the handler's return value gets -
  the tests, `dispatchTool` - and what the cancelled loop no longer does is walk the remaining rows, each a failed fetch the instant after the abort.
  That holds on every transport: on 2025-era HTTP the host matches the client's cancel to the call and ends its exchange, so no request goes out after the cancel there either (see [What is live on each transport](transports.md#what-is-live-on-each-transport)).
  When the client sent a `progressToken` (#2451) the call reports `notifications/progress` - `0/total` before the first request, then one per row on every path (sent, skipped off the allowlist or failed to compose), with a message of the form `3/40 ok` / `3/40 skipped` / `3/40 failed`.
  The message is an index and a status word and nothing the request resolved to: the masking that covers a row's `url`, `error` and test lines runs on the finished matrix (it needs the secrets a script set along the way), so a mid-run string has no such cover and carries none of that data.
  The notification goes out on the request's own stream (`mcpReq.notify`), not the session's, and a failed or post-cancellation send is dropped.
  A client with a short request timeout only benefits if it resets that timeout on progress (the TypeScript SDK's `resetTimeoutOnProgress`): a single `POST /execute` may take up to 310 s (the engine's 300 s ceiling plus the client's grace), so without it the client can give up on a run still working.
  A call with no token sends nothing.
- **The OAuth 2.0 token tools** (issue #760) are how an agent gets a token problem named instead of discovering it as a wall of 401s inside a run: `fetch_oauth2_token` acquires (or force-refreshes) a token for a config and caches it engine-side, `get_oauth2_token_status` says whether an entry exists and whether it has expired, and `clear_oauth2_token` drops one.
  The config is the same block a saved request's `auth` carries, so it can be copied out of `get_request` verbatim;
  the **cache key is the engine's** (`accessTokenUrl` + `clientId` + `credentialsId` + `grantType` + username + the extra parameter rows the engine would send, a credential-named row such as `client_assertion` by its name alone, so the key never carries a secret), so configs differing only in scope share an entry and a distinct `credentialsId` is what separates them.
  Two rules here are security decisions rather than plumbing, and both are stated in the tool descriptions so an agent reads them before it reads a refusal.
  **No tool returns access-token bytes.**
  The engine is what applies a token to a request, so the bytes buy an agent nothing it can use through Vayu, while handing them over would turn a credential the *user* acquired into something an agent can carry off the machine;
  what comes back is the entry's shape - key, type, scope, expiry, whether a refresh token came with it - plus an explicit `accessTokenWithheld`, because an agent that finds no token and is not told why concludes the acquisition half-failed.
  And **the `authorization_code` grant is refused before the engine is called**, not merely because the browser exchange is one MCP cannot drive: `acquire_token` answers a cache hit *before* it looks at the grant, so a call naming a config that happened to match an entry the user authorized interactively would otherwise reach into it.
  The refusal names the app's Auth tab as the place to authorize, and the entry that lands there is the one these tools then read.
  The allowlist gate covers `refreshTokenUrl` as well as `accessTokenUrl` - a gate that read one of two URLs is a gate a config can walk around.
  Three grants are fetchable: `client_credentials`, `password` and `jwt_bearer` (RFC 7523, #3632), whose config the schema passes through whole like any other, so nothing about the grant is enumerated here.
  A `jwt_bearer` config carries `subject`, `assertionAudience`, `assertionClaims`, `signingAlgorithm`, `keyId` and its key, and the **key is where a call differs from a send**.
  The app writes it as one `{{variable}}` reference (`privateKey`), which the engine resolves against the scopes a request names; this tool names no `environmentId` or `collectionId`, so a config copied out of `get_request` with a `privateKey` reference is the engine's `400` `oauth2_invalid_config`, not a token.
  Two ways forward: name the key in `privateKeyFile` (a path read through the engine's file-trust rule, so it must have been picked in Vayu or lie under an allowed folder, and the config then carries a path rather than a secret), or skip the tool and `run_request` the saved request, which composes the reference against its own environment and collection and acquires the token as part of the send.
  The cache key's fifth slot is the grant's identity: the username for `password`, the `subject` for `jwt_bearer`.
  A read of a saved `jwt_bearer` config shows a `privateKey` that is one reference as written, since it names where the key lives without being it, and withholds any other value as `privateKeyWithheld`; `privateKeyFile` is a path and is shown.
- **The mock-issuer tools** let an agent asked to "test this auth flow" mint its own tokens:
  `start_mock_issuer` stands up a [local OAuth 2.0 issuer](../api-reference.md#local-mock-issuer) and returns its `issuerId`, `tokenUrl`, `authorizeUrl`, `metadataUrl`, `discoverUrl` and `signingKey`, so the agent can point a request's `oauth2` auth at the token URL (or set its `discoverUrl` to the returned one and type no endpoint), `run_request` it, and assert on what the target received -
  offline, with no real provider's 2FA prompts or rate limits in the loop.
  `expiresInSeconds` plus `issueRefreshTokens` is how the 401-then-refresh path is exercised, `failureMode` is how retry handling is (`slow`, `server_error` and `invalid_client` break `/token`; `metadata_not_found`, `registration_refused` and `wrong_iss` break discovery, registration and the authorize redirect's `iss`),
  and `resourceScope` is the scope the protected resource at `discoverUrl` requires of a token.
  **No allowlist entry is needed and none is checked**: the engine binds every issuer to `127.0.0.1` and takes no host for it, so an issuer is unreachable off the machine; the per-tool switch is what turns these off.
  The start body is forwarded verbatim under the engine's own key names, and the engine's limits (31-day expiry, 60s `slowMs`, 32 clients, 8 concurrent issuers) stay engine-side rather than being restated in the tool schema, for the same reason `monitor`'s ranges are - a second copy would refuse values the engine accepts the moment either side moves.
  The schema owns the *shape*: a claims object, an integer port, a `failureMode` from the closed set.
  Stopping an issuer frees its port; tokens it already minted stay valid until they expire, since nothing verifies them against a live issuer.
  **A running issuer is edited, not recreated**: `update_mock_issuer` merge-patches `failureMode` and `slowMs` live (issue #757), so an agent can mint a token against a healthy issuer, flip it to `server_error` to watch the client retry, and flip it back without the token URL under test moving or the signing key changing.
  Those two are the only settings a bound listener will take - the engine refuses `port`, `clients`, `claims`, `issueRefreshTokens` and `resourceScope` with "stop it and start a new one", so the tool does not offer them at all rather than offering a call that always fails.
  `expiresInSeconds` is mutable engine-side and is also left out: a token's lifetime is fixed when it is minted, so changing it says nothing about the tokens an agent already holds.
  An empty patch is refused here rather than forwarded, because the engine accepts one and answers `200` - which would report a change that did not happen (the `update_inbox_response` precedent).
- **The mock-server tools** are how an agent stands up the API a client under test expects, out of the collection's own saved examples (issue #757, over the engine's [mock server](../api-reference.md#mock-server) from #481):
  `start_mock_server` binds a listener that answers each request's example - status, headers, body - and returns its `mockId` and base URL, `get_mock_routes` lists what it will serve, and `stop_mock_server` frees the port.
  `latencyMs` and `errorRatePct` are how a client's timeout and retry handling get exercised; `0` and `100` percent are exact by construction, in between it is a per-request roll.
  **A started mock is not necessarily a usable one**, which is why the result carries a caveat rather than leaving the counts in the JSON: a route whose request has no saved example answers `501`, a path matching nothing answers `404`, and a collection with no mappable requests serves nothing at all.
  **Loopback-only** for the same engine-side reason as an issuer - `mock_server.cpp` starts every listener on `127.0.0.1` with no host to configure - so no allowlist entry is needed or checked.
  **A stop is a delete here**, unlike an inbox: a mock records nothing, so its record dies with its listener and it simply leaves `list_mock_servers`.
  The route table is a snapshot taken at start and cannot change under a running mock (editing the collection means restarting), which is why the renderer holds it at `staleTime: Infinity` and a `stop_mock_server` event carries the `mockId` so that cache entry is *dropped* rather than refetched into a `404`.
  Each row's `mode`, `exampleName` and `hits` are the exception - they read off the request's stored mock settings and the mock's own hit counter, so they can change between two reads of the same table even though the routes themselves cannot.
  `get_mock_activity` is the opposite of that snapshot: it is a log that grows for as long as the mock runs, newest first, so an agent watching a client under test calls it again to see what has arrived since the last read rather than trusting a cached copy - unlike the route table, which is worth fetching only once.
  It is capped at 200 rows per call (50 by default), pages with `offset` in the `{data, pagination}` envelope the other paged reads answer (the engine route takes `limit` alone and keeps 200 entries, so the tool reads that whole ring and slices it) and, like the route table, is discarded outright on `stop_mock_server` rather than kept the way an inbox keeps its captures.
  **`allowedOrigins`** (issue #2367) is which browser pages may read the mock's answers, the half of reach that "loopback-only" does not decide: a page open in the user's browser is on this machine.
  Absent or `[]` is the engine's default, any origin and never credentials; a list admits only those origins, with credentials.
  The schema says "array of strings" and no more - the count and length ceilings and what makes an entry an origin are the engine's, and a bad entry comes back as a `400` naming it (`allowedOrigins[1]`) - and the start result and `list_mock_servers` echo the canonical list.
  Fixed for the mock's life, like `latencyMs`.
- **The webhook-inbox tools** are the assertion half an agent testing a webhook needs (issue #756):
  `start_webhook_inbox` stands up a [local inbox](../api-reference.md#webhook-inbox) and returns its URL, `get_inbox_captures` reads back what arrived - method, path, query, headers, body, caller address - and `update_inbox_response` changes what the sender sees, live, so one inbox can answer `200` for the first trigger and `503` for the next.
  **Loopback-only, and not by policy alone**: the engine's `bind` / `confirmNonLoopback` pair is never emitted by `inboxStartPayload`, whatever arguments a call carries, so an inbox MCP started cannot be reached off this machine - a stated non-goal of epic #753, guarded in the one function that builds the body and mutation-checked in `tools/webhook-inbox.tools.test.ts`.
  **A stop is not a delete**: `stop_webhook_inbox` frees the port and leaves every capture readable, while `delete_webhook_inbox` destroys them and therefore takes the write toggle *and* a confirmation whose prompt names how many captures go with it (read from `GET /inbox` first, the way `delete_run` reads the run).
  `clear_inbox_captures` is the middle case - recorded data destroyed, listener kept - so it takes the toggle without the confirmation.
  **No live stream**: `GET /inbox/:id/live` is single-watcher (a second is a `409`) and the app's own inbox tab may hold it, so MCP polls `get_inbox_captures` instead - the same bounded-snapshot posture `get_live_metrics` takes.
  Capture bodies are cut to 32 KB for the result with the engine's own `bodyTruncated` / `bodyBytes` disclosure kept intact (a body that is not valid UTF-8 carries `bodyEncoding: "base64"`, is cut in decoded bytes so it stays whole base64, and is masked in its bytes like any other base64 body, #3109), since `inboxMaxBodyBytes` reaches 8 MB and a webhook payload is whatever the sender sent.
  **`allowedOrigins`** (issue #2367) is forwarded the same way as the mock's - an array of strings, validated by the engine, echoed canonical by the start result and `list_webhook_inboxes`.
  It is CORS policy, which browser pages may read the canned answer, and does not touch who can connect, so it sits beside the loopback guarantee rather than loosening it.
- **Cancellation:** the `AbortSignal` the SDK hands each call fires when the client cancels it, and it is threaded into the engine `fetch` for every tool call, resource read, template list and prompt, so a client cancelling an in-flight call actually aborts it rather than leaving the engine request running detached.
  How the cancel reaches the signal differs by leg: over stdio the SDK reads the `notifications/cancelled` itself, a 2026-07-28 HTTP client's cancel is handled by the SDK itself, and on 2025-era HTTP the host matches the cancel to the call by `Mcp-Session-Id` and request id (see [What is live on each transport](transports.md#what-is-live-on-each-transport)).
  The one exception is the run-ID **completion** callback, which the SDK invokes as `(value, context?)` with no request context to carry a signal.
- **Timeouts:** engine-local calls are bounded at 35s, but `POST /execute` waits on a third-party server, so its budget is derived from the engine's own `defaultTimeout` setting (read per call from `GET /config`, up to its 300s ceiling) plus 10s of grace - the same rule the renderer uses for its proxied calls.
  It is a worst case for the payload sent (#2836, `electron/mcp/execute-budget.ts`): the setting again when `auth.mode` is `oauth2` (the token fetch has the same bound), plus the `scriptTimeout` setting (60s when unreadable) for every enabled `script.pre` / `script.post` element, because one call runs them in sequence.
  A request with neither keeps exactly the setting plus 10s.
  That way the engine's own `TIMEOUT` error, with its error code and its run row, arrives before this client gives up.
  If the budget does expire, the tool says the call may still have completed and what to check before repeating it, which depends on the tool (see [Error results](conventions.md#error-results)); it is never reported as an unreachable engine, because a retry could re-send a request that already went out.
  `run_collection_smoke` bounds the other side of this: a call runs at most `limit` requests (25 by default), so one call stays inside a typical client budget and a longer collection is resumed by `offset` rather than lost to a timeout.
  It also sends a progress notification per row when the client asks, which a client that resets its timeout on progress (`resetTimeoutOnProgress`) can use to outlast a slow API.
