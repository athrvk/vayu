# MCP secret values

### Secret values

With **Reveal secrets to agents** (`revealSecretsToAgents`, default off) in Settings → MCP off, an agent reads no secret through any tool, resource or prompt (#1805, #1809).
Four paths lead to a secret - what is stored, what a write tool answers, what a run recorded, and clearing the secret flag - and each is closed below.
Withheld is stated, never a silent omission, so an agent cannot read a missing value as an empty one.

**What is stored** is withheld as a field the projection replaces:

| What | Withheld as | Read by |
| ---- | ----------- | ------- |
| A variable whose `secret` is `true` (any other value is not a secret) | `value` dropped, `valueWithheld: true` | `list_environments`, `get_globals`, `list_collections` (full rows), `resolve_variables`, `vayu://environments`, `vayu://collections` |
| An auth credential: `token`, `password`, `value` (an API key's), `clientSecret`, `secretKey`, `accessKey`, `sessionToken`, `accessToken`, `refreshToken`, `idToken`, `secret`, `authKey`, `consumerSecret`, `tokenSecret`, `clientToken`, `privateKey`, `code_verifier`, at the top of the block or under `config` | the member dropped, `<member>Withheld: true` | `list_requests` (full rows), `get_request`, `list_collections` (full rows), `vayu://collections` |
| A credential in a Postman import's `postman` source (the auth as Postman wrote it): a v2.1 `{key, value, type}` attribute whose `key` is one of the names above, a v2.0 `{name: value}` member named one of them, and a parameter row (`tokenRequestParams`, `authRequestParams`, `refreshRequestParams`) whose `key` is one of them or `client_secret`, `client_assertion`, `refresh_token`, `access_token`, `id_token`, `assertion`, or a header or query name from the `params` row below (`Authorization`, `X-Api-Key`, `api_key`, and the rest: a row can be sent as a header) | a row's `value` dropped, `valueWithheld: true` on the row; a v2.0 member as above | `list_requests` (full rows), `get_request`, `list_collections` (full rows), `vayu://collections` |
| A credential in an OAuth 2.0 `config`'s extra request parameter rows (`authorizationParams`, `tokenParams`, `refreshParams`, #2536), by the same key names as the Postman rows above; and, as the export's `redact_config_param_rows` treats them, a row with no non-empty string `key`, a row member other than `key`, `value`, `enabled` and `sendAs`, or a list that is not an array, each when it holds a non-empty string that is not a pure `{{variable}}` reference | the row's `value` dropped, `valueWithheld: true` on the row; `key`, `enabled` and `sendAs` stay. A keyless row becomes `{valueWithheld: true}`, another member `<member>Withheld: true`, a list that is not one `<list>Withheld: true` on the `config` | `list_requests` (full rows), `get_request`, `list_collections` (full rows), `vayu://collections` |
| The value of a credential-bearing header row in a saved request or example (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `X-Auth-Token`, `X-CSRF-Token`, or the header the request's API-key auth names, whatever its `in` says; disabled rows included; an empty value or a pure `{{variable}}` reference is shown as written) | `value` dropped, `valueWithheld: true` on the row (a row written back that way keeps its stored value, and an `update_request` that changes the request's origin while one is left holding it is refused, see what a write tool answers, below) | `list_requests` (full rows), `get_request`, `list_request_examples` |
| A saved request's `url` and `params` (#1837): the password of `user:password@` userinfo is dropped (the user stays), and the value of a credential-named query or fragment parameter is emptied (`?api_key=S&page=2` becomes `?api_key=&page=2`); a `params` row with such a name, disabled rows included, loses its `value`. Names are `SENSITIVE_PARAM_NAMES`, matched whole and case-insensitively, plus the key of an API-key auth placed `in: "query"`; `code` and `key` are data, not credentials; an empty value or a pure `{{variable}}` reference is shown as written. The export's rule (#1804), ported rather than redefined | the URL as above, with no marker (an emptied slot written back keeps its stored value while the origin is unchanged, see what a write tool answers, below); a `params` row `value` dropped, `valueWithheld: true` on the row | `list_requests` (a summary's `url` too, masked on the whole row before the summary is cut), `get_request`, `delete_request`'s preview and prompt, `run_collection_smoke`'s `url` on every row (the stored URL for a request that failed to compose; the composed one otherwise, which run output below also masks), `get_graphql_schema`'s `endpoint` (the composed URL; the SDL is never withheld) |
| A cookie value | `value` dropped, `valueWithheld: true` | `get_cookies` (full rows; a summary row has no `value`) |
| The userinfo of a config entry whose key ends in `url` (`proxyUrl`, `proxySystemUrl`) | stripped from `value`, the host kept, `credentialsWithheld: true` on the entry (the value written back unchanged keeps them) | `get_engine_config`, `update_engine_config`'s `updated` echo, `vayu://config` |
| The current side of a spec drift entry's `headers`, `url` or `params` change when it could carry a credential: a header row with a value named by the shared sensitive list or by the request's own API-key auth, whatever its `in`; a `url` the saved-request rule above would change, or one the engine's 120-character cut ended before its host did (a cut password has no `@` left to find); a `params` row with a value named by `SENSITIVE_PARAM_NAMES` or by the request's own API-key-in-query auth (the tool reads the stored request's `auth` for each entry with a `headers`, `url` or `params` change, only while reveal is off; a request it cannot read has those fields withheld whole when non-empty rather than judged). The engine's line is lossy, so it is withheld whole, and an ordinary change passes as written | `current` dropped, `currentWithheld: true` | `diff_spec` |

**What a write tool answers** goes through the projection of the read of the same row (`echoShape`, `withholdReorderRows`), so writing does not grant reading:
`create_collection`, `update_collection`, `unbind_spec`, `create_request`, `update_request`, `restore_trash_entry`, `create_request_example`, `update_request_example`, `move_item` (the renumbered rows), `create_environment`, `update_environment`, `activate_environment` (either direction) and `update_globals` answer the row they changed with the rows above withheld.
The write that would lift the withholding is refused: `secret: false` over a stored `secret: true` on a variable of an environment, the globals or a collection is an error naming the setting, because the next read would return the value.
A value the read emptied and the agent writes back is carried forward rather than stored empty (#3549):
`update_request` re-reads the row and keeps each credential slot of its `url` the call still holds as the read showed it (the password after the same user, a credential-named query or fragment pair by name and occurrence), and `update_engine_config` writes a URL entry repeated as the read showed it as its stored value.
Each kept slot is named in a caveat line.
A credential belongs to the address it was stored for (#3564):
when the written `url` changes the scheme, host or port of the stored one (scheme and host compared without regard to case, a scheme's default port the same as none, a `{{variable}}` compared as written, an authority that cannot be read as `host[:port]` only by an identical spelling),
nothing is carried, the slots stay as written, and a caveat line per slot says it was not carried because the host changed.
A path, query or page edit on the same origin keeps everything.
A header row of a saved request or example is the same (#3550):
`create_request`, `update_request`, `create_request_example` and `update_request_example` take `headers` as the rows the read returns, and a row written back with `valueWithheld: true` and no `value` keeps the value of the stored row with the same name (case-insensitive) and occurrence, while one with no such stored row (on a create, any) is an `input` error naming the header.
A `headers` map still replaces the list, one enabled row per name; while reveal is off, `update_request` and `update_request_example` read the stored row first and name, in a caveat line, each stored row whose value the read withheld that the write left out.
A header row and an `auth` block are held to the same address, and a refusal rather than a caveat enforces it (#3654):
an `update_request` that changes the origin of its `url` while reveal is off is an `input` error, with nothing written, if the stored request holds a credential header row (the rows above, disabled ones included) that the call leaves with its stored value -
a `headers` row written back withheld, or no `headers` at all - or a stored `auth` block that holds a credential (a `none`, `noauth` or `inherit` mode, or a block of `{{variable}}` references only, holds none) and the call does not replace.
The error names each such row and the stored auth mode, and says what to do in the same call: pass `headers` with a real value for each row, and `auth` with the real credentials, or clear them - `auth: {"mode": "none"}` (the key is `mode`, not `type`) and `headers` without the rows.
A row given a value or left out of a written `headers` list no longer holds the stored credential, and a call that sends `auth` replaces the stored block, whatever it holds.
A write with no `url`, a `url` on the same origin, and any write with reveal on are not judged, and a withheld row standing for a header that holds no credential is carried to the new host as before.
The userinfo password and credential query values of the `url` are not refused: they stay empty, as above.
Known limit: a `{{variable}}` in the host is compared as written, so changing the variable's value moves the request to another host without changing its origin; that is a write to the variable, and an agent with writes on already holds that trust.
An example is read from its request's list, since there is no by-id read, and written under its version as a request is.
So an agent cannot set such a slot to literally empty over a stored value: removing the parameter or the userinfo deletes it, and a proxy URL's credentials go when it is cleared or its address changes.
`secret: true` and every other edit pass, and with reveal on nothing is refused.
Removing a variable and creating it again stores the value the agent sent, which is no secret of the user's.

**What a run recorded** is masked in place with the engine's `<redacted>` marker, so the record keeps its shape (`runOutputShape`).
A request that references a secret still sends it, so the trace holds the resolved value in whatever encoding it went out in; an agent reads `<redacted>` there instead:

| What | Masked as | Read by |
| ---- | --------- | ------- |
| The value of every secret variable of the workspace (globals, every environment, every collection), and every literal credential a stored collection's or request's `auth` holds (the members the first table withholds; an empty value or a lone `{{variable}}` is none), in any string of the output, in its raw, percent-encoded (`url_encode`, query, and a URL's path, fragment and user info as composition writes them), JSON-escaped and XML-escaped forms; a value under 4 bytes is not masked, and a base64 body (`bodyEncoding: "base64"`, #2458) is searched as the bytes it decodes to, never as its base64 text, where a match is coincidence: each form is matched as UTF-8 bytes and as Latin-1 bytes, the marker replaces the bytes it matched, and the body is re-encoded so it still decodes (`bodySize` / `bodyBytes` keep the engine's count; a body with no match comes back unchanged) | the value replaced by `<redacted>` | `run_request` (the response, and the events of a streamed one), `get_run_report`, `read_body` (the whole record before a page is cut, a base64 body by its decoded bytes, a saved example's body too), `list_request_examples` (each example's body, masked before it is bounded; the headers are withheld as in the table above), `diff_bodies` (both records in one pass before the diff), `get_run` (its `mode` / `duration` echo; the projection carries no other stored text), `export_run_report` (the document text), `get_run_samples`, `list_runs`, `get_inbox_captures`, `get_mock_activity` (each entry's `path`), `set_run_baseline`, `run_collection_smoke` (each row's `url`, `reason`, `error`, `mcp.message` and failing test lines; every row's `url` is also withheld as a saved request's is, in the table above, so a credential typed literally into it does not pass), `start_load_run`'s confirmation preview (the planned run and the question that names its target), `vayu://runs`, `vayu://run/{runId}/report`, the `summarize_run` and `diagnose_errors` prompts |
| The value of a credential-bearing header (the names above, plus the header any API-key auth block names whatever its `in` says, including one sent inline: the engine's `api_key_header_names`) in a header map, a header row list (a response's `headerLines`, an exchange's `requestHeaderLines`, a trace's `sentHeaderLines` and each redirect hop's `redirects[].headerLines`, #2461, included) and a `rawRequest` header line, request and response alike | `<redacted>` after the name | the same |
| The value of the query parameter auth wrote into the request at send time, named by the trace's `request.authQueryParam` (an OAuth 2.0 token or an API key placed in the query; the engine's raw, unencoded name), in the sibling `url` and in the request line of the sibling `rawRequest`; and the headers named by `request.authHeaders`, in the sibling `headers`, `sentHeaders` and `rawRequest` header block, beside the names above (#1835). `run_request`'s answer carries both keys at its top level (#1845), where `requestHeaders` stands for `headers` and the dialled `url` sits beside them (#3650). On `run_request`'s answer the same name masks each followed redirect hop's `redirects[].url` (#2949), since the hop sits beside the key; a stored trace keeps the hops under `response` and the key under `request`, so there a hop's `url` is masked by the secret forms and the credential-named rule, and by the engine, which writes `<redacted>` for the auth-written parameter in the hop URL it records. The `authNotice` beside them, saying auth sent nothing (a mode Vayu does not execute, #2474, naming the mode; an empty bearer token or API key name, #3203) or that the request's own `Authorization` header was sent in place of an OAuth 2.0 token (#3202), is a plain string, carries no credential and is not masked | `<redacted>` after the name | the same |
| The value of a credential-named query parameter (`SENSITIVE_PARAM_NAMES`, the saved-request rule above, whole name and case-insensitive) in the `url` of a record (a followed redirect hop's `url` included, #2949) and in the request line of a `rawRequest`, whether it was typed into the saved URL, came from a `Params` row or was written by auth: a credential that is no secret variable and no stored auth credential has no form to match, so the name is what masks it (#1909). `?api_key=LIT&page=2` reads `?api_key=<redacted>&page=2`; `api_key2`, an empty value and a lone `{{variable}}` are shown as written. Only the query between the first `?` and the first `#` is read, so a fragment parameter is not masked here | `<redacted>` after the name | every read of run output above, and `delete_run`'s confirmation prompt, whose subject line names the run by its `url` |
| The password of a URL's `user:password@host` userinfo, in the `url` of a record (a followed redirect hop's and a monitor's included) and in `metadata.requestUrl` of a run report, the member the engine copies from the run snapshot's `url` and which is read exactly as `url` is, so its credential-named query values are masked by the row above. The password is dropped and the user name kept (`http://u:LIT@h/p` reads `http://u@h/p`), as a saved request's `url` is, so the record keeps its shape; a lone `{{variable}}` password and a URL with no password are shown as written. Only the authority is read, so an `@` in the path, query or fragment is not taken for userinfo | the password dropped | every read of run output above, `get_run_report` and `vayu://run/{runId}/report` included |
| The planned run's `auth` block, composed with the stored or inherited credential in it | as a stored row's: the member dropped, `<member>Withheld: true` | `start_load_run`'s confirmation preview |

The masking is the engine's own rule for a run's config snapshot (#1803), applied to what a read can know: the secrets of every scope rather than only the run's, because a run row names its environment but not the collection chain an inline send resolved through, a list reads many runs at once and an inbox capture belongs to no run.
A literal credential typed into a stored auth block is no variable, but the engine writes it onto the wire after composing (an API key `in: "query"` lands in the trace URL and `rawRequest`), so it is masked as a value too.
A credential no stored row holds, such as an OAuth 2.0 token the engine fetched, is masked by *where* it went instead:
the stored trace names the query parameter (`request.authQueryParam`) and the headers (`request.authHeaders`) auth wrote, `run_request`'s live answer names them as `authQueryParam` and `authHeaders` at its top level (#1845) beside the `url` and `method` it dialled (#3650, the `url` masked as the trace's `request.url` is), and the masking reads them per record.
`run_request` passes the engine's top-level `authNotice` (#2474, #3202) and `warnings` (#3307, `[{code, message}]`, `[]` when empty; a cookie named by name only, never a value) through as they came, unmasked, and `get_run_report` keeps a stored trace's top-level `warnings` beside its bounded `request` and `response`.
The parameter is matched on its whole name, case-sensitively, in the URL's query (between the first `?` and the first `#`) and in the request line only, as the engine wrote it: raw, or percent-encoded as `encode_query_component` writes a key unless the request disabled URL encoding.
A pair of that name is masked wherever it appears in the query, the user's own included; `api_key` leaves `api_key2` alone, a body is untouched, and an empty value or a lone `{{variable}}` is shown as written.
The credential-named parameters of the saved-request rule are masked in the same two places by the same bounds, but case-insensitively, as that rule matches them.
With URL encoding disabled, a value holding a raw `&` ends at it.
The values are read when the tool is called, so a secret rotated since masks under its new value only.
Keys are not touched, nor numbers, so a size the engine reported still describes what it measured.
A tool that cuts a body to a byte cap (`run_request`, `get_run_report`, `get_inbox_captures`) masks *before* it cuts, because a cut through an unmasked secret leaves a prefix no form matches.
`compare_runs` forwards numbers only and has nothing to mask.

**Masking fails closed.**
It needs four reads (the globals, the environments, the collections, every request) to know the values it masks.
If any of them fails, the read answers an error naming the lookup that failed and that masking could not complete, and returns none of the result: masking with the reads that answered would hand over every secret the failed one holds.
A tool answers it as an error result, a resource or a prompt as a failed request (`MaskingIncompleteError`).
A tool that sends traffic (`run_request`, `run_collection_smoke`) has already sent it when it answers so; the run is in `list_runs` once the engine answers again.
With reveal on none of the reads is made.

A tool words that error by the lookup's cause (#2780, `maskingIncompleteResult` in `kit.ts`), and a resource or a prompt does the same through `maskingOutageMessage` (#2854), so its failed request carries the same text.
When the engine refused the connection or answered with a failure it classes `unreachable` or `transient`, the answer is the same one every other tool gives (`Could not reach the Vayu engine ...`, `Engine error (500): ...`), in that class, followed by a sentence that the result is withheld whole until the engine answers;
the Reveal secrets setting is not mentioned, since it is not a remedy for an outage.
Any other cause, including the `Unexpected error` fallback and an engine refusal of the lookup itself (a 4xx), keeps the masking message naming the lookup that failed.
A resource or prompt read puts its own engine read and the lookups out together and settles both: an outage lookup failure leads even when the read failed first with a bare `fetch failed`, and a lookup failure that is not an outage yields to the read's own failure (a 404 for an unknown run).
A cancelled read says so without a tool call's "may have completed" advice, since a read sent nothing.

**An engine refusal's text is masked too.**
The engine words its refusals to quote no resolved variable value (a header name is quoted as written, with the one byte at fault), but that is the engine's rule to keep,
so a tool error built from an engine refusal body (`Engine error (400): ...`, a `restore_trash_entry` 404 or 409, the engine's 404 sentence) reads each secret form as `<redacted>` under the rule above, in its text and in `structuredContent.error.advice`.
The mask is applied in `dispatchTool` (`maskEngineText`, `kit.ts`), keyed on the failure's `engineText` mark, so an error that holds no engine text (a missing argument, a policy refusal) makes no lookup and an outage needs none.
It fails closed like the reads above: when a lookup fails the answer is the masking error and none of the refusal text.
With reveal on nothing is masked and no lookup is made.

The stored trace stays raw on purpose: Vayu's own History shows what went over the wire, and the engine's rows are unchanged.
Only the MCP read is masked.

The credential lists are the engine's own `SECRET_AUTH_KEYS` and `SECRET_PARAM_KEYS` (`core/vayu_extensions.cpp`), the sets a collection export blanks, and the `postman` walk is its `redact_postman_auth`;
the header names are the shared sensitive-header list and the parameter names are the engine's `is_secret_param_name` set, both pinned to the engine's by `withhold.conformance.test.ts` (`sensitiveHeaderNames` and `sensitiveParamNames` in `log-redaction-conformance.json`).
An auth member or row holding one `{{variable}}` reference and nothing else is shown as written, the way the export keeps it: it names where the secret lives without being it, and the variable it names is withheld on its own terms.
An auth block carrying a withheld marker (a `<member>Withheld` member, top level, under `config` or in its `postman` source, a `valueWithheld` row in that source, or any `...Withheld` marker on or in place of a `config` extra parameter row or list) is refused as `auth` by every tool that takes one (`readAuthArg`):
stored, it would replace the user's credential with nothing, and sent, it would authenticate with nothing.

The other marker, `<redacted>`, is what a run's record shows in place of a credential (above), and a request copied out of one carries it back.
It is refused as `input` in the credential slots a read withholds, exactly as the `...Withheld` markers are, and only as the *whole* value (`isRedactionMarker` in `withhold.ts`; `tools/redacted-input.ts` holds the refusals):
an auth member (`readAuthArg`, so every tool that takes `auth`), the value of a credential-named header (a row of `create_request`, `update_request`, `create_request_example` and `update_request_example`, or a `headers` override of `run_request`, `start_load_run` and `get_graphql_schema`; a row written back as `valueWithheld: true` has no value to judge),
the value of a credential-named query or fragment parameter or the userinfo password of a request's `url` (`create_request`, `update_request`, or the `url` override of `run_request` and `start_load_run`), and the value of a variable that is, or is being written as, `secret: true` (every tool that writes a variable blob).
The call is refused before anything is written or sent, and the error says to pass the real value or a `{{variable}}` reference.
A request body, a description, a header or parameter no read withholds, and a value that only contains the text are stored as written, and with reveal on nothing is refused: the marker then stands for nothing.

The server instructions state the withholding rules once, in full, in every session where reveal is off, beside the write gate's sentence and for the same reason, and the run and config resources repeat the rule for their own output.
Each tool that carries one of the rows above gets one line in its own description (`withheldPointer(config, kind)` in `withhold.ts`: what its result reads in place of a secret, and that the instructions give the rules), so an agent that never reads the instructions still learns that the marker means "withheld", not "missing".
The line is empty when reveal is on, and so are the instructions' rules: a session gets the rules exactly when its tools carry the pointer, and with reveal on no description says `Withheld` or `<redacted>`.
The projection lives in `withhold.ts`.

A script an agent sends is not a path: it is refused while reveal is off (see [*Scripts an agent supplies are refused*](request-composition.md#request-composition)).
A script an agent *stores* through a write tool is outside that refusal and still runs with the secrets; see the write toggle.
