# Editor support and limitations

## What the editor offers, and where it comes from

Everything the script editor advertises - completions, hover documentation and the insertable templates listed under the editor - is generated by the engine and served at `GET /scripting/completions` (`engine/src/http/routes/scripting.cpp`).
There is no second list in the app, which is why a member documented here and offered there cannot drift apart.

An entry whose `kind` is `28` is a **template** rather than a member, and it carries two fields no other entry does:

| Field | Values | What it decides |
|-------|--------|-----------------|
| `context` | `pre`, `test`, `both` | Which script kind the template belongs in. [Details](#the-context-field-in-full) |
| `group` | `Variables`, `Request`, `Response`, `Tests`, `Signing`, `Logging` | The heading it is listed under. |

The app's snippets surface under each script editor is built from those two: it shows the templates for the editor it sits under, grouped by heading, and inserts one at the cursor with its `${1:placeholders}` intact.
A pre-request script is offered `pre` and `both`, a post-request script `test` and `both`, and a `script.setup` / `script.teardown` script - which run once per run, outside any request, with no `pm.request` or `pm.response` to template - only `both`.
Adding a template to the table is therefore all it takes to offer it in the app - see [`pm-api-compatibility`](../../app/pm-api-compatibility.md#editor-autocomplete) for the payload itself.

### The `context` field in full

A template that reads `pm.response` is `test`, because a pre-request script has no response to read; one that writes `pm.request` is `pre`, because a test script's writes go nowhere.
`both` needs neither, so it is offered under every script editor.

## Limitations

The **language** is current; what is missing is the **host environment**:

- **Modern syntax works.**
  Optional chaining (`?.`) and nullish coalescing (`??`) are ES2020 and supported, as are later additions like `Array.prototype.at`, `Object.hasOwn`, `String.prototype.replaceAll`, the ES2023 copying methods (`toSorted`, `toReversed`, `with`), `findLast`, `Object.groupBy` and `Promise.withResolvers`, and the newest library members:
  `RegExp.escape`, `Math.sumPrecise`, `JSON.rawJSON` and `JSON.isRawJSON`, and `Uint8Array`'s `fromBase64`, `fromHex`, `toBase64`, `toHex`, `setFromBase64` and `setFromHex`.
  The script editor's type declarations use TypeScript's `esnext` library, so none of the first group is marked as an error; the engine's own declarations add the newest ones, which TypeScript's bundled lib does not have yet (`LIBRARY_GAPS` in `script_types.cpp`).
  `?.` and `??` are ES2020 and available, so any workaround written around their absence can go.
  What limits a script is the global list above, not the syntax.
- **No host globals**: no `fetch`, `URL`, `TextEncoder`, `structuredClone` or `crypto.subtle` - see the table above for what replaces the ones that have a replacement.
  The timers are there, and run before the script ends without waiting ([Timers](sandbox.md#timers-settimeout-and-setinterval)).
- **No `Intl`**: the global does not exist, so `Intl.DateTimeFormat` and its siblings throw a `ReferenceError`.
  `toLocaleDateString`, `toLocaleTimeString`, `toLocaleString` and `Number.prototype.toLocaleString` run but ignore their locale and options arguments, so `toLocaleDateString('en-US', { month: 'long' })` does not format a month name.
  For dates use [`moment`](require-shelf.md#the-require-shelf); otherwise format by hand.
  The script editor marks a bare `Intl` with a warning that says this ([Editor autocomplete](../../app/pm-api-compatibility.md#editor-autocomplete)).
- **No Node.js APIs**: `require()` answers only the [shelf](require-shelf.md#the-require-shelf) (`crypto-js`, `uuid`, `lodash`, `moment`, `csv-parse/lib/sync`, `xml2js`, `chai`, `ajv` and `tv4`); `fs`, `http`, `crypto` and every other module throw `Cannot find module`.
- **Sandboxed**: No filesystem access.
  The only network access is [`pm.sendRequest`](send-request.md#sending-a-request-from-a-script-pmsendrequest) - capped at 10 requests per script, bounded by the script's own deadline and by the response byte bound its path reads, and refused outright for agent-started runs.
- **Memory limit**: 64MB per script execution (`scriptMemoryLimit`, 1 MiB to 256 MiB).
  Running out ends the script: since quickjs-ng 0.18.0 the out-of-memory error cannot be caught by the script itself, so a `try` cannot swallow it and keep allocating.
  It is reported as `Script ran out of memory at the 64 MiB limit`, naming the limit in force.
  The engine holds the limit itself, counting each block as QuickJS asked for it rather than as the platform allocator rounded it, and it is the engine's record of the refusal that decides the report, whatever QuickJS raised in its place.
  At the 1 MiB floor a library as large as lodash cannot load: `require('lodash')` fails with that sentence, so raise the limit rather than load it.
  See [Error Handling](errors-and-practices.md#error-handling) for the rest.
- **Console output**: 64 KiB per line, 1 MiB and 1000 lines per script execution; the rest is dropped behind one warning line ([Console Output](console-and-examples.md#console-output)).
- **Stack size**: 256KB per script execution (default), configurable through `scriptStackSize` from 64KB to 256KB, so it can only be lowered.
  QuickJS measures its ceiling from where the runtime is created, already some frames into the worker thread, and a secondary thread has 512KB on macOS (Windows gives 1MB) - no engine thread sets its own stack size - so a 512KB ceiling would overflow the native thread before QuickJS could refuse the recursion; 256KB is the size proven on it.
  A value an older engine stored above it is read as 256KB.
- **Timeout**: 5 seconds per script (default), enforced by a wall-clock deadline - an infinite-loop script is aborted and reported as an error rather than hanging the engine.
  Configurable via the `scriptTimeout` setting (milliseconds, 1 to 60000); there is no way to turn the limit off, and a `0` stored by an older engine (it meant "no limit") is read as the 5s default.
  The deadline is checked *between bytecode operations*, and since quickjs-ng 0.16.2 inside the long-running `Array.prototype` builtins too (`map`, `filter`, `forEach`, `reduce`, `indexOf` and their kin), but it cannot interrupt a blocking call - which is why `pm.sendRequest` clamps its own timeout to the budget that is left rather than relying on it.
  **A script is reported as timed out when the deadline actually stopped it**, not whenever its error happens to land past the deadline: a script that throws its own error at the buzzer reports *that* error, and `pm.sendRequest` refusing a spent budget reports its own sentence rather than a generic timeout line.
  A function an assertion calls - `pm.expect(fn).to.throw()`, `.to.satisfy(fn)` - is stopped by the same deadline, and that is **reported as the abort it is**, never as a satisfied assertion: the engine stopped `fn`, `fn` did not throw.
  Inside a `pm.test` that is a failed test, since `pm.test` reports what its callback threw; outside one it ends the script.
  A later assertion in the same script is still judged on its own, and a stack overflow inside such a function is a `RangeError` the script could have caught, so that still counts as a throw.
  **The deadline covers the promise jobs and the timers too** (#2531, #2577): the queues a script leaves are drained inside the same budget, checked between jobs and timer callbacks as well as inside one, so a runaway `while (true) await null;` or an uncleared `setInterval` stops with the same `Script execution timed out after <n>ms`.
  The setting always yields a deadline (#2359), so the drain is bounded by it; only an engine started with no deadline at all (an embedder or a test) has none, and there the drain stops after 100,000 jobs and timer callbacks together (`MAX_ASYNC_JOBS_WITHOUT_TIMEOUT`) with its own message, `Script stopped after running 100000 promise jobs and timer callbacks: ...`.
  A job or timer left queued by either stop is never run.
