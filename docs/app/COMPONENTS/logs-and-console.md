# Logs and Console

## Logs (`modules/logs/`)

The bottom panel's Logs tab (#3635): the files under `<data-dir>/logs/` read through the main process and shown as a table, without leaving the app. `BottomPanel` mounts `LogsTab` in its tab's content box, and the mount is the tail's lifetime (below). What the main process offers is `electronAPI.logs` (`list`, `read`, `tailStart`, `tailStop`, `onRecords`), documented in [Engine Logging](../../engine/logging.md#reading-the-files-in-the-app); the renderer never names a path.

- `LogsTab.tsx` - the entry, no props. Outside Electron (`window.electronAPI.logs` absent) it is an `EmptyState` saying the logs are available in the desktop app, with no stubbed bridge. Otherwise `LogsView` calls the store's `start()` on mount and `stop()` on unmount, which is the whole of the tail's lifetime: a tab that is hidden or a panel that is closed is unmounted, so nothing polls for a log nobody is looking at.
- `LogsToolbar.tsx` - the controls. **Level**, **Source** and **Component** are `Select`s over `logs-store`'s `controls`; the component's options are the categories any read has returned (`knownCategories`), and `cat:oauth` in the search box reaches one that has not been seen. The search box is debounced (`TIMING.LOG_SEARCH_DEBOUNCE_MS`) because each change restarts the tail. **Follow** is a `Switch`; **Jump to time** is a native `datetime-local` input read in the user's zone and sent as an ISO instant (`around`), followed by a page after it (`after`); **Export** saves the held lines as JSON lines through `downloadTextFile` and says how many it wrote; the folder button is `electronAPI.openLogsFolder`, which reports a failure as text.
- `LogList.tsx` / `LogRow.tsx` - the list, in the tab's own scroller (the panel clips). Columns are `LOG_COLUMNS` (`log-columns.ts`), shared with the header: time (`TimeValue`, UTC on hover), level (`LogGutter` with `LEVEL_TONE`, which gained `debug`), `src`, `cat`, message, then the record's other fields as `key=value` (`fieldsText`). A row is a button that opens to the whole record as formatted JSON and a **Copy line** (`useCopy`: the line as the file holds it, from the record's `$raw` key, which no column, field or the opened row's JSON draws; an unparsed line is its raw text; `entryLine` in `log-entry.ts`). A line that is not a record shows raw, with an "unparsed" marker where the component would be. The list is windowed by `useLogWindow` (#3670), a window with two ends that mounts at most `LOG_WINDOW_MAX_ROWS` (600) rows whatever the store holds: a plain growing list rather than a measured one, as `useGrowingWindow` argues, because an opened row is variable-height (the fixed-row window in `collections/useTreeWindow.ts` is the drawer's). While following it is the newest lines; otherwise it is anchored on its first row by the entry itself, not an index, since the store's trim of the oldest moves every index. A sentinel above the first row and one below the last each mount a step (`LOG_WINDOW_STEP`, 200) towards their end, and past the cap the far end unmounts; lines added below while the reader is not following (a page newer, a tail batch while scrolled up) wait past the lower end until the reader reaches them. `generation` resets it to the newest step, so a tail batch does not; a **jump** (`jumpTarget`, #3674) resets it onto the time instead, a few rows before the first line at or after it, so the line is mounted whatever is newer. Until the jump's first page newer has landed (`jumpPaging`) the window is unsettled: it shows the time where a line at or after it is held and the newest rows where not, holds no first row, and neither sentinel grows it, so the page's arrival opens it on the time whatever the page carries (even no timed line) and wherever the reader had scrolled to meanwhile; after it, the window is anchored on that line, or on the newest rows when none is held. **Growing above the reader keeps their place** (#3675): the top sentinel's growth first notes where the list's first row sits (`useHoldPlace`, `hooks/useHoldPlace.ts`) and the commit moves the scroller by however far that row went, because Chromium does not scroll-anchor at `scrollTop` 0 and the sentinel would otherwise stay in view after one step, leaving 400 rows mounted whatever is held. It measures the row rather than the scroll height since the far end gives rows up at the cap. Only that growth moves the scroller; the follow pin, the bottom sentinel and a new generation do not. **Follow is `useStickToEnd`** (#3671, `hooks/useStickToEnd.ts`): the pin and the resize re-pin of the `ul` are the hook's, and the Follow rules stay `LogList`'s - the store's `follow` is the hook's `following`, and a scroll to the end resumes it only when the list is not detached and has no rows below the window (`canResume`). **The older bar** ("Searched back to ...", **Search older**, "Reached the start of the logs.") is drawn only when the window starts at the oldest line held (`!hasAbove`), since both speak of what is above everything held, not above the window.
- **Follow is the scroll position.** Scrolling off the end turns it off, reaching the end turns it on - except on a list that is `detached` from the tail, which only the Follow control resumes (by reading afresh), and at the end of a window with lines still unmounted below it, which is not the end. After a jump, **Search newer** below the last row (`loadNewer`, with "Searched forward to ..." mirroring the older bar) pages towards the newest lines, and the page that reaches them attaches the tail, so reaching the end follows again.
- **A jump is marked and scrolled to** (#3674). `jumpTo` records its time as `jumpTarget`, and every other replacement of the list clears it. `LogList` draws a `role="separator"` rule ("Jumped to ...", named by the time) before the first line timed at or after it, or at the end when none is (a line with no time is neither), and once the first page newer has landed (`jumpPaging` false), calls `scrollWithin` on it, block `center`, once per generation: the window and the rows move as that page lands, so an earlier scroll would be to a place that then moves. The scroll goes through `useStickToEnd`'s `scrollOwn`, which keeps the scroll event it causes from reading as the reader reaching the end, so Follow stays off when the page reached the end of the logs and the time lies within a screen of it. Resetting the scroller to its end instead would show the newest lines.
- `LogsFooter.tsx` - the held count and estimated size (`formatBytes`), the tail's `dropped` count, and the engine's `logLevel`, read from the config query Settings › Observability reads (`useConfigQuery`), with the sentence that requests answered 2xx and database writes are `debug` and a link to Settings › Observability (`revealSettingsCategory`), where the level changes and applies after a restart.
- `logs-store.ts` - the lines, the controls and the bound (10,000 lines or 16 MiB); see [state-management](../state-management/module-local-stores.md#moduleslogslogs-storets---the-logs-tabs-lines). `parse-search.ts` is the search box's grammar, a renderer copy of the reader's `parseSearchInput` that `electron/log-search.conformance.test.ts` holds equal. `log-entry.ts` is what is done with one line: record or not, its fields text, the opened row's JSON (`recordJson`), its line (`entryLine`, for Copy line), its export line (`exportLine`: the cut record re-serialised where the reader cut the raw line, so the export stays JSON), its byte estimate (`entryBytes`, fields, raw line and position), its key; `RAW_LINE_KEY` and `POSITION_KEY` (`$pos`, where the line sits in its file, which nothing draws, copies or exports either) are the reader's, held equal by `electron/log-raw-line.conformance.test.ts`.
- **Surface:** the tab sits on the panel's `bg-panel`; the one block it paints, an opened row's JSON, is `surface-sunken`. → `BottomPanel.surface-rule.test.tsx`.
- **Guards:** `no-renderer-log-read.test.ts` (no renderer source names `readFile`, `createReadStream` or `fs`).

→ `LogsTab.test.tsx`, `logs-store.test.ts`, `parse-search.test.ts`, `electron/log-search.conformance.test.ts`.

## Console (`modules/console/`)

The bottom panel's Console tab (#3634): everything this window sent, newest last - each Send, each collection-run step, and their scripts' `pm.sendRequest` calls and console lines - with method, URL, status, time and size. `BottomPanel` mounts `ConsoleTab` in its tab's content box; the rows live in the session ring, so closing the panel drops the tab's filters and never the rows. History is what persists; nothing here writes to it.

- `ConsoleTab.tsx` - the entry, no props: the toolbar over the list, and the filter as the tab's own state (a way of looking, not a setting).
- `ConsoleToolbar.tsx` - **Type** (all, requests, script requests, console lines; a collection-run step counts as a request), **Level** (all, log, info, warning, error; a level names console lines only, so a request row is not listed while one is chosen), a search box over the method, URL, status and message (a step's name, a script request's summary line and an error code too), and **Clear**, which empties the ring and touches nothing in History.
- `console-filter.ts` - the one predicate the three controls make (`consoleRowMatcher`), and `filterConsoleRows`, which hands the ring back untouched when nothing narrows.
- `ConsoleList.tsx` - the list, in the tab's own scroller. **The filter runs over every row in the ring before the window is taken**, as `ConsoleOutput` does: `useGrowingWindow` draws the newest slice and grows upward from a sentinel above it, with the filter as its reset key, so a match above what is drawn is still listed and an append does not shut the window. Growing above the reader holds their place (`useHoldPlace`, passed as the hook's `beforeGrow`, #3675), so steady scrolling up reaches the oldest row; no other `useGrowingWindow` caller grows upward. It follows the newest row while scrolled to the end, through `useStickToEnd` (`hooks/useStickToEnd.ts`, #3671, shared with `LogList`'s Follow): rows are `skip-offscreen`, so the list's height grows a frame after a pin and the scroll event the pin causes reads a gap the reader never made. The hook therefore pins again when the `ul` resizes (`ResizeObserver`) and ignores a scroll that lands on the position it just set, so only the reader's own scrolls stop the following (up) or resume it (back to the end); a larger tolerance or a per-row-kind height estimate would still lose it, since the gap scales with what arrived. Once the ring has dropped rows it says so once, at the top - above the oldest row the ring holds, so only once the window has grown to it ("3 older rows dropped: the console keeps the newest 5,000 rows or 32.0 MB. History keeps each run, up to its own retention limit."). An empty ring and a filter that matches nothing are each an `EmptyState`, the second with a link that clears the filters.
- `RequestRow.tsx` - a Send or a script request: the shared `SampledExchange` row (`MethodBadge` and the masked URL as its title, a script request's script and level beside them; `StatusCodeBadge`, `formatLatency`; `formatBytes` and `TimeValue` in its last track), expanding to the timing tiles (a Send that reported `timing.scriptMs` adds a "Scripts" tile, #3739) and `ExchangeView`. Its actions: **Copy as cURL** and, for a Send that knows its run (a stream's, or a recorded buffered Send's, #3679), **Open run** (`openTab({ type: "run" })`).
- `StepRow.tsx` - a collection-run step, drawn live from its `step` frame with the step's name and outcome chip (`step-outcome.ts`, shared with History's `ScenarioStepCard`). A frame carries no exchange, so the expansion reads the step's stored row: `useRunReportQuery` - asked only while the row is open - and `stepRowsFromReport`, matched on iteration and position, then `responseFromRunResult` as History's step card does. It shows, in the order the step ran, the pre-request script's lines and requests (`ScriptLogs`, `ScriptError`), the timing (the stored `trace.scriptMs` as a "Scripts" tile, #3739) and the exchange, then the post-request script's. While the run streams nothing is stored yet and the row says the exchange arrives when the run ends (the run service invalidates the report then, so an open row fills in); a failed read says why with Try again; a finished run without the row says History has no stored copy. Its action is **Open run**.
- `LineRow.tsx` - a console line (a script's thrown error is one, at level `error`): the time, `LogGutter` with `LEVEL_TONE`, the message as written, and the script and level that wrote it (`ScopeTag`).
- `ExchangeView.tsx` - a row's exchange in `UnifiedResponseViewer`: the response body, the request body on the viewer's Request tab, and both header lists, every value as the row holds it. A body the ring cut at 256 KiB (`CONSOLE_BODY_MAX_CHARS`) says so above the viewer.
- `console-curl.ts` - Copy as cURL, through `generateCurl` from the row's masked request: the copy carries `<redacted>` wherever the row does, and the action's tooltip says so (and that the body is cut, when it is). `disableUrlEncoding` keeps the marker from being percent-encoded; codegen masking stays off, because the row is already masked. A row's URL with its userinfo password masked (`user:<redacted>@host`, the Send row and a script request's alike) becomes `-u 'user:<redacted>'` in the copy, which names the user and withholds the password.
- `console-rows.ts` - what the ring is handed. `sendConsoleRows` (through `appendSendToConsole`) is the one builder both Send completions call, the buffered `handleExecute` and the streamed `finalizeStreamRun`; it orders a Send's rows (pre-request lines and script requests, the Send, post-response) with the response pane's own `consoleRows`, adds a thrown script's `preScriptError` / `postScriptError` as an `error` line after its phase's rows (#3673), and masks the Send row before it is stored (`maskedExchange`: `isSecretHeaderName` (the engine logger's name set less the challenge headers) and the response's `authHeaders`; `maskUrlCredentials` with its `authQueryParam`, writing `user:<redacted>@host` as the engine does). A step's expansion masks its stored exchange with the same `maskedExchange`. `step-row.ts`'s `stepConsoleRow` is a collection-run `step` frame's row, appended by `scenario-run-service.ts`; it is a file of its own so the service, which `@/queries` reaches through `@/services`, does not import the response viewer.
- The rows, their bounds and the cut live in `stores/console-store.ts`; see [state-management](../state-management/engine-and-response.md#console-storets---the-session-consoles-rows).
- **Surface:** the tab sits on the panel's `bg-panel`; what it paints on a card (the exchange viewer) declares `surface-card`. → `BottomPanel.surface-rule.test.tsx`.

→ `ConsoleTab.test.tsx`, `console-filter.test.ts`, `console-curl.test.ts`, `console-rows.test.ts`, `request-builder/console-send-paths.test.tsx`, `stores/console-store.test.ts`.
