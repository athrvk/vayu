# App Shell

## `App` (`App.tsx`)

Root component. Renders `<TitleBar />` over `<Shell />`. On mount it wires up app-wide concerns via hooks/queries: OS/Electron theme sync (`useElectronTheme`), engine health polling (`useHealthQuery`), and prefetching of server state (`usePrefetchCollectionsAndRequests`, `usePrefetchRuns`, `useScriptCompletionsQuery`).

Those three are prefetches in the literal sense - they fill a cache once and do not observe it. The root deliberately mounts no polled query but `useHealthQuery`: an observer here lives for the whole session, so mounting `useRunsQuery` for its cache-warming side effect kept a 5s runs poll running with History closed and nothing at the root reading the result (#1150).

## Error Handling (`errors/`)

`main.tsx` wraps the whole render tree in `ErrorBoundary` (`errors/ErrorBoundary.tsx`), and registers `window.addEventListener("error")` and `("unhandledrejection")` beside it (issue #1558) - the boundary catches what a component's render throws, the two window listeners catch what it cannot (an event handler, a timer, a raw DOM listener, a promise nobody awaited). All three funnel through `errors/error-logger.ts`'s `logError` / `logApiError`. Inside Electron, `logError` forwards `{level, cat, msg, err, fields}` over the one-way `electronAPI.log` channel (`preload.ts` → `log:record` IPC → `log-ipc.ts` in the main process), which validates and bounds the shape, strips URL secrets from its text, redacts and applies the engine's `logLevel` floor before it reaches `app_<stamp>.log` as a `src: "renderer"` record - see [Engine Logging](../../engine/logging.md). Outside Electron (the vite-hosted sweep/probe harnesses `app/CLAUDE.md` describes, where `window.electronAPI` is absent) it keeps writing to `console.error` / `.warn` / `.info` by severity, the behaviour this issue found already in place. `ErrorBoundary`'s own fallback UI still renders locally either way - the log path only decides where the record goes, never whether the user sees the error.

## The two chrome rows

Top chrome is 32px + 32px, and the split is what makes both halves work:

```
[ icon | ............ centered search bar ............ | env switcher | controls ]  <- title row, --titlebar-height
[ drawer header band | tab strip over main + context, left edge = drawer edge    ]  <- --tabstrip-height
[ drawer body        | main content                    | context bar             ]
[ dock                                                                           ]
```

The title row belongs to the **window** (it is what drags it, and what the macOS traffic lights and the Windows caption overlay are drawn into); the second row belongs to the **content**. Tabs switch the main area and the context bar and never the drawer, so the strip is scoped to that column and its left edge follows the drawer's resize handle - it is the drawer's flex sibling, so there is no width to keep in sync. The drawer's own half of the row is `DrawerPanel`'s header band.

Both rows are tokenized: `--titlebar-height` (mirrored in `electron/constants.ts`, which sizes the real window frame and cannot read CSS) and `--tabstrip-height` (renderer-only - nothing the main process draws is that tall). `titlebar-height.test.ts` holds each token to its readers (and `GRAPHQL_PANE_HEADER_HEIGHT`, the JS twin of `--spacing-band`), and a top-anchored toast subtracts **both** (`constants/toast.ts`).

Tabs used to live in the title row. They are content-width and overflow into a dropdown, so every pixel another control took there converted directly into overflowed tabs - which is why a search bar could not simply be added beside them.

## `TitleBar` (`components/layout/TitleBar.tsx`)

Custom window title bar (Electron frameless window, `--titlebar-height`). Renders nothing outside Electron - there is no window chrome to draw. A 3-column grid (`minmax(0,1fr) auto minmax(0,1fr)`), so the search bar is centred on the *window* rather than on whatever space the two clusters leave. The bar is `clamp(2.5rem, 100vw - 36rem, 28rem)` wide - 28rem down to the 1024px window minimum, then it gives way - and the environment switcher shrinks and truncates rather than overlapping it; the chord caps hide by CSS below a 46rem window (#3494).

- **All platforms:** `NavigationControls` (Back / Forward, leading edge, issue #1245), `<CommandSearchBar />` (centre), `EnvPill` (right).
- **macOS:** Native traffic light inset (`--traffic-light-inset`, 104px left); no HTML window controls.
- **Windows:** App icon as the application-menu button on left click and the system-menu control on right click (left); native window overlay, no HTML controls in the bar.
- **Linux:** App icon as the application-menu button (left); custom HTML min/max/close buttons (right).

`AppIcon` is where the application menu is reachable at all on Windows and Linux (issue #1361): the window is frameless, so neither platform draws a menu bar, and the template `createMenu` installs contributed accelerators and nothing else there - Help > Documentation, About Vayu and Check for updates had no mouse route. Help › Third-party notices (#2693) sits outside the Windows/Linux-only group of that submenu, so macOS has it too; it opens the loose `THIRD_PARTY_NOTICES.txt` the installer ships (`electron/third-party-notices.ts`) and logs a failure rather than raising a dialog, and the About panel's credits point at it. Left click, Enter, Space, `APP_MENU_CHORD` (F10) and a tap of Alt all send `window:appMenu`, and main pops `Menu.getApplicationMenu()` at the icon: one template, two surfaces, no second menu in the renderer. The labels that differ by surface (Title Case in the macOS menu bar, sentence case in this popup) come from `menuLabels(platform)` in `electron/menu-labels.ts`, and the settings item reads "Settings…" on both (#3500). Both keyboard routes ask `isModalOpen()` first, and the Alt tap is a state machine (`lib/alt-tap.ts`) rather than a `Chord`, because Alt held as a modifier - Alt+Tab, Alt+← - is not a menu request. Losing focus, a pointer press and a wheel turn mid-hold (Alt+scroll, #3403) cancel the tap too. macOS renders no button and registers no listener; its menu bar draws the same template already. → `app-icon-menus.test.tsx`, `electron/app-menu.test.ts`.

The entire bar is marked as a drag region (`WebkitAppRegion: "drag"`) except for interactive elements, which explicitly set `no-drag` - a drag area ignores every pointer event, so a control that forgets is dead rather than merely awkward. Opting out per control or per cluster is fine; opting out a wrapper that spans the row's slack is not, because that slack is what the window is dragged by. → `TitleBar.search-bar.test.tsx`.

The env switcher's accessible name is its visible text behind an `sr-only` "Environment: " prefix ("Environment: Staging"), never an `aria-label`: a label replaces the visible name, so a speech-control user saying "click Staging" matched nothing (WCAG 2.5.3). → `TitleBar.search-bar.test.tsx`.

The env switcher's menu is controlled by `env-switcher-store` (issue #2115) rather than left to Radix: the import's toast action **Choose environment** has no other way to open it. The menu's own open and close write back to the store. → `TitleBar.env-switcher.test.tsx`.

`NavigationControls` puts Back and Forward at the leading edge, each a `TooltipIconButton` with its own `no-drag`, disabled when its half of `navHistory` is empty (`canGoBack` / `canGoForward`), and a tooltip naming its chord (`GO_BACK_CHORD` / `GO_FORWARD_CHORD`).

The logo is imported as a module (`@shared/icon_png/...`), not referenced as `/icon.png`: the import is what puts the file through the build and into `dist/`. The packaged document is served from `vayu-app://app/` (#2380), so a root-absolute path now resolves against `dist/` rather than the filesystem root, but it still names a file the build never emits.

## `CommandSearchBar` (`components/layout/CommandSearchBar.tsx`)

The palette's visible entry point, in the title row. A `<button>` styled as an input: it looks like a field because that is what makes ⌘K discoverable, but typing happens in the palette's own input - a real field here would be a second query state and a second ranked list to keep in step. Clicking sets `paletteOpen`; the hint it prints is one `Kbd` cap per key from `chordKeys(PALETTE_CHORD)` (`constants/shortcuts.ts`), the same constant `CommandPalette`'s listener matches, so the bar cannot advertise a chord nothing handles.

## `TabStrip` (`components/layout/TabStrip.tsx`)

Horizontal row of open tabs plus a "+" button, rendered by `Shell` over the content column (not in the title bar). Reads from `useTabsStore` (open tabs, active tab, add/close/focus methods). Takes its height from `--tabstrip-height` and carries no `app-region` markers - nothing down here drags the window.

Labels and icons come from `tab-descriptors.ts`, a sibling module rather than this file, because the command palette lists the same tabs and must name them identically - a tab that reads "GET /v1/orders" in the strip and "Request" in the palette is two answers to one question.

- **One tab per open entity**, deduplicated per type and `entityId`. Tabs show: icon (method badge for requests, folder for collections, lightning for dashboard, etc.), label (request method + URL path / collection name / screen name). A request tab with no name of its own is titled from the URL as the Params panel's **Sends** line resolves it (`request-builder/utils/sends-url.ts`, #2637), so a `:name` path row's value and `disableUrlEncoding` read the same in both; the title differs from the line only in what the wire adds, since it cuts the fragment but never carries the auth's query parameter (an API key or an OAuth 2.0 token) or a GraphQL GET's document (#3437). A name a pre-request script sets at send stays written as `{{name}}` in that title (#2741): the names are the engine's `deferredVariables`, read from the compose cache entry the Params panel and the Code section share (`useCachedDeferredNames` in `tab-descriptors.ts`, a disabled observer per request tab, never a fetch - the strip must not pay a `POST /compose` per tab), so a tab nobody has opened keeps the stored URL in its title until one of them has composed the request.
- **Max 12 tabs** with LRU eviction when exceeding: the least recently focused tab (`tabFocusedAt`, not strip order) goes first; dashboard tabs are exempt from eviction. Dirty tabs (unsaved) are skipped during eviction (autosave is the safety net).
- **Middle-click closes** a tab (browser-like).
- **An empty strip says what to do, and does not collapse** (issue #1688). With no tabs open it was a blank 32px band with a lone "+" - a user whose last tab had just closed had nothing on screen saying where the app went. It now carries a muted line, "Open a request from the sidebar, or press <chord>", with the chord read from `constants/shortcuts.ts` through `formatChord` so the modifier is this platform's. The band itself stays: its height is the same token the drawer's header band reads, so a strip that disappeared would leave that header as a step in the rule running across the window and would jump the content area by a band's height at the moment the last tab closed. → `TabStrip.empty.test.tsx`
- **No unsaved dot** - autosave ensures safety.
- **Keyboard support:** ⌘1–9 jump to tab, bound to the physical digit row (`e.code`) rather than to the character it types, so they work on AZERTY and every other shifted-digit layout; displayed via dock shortcuts. ⇧⌘] and ⇧⌘[ sit beside them, matched by `code` (`BracketRight`/`BracketLeft`) for the same layout reason, and step to the next and previous open tab. All four chords are `Shell`'s, not the strip's, and all four **activate** the destination tab - the bracket pair through `focusAdjacentTab` (`tabs-store.ts`, `openTabs` order, wrapping at both ends), the digits by direct index - where the strip's own Left/Right move only DOM focus along its roving tabindex and leave the active tab untouched.
- **The strip is one Tab stop, and stays one.** Roving tabindex: exactly one tab carries `tabIndex=0`, Left/Right/Home/End move focus within the strip, and Enter or Space activates - focus moves *without* activating, so skating past a dashboard tab mounts nothing. The stop is component state, not a DOM write (#1856): `useRovingStop` (`components/layout/useRovingStop.ts`) holds it, follows the active tab, and lets an arrow press move it away until the active tab changes or the arrowed-to tab closes or drops out of the strip, when it falls back to the active tab. It reaches `TabItem` as `isRovingStop`, which `tabItemPropsEqual` compares, so the memo re-renders the tab that gains the stop and the one that loses it. Written onto the element instead, the stop sat on top of a prop React never re-applied: arrow then click left two `tabindex="0"` tabs, and arrow then Delete left none. Delete or Backspace closes the focused tab (both keys, since a Mac's "delete" reports `Backspace`). → `TabStrip.keyboard.test.tsx`
- **Alt+Arrow / Home / End move the focused tab** (issue #2038). Alt+← and Alt+→ move it one place, Alt+Home and Alt+End to either end: `MOVE_TAB_*_CHORD` in `constants/shortcuts.ts`, matched by `matchesChord` in the strip's own `onKeyDown` rather than at `window`, because they act on the *focused* tab and only the strip knows which that is. The target is read from the focused tab's place in the store's `openTabs`, not among the tabs that fit, so a move is a statement about the whole list; at an end the move is a no-op and the key is still taken. The handler goes through `moveTabAndFocus` (`tab-focus.ts`), which flushes the write and refocuses the tab - Chromium drops focus to `<body>` from an element React reinserts - and moves the roving stop with it, without activating the tab. These are the one overlap with `Shell`: off macOS Go back and Go forward are the same Alt+←/→. The strip resolves it as the tree does, taking the chord only while a `role="tab"` element has focus and calling `stopPropagation` so `Shell`'s window listener never sees it; Go back stays reachable from every other focus, the title-bar buttons, the palette and mouse buttons 3 and 4, and on macOS it is ⌘[ and nothing collides. The palette carries **Move tab left** and **Move tab right** (`lib/commands/registry.ts`), which act on the *active* tab where the chord acts on the focused one - the same split Close Others records; Home and End are repeats of those and have no row (`palette-parity.test.ts`). → `TabStrip.keyboard.test.tsx`, `tabs-store.move.test.ts`
- **Tabs drag to reorder** (issue #2039), the pointer half of moving a tab beside the Alt+Arrow chords. `useTabStripDnd` (`components/layout/useTabStripDnd.ts`) is `useTreeDnd` with everything tree-shaped removed: the press-versus-drag gesture (`lib/drag/drag-gesture`, ~4px, never a timer, so a click that wobbles is still a click), the slot maths (`lib/drag/drop-slot`) and pointer capture on the pressed tab. A drop is one `moveTabAndFocus` call, the keyboard path's own, and then hands the roving Tab stop to the moved tab; the active tab is not changed and a drop never stamps focus for the LRU. The slot indexes the tabs the strip *renders*, and a slot lands right after the visible tab to its left (the end slot after the last rendered tab, which is the end of the list when the active tab was surfaced from the menu), so a drop beside a run of hidden tabs lands at the head of that run and the dropped tab stays on screen. Whether a slot draws a line is decided in store terms, on the landing index, not on the visible neighbours: a slot that is a real move across a gap of hidden tabs shows its indicator. **No edge auto-scroll**: the strip is `overflow-hidden` on purpose and what does not fit lives in the "+N" menu, so there is nothing to scroll; `slotAt` counts midpoints, so a pointer over the "+N" trigger or the "+" button names the slot after the last tab with no clamping. Tabs inside the overflow menu are not draggable (a Radix menu captures the pointer and closes on press); choosing one surfaces it in the strip, where it drags like any other. A **release above or below the strip cancels**, as do Escape (a `window` listener while a drag is live) and `pointercancel`; a completed or cancelled drag swallows the one trailing click in `onClickCapture` (`consumeClick`), or the dropped tab would activate. A press on the close control (`data-tab-close`) is not a press on the tab. The dragged tab dims (`opacity-50`, the tree's drag-source class) and the slot is a 2px `DropIndicator` inside the tab beside it; no ghost, no raised surface, and no slide - React re-keys the moved tab and the tabs reflow, so the only motion is the opacity transition `TabItem` already had, and nothing new needs a `prefers-reduced-motion` guard. **The state reaches `TabItem` through `TabStripDndContext`** (`TabStripDndContext.ts`: `draggingId`, the tab and edge the line is drawn on, and one stable handlers object whose tab id is read from `data-tab-id`), not props, so `tabItemPropsEqual` is unchanged: the value is the same object at rest and changes only while a drag is live, which is what keeps `TabStrip.render-count.test.tsx` as it was. The indicator is `aria-hidden` and lives inside a tab, never as a `role="tab"` sibling. → `TabStrip.dnd.test.tsx`
- **A close from the keyboard hands focus on.** The tab holding focus is the one that unmounts, so closing it without claiming focus dropped the user to `<body>` and the next Tab restarted from the top of the document (#1218). All three keyboard-driven paths - Delete/Backspace here, ⌘W from wherever focus is, and the palette's **Close tab** row (#3401) - go through `closeTabFromKeyboard` (`tab-focus.ts`), which focuses the store's own choice of next active tab, or the "+" button (`data-tab-new`) when the last tab was the one closed. It flushes the store write first: the strip renders only the tabs that fit, so the tab that becomes active can be one the overflow menu was holding a moment ago. The palette closes itself and flushes that close *before* it runs the picked command (`CommandPalette`'s `pick`): while the dialog is open its focus trap pulls focus back into the search field, and the palette's restore-focus effect would otherwise take it to whatever held focus before the palette opened, so a command that moves focus has to run after both. The mouse paths are untouched - a click has already put focus where the user meant it. → `TabStrip.keyboard.test.tsx`, `Shell.close-tab-focus.test.tsx`, `CommandPalette.test.tsx`, `registry.test.ts`
- **Section-tab strips share the fit.** `useFittedTabs` (`components/layout/useFittedTabs.ts`) is `TabStrip`'s measured-fit for Radix `TabsTrigger` strips, with `TabOverflowMenu` (`components/layout/TabOverflowMenu.tsx`) as the `+N` menu; the request builder's `RequestTabs` and the response viewer's `ResponseViewer` use them instead of scrolling (#2200). The widths come from `tab-fit.ts` (`naturalTriggerWidth`, `MARK_ALLOWANCE`, and `fitTabs`' `reserved` option, whose default is this strip's New-tab button), and the hook measures a wrapper around the `TabsList`, never the list. A hidden tab keeps its marks: `TabOverflowMenu` takes an optional `mark` node per tab, drawn after the label in its item, and an `attention` flag that puts a `TabErrorDot` on the `+N` trigger and names the tab in its `aria-label` ("3 more tabs, Console has an error"), so a failure is not lost to the menu.
- **The tablist holds tabs and nothing else.** The overflow "+N" trigger and the "+" button are siblings of the `role="tablist"` element, not children: inside it they are announced as part of the tab set. Each tab carries `id`/`aria-controls` (`tabElementId`, `tabPanelElementId`), and `Shell` gives the content region the matching `role="tabpanel"` + `aria-labelledby` - the WAI-ARIA relationship in both directions.
- **Right-click opens a menu of its own** (`tab-actions.ts`, issue #1360): Close, Close Others, Close to the Right, Close Saved, plus Copy Path for a loaded request tab (the collection chain and the request name, from `useTabDescriptors`) and **Copy for agent** for every tab that names an entity (request, collection, run, inbox, mock server; #2047). The line is the descriptor's `agentReference`, built in `useTabDescriptors` for the reason `path` is: a request tab's from the request's own name, never the URL-derived title; a run tab's from the loaded run through `lib/run-reference-input.ts`, since `GET /runs/:id` carries a `configSnapshot` and no `summary`; an inbox or mock-server tab's from the record `lib/shown-service.ts` says the tab shows, the lowest port when the tab has no address. Each is absent until its entity has loaded, and the welcome, settings, variables and dashboard tabs have none. No Duplicate - the store allows one tab per entity, so a second tab on the same request is not a menu item withheld here, it is a shape `openTab` refuses; duplicating the *request* is a different action under the same word, and it stays on the request's own row (decided in #1389, not deferred). The keyboard path needs no handler of its own: the platform's own contextmenu event (Menu key / Shift+F10) reaches the same `RowContextMenu`. Close Others, Close to the Right and Close Saved are store actions (`closeOtherTabs` / `closeTabsToRight` / `closeSavedTabs`), not a loop of single closes - see [tabs-store](../state-management/tabs-layout-session.md#tabs-storets---open-tabs--navigation). The same three are commands in `lib/commands/registry.ts`, so the palette reaches them too; they take the *active* tab where the menu takes the one under the pointer, and neither carries a chord - a keystroke that closes a strip full of tabs is one slip from losing the lot.

## `Shell` (`components/layout/Shell.tsx`)

Main layout: tab-centric with an activity rail, resizable drawer, split/overlay context bar with its own rail, a bottom panel under the main row (closed by default), and a docked footer (status in the centre, the bottom panel's button and per-tab view controls on the right).

- **One uniform layout for every tab** - `ActivityRail` + `Drawer` (left) + a content column holding `TabStrip` over main + `ContextBar` + `ContextRail`. No tab type takes over the row. This is deliberate: the rail's view switchers always have a Drawer to act on, so they can never be dead. (Settings used to full-take-over and suppress the Drawer, which left those buttons doing nothing while Settings was open.)
- **Left navigation is always the Drawer.** Every main view that needs a category/entity list uses the shared Drawer for it - never its own left rail. `SettingsMain` and `VariablesMain` are pure content panes; their category trees live in the Drawer (`settings` / `variables` views). Follow this pattern for any new view - do not add a second sidebar inside the main area.
- **Keyboard handlers:** ⌘N (new request - a blank one opens with the caret in its URL field, so typing starts at once, #3400; one created from a preset leaves focus where it was), ⌘S (save), ⌘W (close tab), ⌘B (toggle drawer), ⌘L (focus the URL bar), ⇧⌘E/H/U/S/T (drawer views), ⇧⌘] / ⇧⌘[ (next/previous tab), ⌘I (toggle context bar), ⌘J (toggle the bottom panel, #3635; Monaco binds no plain CtrlCmd+J, so it needs no `editor-chords.ts` bridge), ⇧⌘B (toggle the response position - beside or below the request - on a request tab only, #1711), ⌘, (open settings tab), F6 / ⇧F6 (next/previous region), and the navigation pair - ⌘[ / ⌘] on macOS, Alt+← / Alt+→ elsewhere (back/forward through the tab history, #1245). Every one of them is a `Chord` in `constants/shortcuts.ts`, matched by `matchesChord` - the same registry the `ActivityRail`'s tooltips advertise from, so no surface can claim a chord the handler does not listen for. They were fourteen hand-rolled comparisons until #938, which is how AltGr (Ctrl+Alt on European Windows layouts) came to fire Save and close tabs, and how ⌘1-9 came to be dead on AZERTY. F6 and ⇧F6 carry no ⌘ or Ctrl - the only chords here that do not - so a module-level `regionStep` helper matches them **before** the `if (!(e.metaKey || e.ctrlKey)) return` gate - as does `navigationStep`, for the same reason off macOS, where the navigation pair is Alt+← / Alt+→ (it declines a target that `ownsEnterKey`, so Monaco keeps the CtrlCmd+[ and +] it binds to outdent and indent) that keeps this listener off the typing path for everything else, still behind the `isModalOpen()` check every chord here shares. Off macOS the navigation pair is Alt+Arrow, the same chord the collection tree uses to reorder a row and the tab strip uses to move the focused tab, so neither widget's handler lets the event reach this listener: each calls `stopPropagation` while its own row or tab holds focus. Go back and Forward stay reachable from every other focus, the title-bar buttons, the palette and mouse buttons 3 and 4. The native menu's chords (zoom, full screen, close window, quit) and the collection tree's and tab strip's own keys (Alt+Arrow to move a row, F2, Delete, the row menu, Delete to close a tab) are **not** in this map either - Electron's menu and the focused element's `onKeyDown` take them first - but they are `Chord`s in the same file, listed in the panel and display-only: never pass one to `matchesChord` or a live handler (#3325). F8 (focus the notification stack) is the same shape: Radix's `ToastProvider` binds it, `FOCUS_NOTIFICATIONS_CHORD` only lists it (#3498). ⌘K (command palette) is **not** in this map - it is owned by `CommandPalette`, on the capture phase, because Monaco swallows the key on the bubble. It still honours the modal rule: it asks `isModalOpen()` itself and does nothing over another dialog (#3320), except that with the palette already open the chord closes it, since the palette is the open dialog. ⌘I is in the map and still needs help reaching it: Monaco claims CtrlCmd+I for `triggerSuggest`, so the bridge in `lib/editor-chords.ts` re-dispatches it from inside an editor (see [`code-editor`](ui-primitives.md#code-editor)), as it does the two send chords and, now, ⌘L - Monaco binds CtrlCmd+L to `expandLineSelection` the same way it claims CtrlCmd+I.
- **Region cycling (F6 / ⇧F6).** `cycleRegionFocus` (`region-focus.ts`) walks the shell's regions in document order - the eight bands carrying `data-app-region` (`TitleBar`'s `<header>`, `ActivityRail`'s `<nav>`, `Drawer`'s `<aside>`, `Shell`'s own `<main>`, `ContextBar`'s `<aside>`, `ContextRail`'s `<nav>`, `BottomPanel`'s `<section>` while it is open (#3635), the `Dock`'s strip; the last two since #3498), each spreading `regionProps("<band>")` from that file rather than writing the attribute itself, so the name it queries is spelled in one place - skipping any with nothing focusable and never re-entering the region focus is already in. A closed band (the drawer, the context bar) is simply absent from the DOM, so the cycle needs no knowledge of visibility. `ActivityRail` and the `Dock` are always present, unlike the drawer and context bar, so they are never bands the cycle has to skip; the `ContextRail` is present whenever the active tab has context to show. The `TabStrip` is deliberately not a band: it is the main pane's header, one roving tab stop directly above `main` that Shift+Tab reaches from the pane, with chords of its own (see `docs/design-system.md`). It lands focus on the region's first focusable element, found through `lib/focusable.ts` - the same `focusableWithin`/`focusFirstOf` pair `lib/editor-chords.ts` uses for the Monaco Tab-trap exit - rather than on the region container itself, which under the app's `:focus-visible` rule paints no ring for a `tabindex="-1"` element and would move focus with nothing on screen saying where it went. ⌘L is the same idea aimed at one field: `focusRequestUrl` (also `region-focus.ts`) finds the URL input by id - `REQUEST_URL_INPUT_ID`, declared in `constants/dom-ids.ts` since the Shell has no ref into the request builder that mounts the field - and does nothing when no request tab is open.
- **Drawer:** toggles visibility via `toggleDrawer()` (state in `useLayoutStore`); always resizable 220–480px.
- **Side panel modes:** one `useWindowWidth()` (`hooks/useWindowWidth.ts`) feeds `sidePanelMode(width, threshold)` for both panels, with the thresholds named in `constants/layout.ts`: `DRAWER_PUSH_MIN_WIDTH` (1000) and `CONTEXT_BAR_PUSH_MIN_WIDTH` (1200), window CSS px, push at or above. The drawer and the content column share a `relative` box that leaves out the `ActivityRail`, so an overlaying drawer opens over the content's left edge and never over the rail that toggles it (#3494). The box is there in both modes, so crossing a threshold changes a class list, not the tree the tab renders into. `Shell` computes both modes once and hands each panel the other's as `siblingMode`. → `Shell.panel-modes.test.tsx`, `side-panel-mode.test.ts`.
- **Content routing:** switches main area based on `activeTab.type` (welcome | request | collection | dashboard | run | variables | settings | inbox | mock-server). Default is `WelcomeScreen`.
- **Every surface but `RequestBuilder` is `React.lazy`** (#1146), behind one Suspense boundary inside the tab panel whose fallback is a `DetailSkeleton` naming the pane. Only one surface is mounted at a time, so a boundary per branch would be the same fallback written eight times. `RequestBuilder` stays eager because it is what most sessions open into. Two consequences worth knowing: a surface must be imported from its own file rather than its module barrel (`@/modules/settings` also exports the Drawer's `SettingsCategoryTree`, so importing the barrel here would put the settings surface back in the entry chunk), and a lazy branch is still one component per tab type - the boundary does not remount tab content, which `shell-tab-identity.test.tsx` holds.
- **Drawer-view sync:** an effect points the Drawer at the view matching the active tab - `variables`→variables, `settings`→settings, `request`/`collection`→collections - and opens it. It fires on a change of tab type; switching between two tabs of the same type leaves the drawer's open state alone, so a drawer the user closed stays closed (#1863).
- **ContextBar mode:** "push" at or above `CONTEXT_BAR_PUSH_MIN_WIDTH` (1200px), "overlay" below it. It renders on the tab types the section registry has entries for - request, collection and run - and nothing on the other four. `relative` sits on the main+context row rather than on the outer one, so the overlay stops at the tab strip instead of covering the tabs it belongs to. `ContextRail` is a sibling of that `relative` row, not a child of it, so an overlaying `ContextBar` covers `main` up to the rail and never the rail itself (#1615). An overlaying bar closes on Escape (focus inside, nothing of its own open above it, focus back to its rail), on a pointer press outside, and when the drawer starts showing as an overlay (the most recent wins, the drawer where neither opened; the loser's persisted flag is written false), through the same `useOverlayPanel` as the drawer; it never closes on a selection, having none (#3507).
- **The content region is the strip's tab panel.** A `role="tabpanel"` div inside `main` (not on `main`, which is a landmark and carries only `role="main"`), carrying the active tab's panel id and naming that tab with `aria-labelledby`. → `shell-tab-identity.test.tsx`.
- **The restructure must not remount tab content.** Drawer state is upstream of the column the active tab renders into, so a `key` derived from it - or a wrapper mounted only while the drawer is closed - throws away an unsaved body, a scroll position, a Monaco model. → `shell-tab-identity.test.tsx`.
- **`<ImportModal />`** and **`<CommandPalette />`** mounted once each as global overlays; visibility in a store rather than in the Shell.
- **`<RunAnnouncer />`** mounted once, outside the tab panel: the polite region that says a load test or collection run started and how it ended, from `dashboard-store`'s phase and `scenario-run-store`'s `endedAs` and `endedByEngineStop` (`run-announcement.ts` holds the sentences; a load test whose engine's process ended under it says "Load test ended. Vayu's engine stopped", #3605, and a collection run says "Collection run ended. Vayu's engine stopped", #3621). A collection run's ending names a missed budget after the step counts ("Collection run completed. 12 passed, 0 failed. 1 of 2 budgets missed: p99", #3539), from the budget block the service writes with `endedAs`. Not inside a run view, because a run usually ends while its tab is not the one mounted, and a live region announces only a change to a node already in the DOM. → `RunAnnouncer.test.tsx`, `shell-tab-identity.test.tsx`.

## `Drawer` (`components/layout/Drawer.tsx`)

Resizable sidebar (220–480px, one width shared by every view - `layout-store` collapsed the per-view widths in v3). The single left navigation for the whole app - one of six views per `useLayoutStore.drawerView`. Every view is titled: its `DrawerPanel` header is the drawer's half of the second chrome row, sharing `--tabstrip-height` and its bottom rule with the tab strip across the resize handle, with an optional tools slot beside the title.

| View | Component | Band tools today |
|------|-----------|------------------|
| **`collections`** | `CollectionTree` (hierarchical collections + requests) | add collection, add request, new request from a template, import |
| **`history`** | `HistoryList` (past runs, filtered/sorted) | run count |
| **`variables`** | `VariablesCategoryTree` (globals, environments, collections) | - |
| **`services`** | `ServicesPanel` (webhook inboxes, OAuth issuers, mock servers) | new inbox, new issuer |
| **`trash`** | `TrashList` (deleted collections, requests, environments, saved examples and client certificates, restore or purge for good) | item count |
| **`settings`** | `SettingsCategoryTree` (app + engine setting categories) | - |

Both `variables` and `settings` follow the same nav/content split: the tree lives here in the Drawer, the editor is the corresponding tab (`VariablesMain` / `SettingsMain`), and selecting a category sets the shared store selection **and** opens/focuses that tab.

A `TrashList` row is a `data-trash-id` box carrying `tabIndex={-1}` and `.focus-row`: not a tab stop in front of its buttons, but a target focus can be *put* on - which is what a permanent delete needs, since its confirm dialog has no trigger for Radix to restore to and the row it was opened from is about to go. Where focus lands follows the outcome rather than the confirm click, through the shared `useRemovalRefocus` (`hooks/useRemovalRefocus.ts`, also the collection tree's): the purged row while it is still there, and the next row - or the previous one, when the purged row was last - once it has actually gone (#1234). Purging the only entry leaves neither, and Trash has no create control to fall back on, so focus goes to the `data-trash-list` container itself, which stays mounted holding the empty state (#1279). The variables sidebar's environment rows delete the same way, through the trees' `useDeleteRefocus`. A row's secondary line names the kind, the owner of a request or example (`parentName`, "from <name>", so two same-named entries tell apart, #3449) and, for a collection, what a purge destroys (the engine's `purgeCollections` / `purgeRequests`, not the cohort a restore brings back); the "Delete forever" dialog for a collection states the same totals (`collectionPurgeDescription`). The retention line under the title says the sweep runs when Vayu starts ("Items more than 30 days old are permanently deleted the next time Vayu starts."), because the engine sweeps once at start and never on a timer. Its three buttons (Copy for agent, Restore, Delete forever) take no width until the row is hovered or focused, through the same `ROW_ACTIONS_REVEAL` the History rows use (#3495): they stay in the DOM and in the tab order, a device with no hover keeps them showing, and the secondary line is one truncated line whose full sentence is its `title` while it is cut.

Resize handle on the right edge (double-click resets to defaults). Visibility toggled by `toggleDrawer()` or ⌘B.

- **Push mode** (≥1000px, `DRAWER_PUSH_MIN_WIDTH`): the content column's flex sibling, takes layout space.
- **Overlay mode** (<1000px): floats over the content's left edge (`absolute left-0 top-0 bottom-0`, `shadow-lg`, `z-10`, the context bar's set mirrored), so opening it does not reflow the content. Same toggles, same F6 stop, same width and collapse animation as push mode. Besides its toggles it closes on Escape (focus inside, nothing of its own open above it), on a pointer press outside, when the context bar opens as an overlay, and when a drawer item opens a tab (`useDrawerItemOpened()` from `drawer-item-opened.ts`: the collection tree's request and collection rows, a history run, a variables scope, a settings category, a Services row, and every create that opens a tab - the toolbar's New request, a row menu's Add request, New environment; not Duplicate or the undo of a delete). Push mode does none of that. All of it is `useOverlayPanel` (#3507), shared with the context bar; the rules are in `docs/design-system.md` under "Push or overlay". → `Drawer.overlay.test.tsx`, `useOverlayPanel.test.tsx`, `Shell.overlay-panels.test.tsx`.

The threshold is 40 + 480 + 440 + 40: both rails, the drawer at its maximum width, and one 440px builder pane of content (the derivation is in `constants/layout.ts`). The maximum rather than the current width, so dragging the handle never flips the mode mid-drag.

## `ContextBar` (`components/layout/ContextBar.tsx`)

252px panel showing a stack of collapsible sections about the active tab. It owns the frame - landmark, resize handle, header, scroll container, per-section collapse state - and nothing about what any section shows.

- **Push mode** (≥1200px, `CONTEXT_BAR_PUSH_MIN_WIDTH`): adjacent to main content, takes layout space.
- **Overlay mode** (<1200px): floats over main content, top-right (absolute positioned, shadow, z-10).
- **Toggle:** ⌘I, or any `ContextRail` icon. Visibility in `useLayoutStore`. `ContextRail`'s own visibility is "the active tab has content for the bar" (`contextBarHasContent`, shared with the bar itself) - previously the Dock's toggle button was pressed on `contextBarOpen` **and** that predicate, since a lone open flag lit it up on tab types the bar renders nothing for; the rail's per-section buttons now carry that same "open and expanded" logic individually. That predicate reads only `appliesTo`, never a section's `useRelevance`, and stays that way on purpose: it has to answer while the bar is closed, and a relevance hook run then would issue queries for a bar nobody opened.
- **Structure:** an `<aside>` landmark ("Context sidebar"), like the Drawer facing it. The resize handle and the header are direct children; the scroll lives on an inner wrapper (`data-context-bar-scroller`, the target `ContextRail`'s `scrollWithin` call scrolls), so the drag strip and the close button stay put while the sections scroll. Each section is wrapped in a `data-context-bar-section="<id>"` div - the anchor the rail scrolls to - since a section hidden by its own `useRelevance` renders nothing for `scrollWithin` to find otherwise. The left edge is the handle's own 1px hairline - the panel draws no `border-l` of its own.

## `ContextRail` (`components/layout/ContextRail.tsx`)

The right-edge counterpart to `ActivityRail`: one `RailButton` (`"tile"` variant) per entry `sectionsForTab(activeTab)` returns, so it renders nothing on a tab the bar has nothing for - the same `contextBarHasContent` predicate the bar itself and the old Dock toggle used. Clicking a section's icon opens the bar if closed, expands the section if collapsed, and scrolls it into view with `scrollWithin` (`@/lib/scroll-within`, #1612) - deferred to a `requestAnimationFrame` inside the click handler rather than called synchronously, since the target may not exist (or may still be collapsed) until React commits the open/expand state the same handler just requested; `requestAnimationFrame` runs after that commit's paint, not before it, which a `useEffect` keyed on the pending id would (correctly, but redundantly) achieve by calling `setState` from inside an effect body - `react-hooks/set-state-in-effect` is why this is a plain callback instead. Clicking the icon of the section that is the *only* one currently expanded collapses the whole bar instead - this rail's answer to a dedicated close button. The rail is one roving Tab stop, not one per section: `useRovingStop` holds it on the first expanded section (the first section when all are collapsed), and Up/Down move focus without toggling, wrapping at the ends - the model `ActivityRail` uses. → `ContextRail.test.tsx`. Present in both of `ContextBar`'s layout modes, including overlay (<1200px): it is a flex sibling of the `relative` box the bar overlays from, not a child of it, so the rail is never covered by the bar it fronts.

### The section registry (`components/layout/context-bar/registry.ts`)

`CONTEXT_BAR_SECTIONS` is one ordered list of `{ id, title, icon, appliesTo(tab), useRelevance?(tab), Component }`. `sectionsForTab(tab)` filters it on `appliesTo`, and `contextBarHasContent(tab)` is `sectionsForTab(tab).length > 0` - so the bar's visibility and `ContextRail`'s own visibility read the same list and cannot drift. Adding a section for another tab type is one entry here and nothing else - `icon` is what `ContextRail` draws, so a section with none would leave the rail silently short a button rather than failing near the registry (`registry.test.tsx` asserts every entry carries one). `appliesTo` stays a pure, synchronous function of the tab alone and never a query: `contextBarHasContent` is called on every render of `ContextRail` and the old Dock toggle alike, including while the bar is closed, and a predicate that read a query could not be called from there at all.

`useRelevance` is the second, optional question a section can answer, asked only by the bar and only while it is open: how much this section has to say about *this* request, once its own data is in, rather than just this tab type. It answers `"content"` (draw as usual), `"hidden"` (draw nothing - the section structurally does not apply to this request, such as GraphQL off a non-GraphQL body or cookies before the URL has a host), or `{ empty: note }` (draw the header alone, with `note` after the title and no chevron, since there is nothing to expand). A section without one is `"content"` by definition, which is why the collection and run sections carry none. Before this, a plain REST request opened seven sections of which three existed only to say they did not apply ("This request does not send a GraphQL body", "No cookies held for this host", "This request has not been sent yet"), a header the reader scanned past on every tab (#1310).

**A section's component is mounted only while its section is expanded** (`context-bar/Section.tsx`), which is most of the cost model: the bar is open on every tab that has sections, so a collapsed section must register no queries. The one exception is a section's own `useRelevance` hook, which runs whenever the bar is open, expanded or not - so the precise guarantee is "no section mounts, and no query beyond the one its relevance already needs"; every relevance hook reads a query its own section already reads. Collapse state persists per section id in `layout-store` (`contextBarCollapsedSections`, collapsed-by-exception), and `code` is the one section that ships collapsed by default (`CONTEXT_BAR_DEFAULT_COLLAPSED`): its query is a `POST /compose` round trip, so an expanded-by-default Code section would have composed a snippet on every request tab opened, whether or not anyone looked. It declares no `useRelevance` for the same reason - answering would mean composing to find out.

**Mounting late is not the same as loading late.** A registry entry is imported when the registry is, and the bar is on every tab - so the GraphQL section, the one entry that reaches the `graphql` package (~320KB of source, through `parseGraphQLBody` and the schema cache), is a `React.lazy` component and arrives when it first renders (#1146). `ContextBar` wraps each section in its own Suspense boundary with `SectionLoading` as the fallback, so a section still loading looks like a section still fetching and cannot blank the ones beside it. Every other section is app code and Radix, and stays eager; a new one only needs the lazy form if it drags a parser-sized dependency in with it. Since `useGraphQLRelevance` now hides the section outright off a non-GraphQL body, "renders" no longer means "every request tab": a REST tab never requests the chunk at all, where it used to arrive the moment the expanded section mounted just to say the request was not GraphQL (#1310).

Sections are leaf components over the existing query layer - no bar-wide shared state - each with its own loading and empty body (`SectionEmpty`, `SectionLoading`).

`run-scenario.ts` is the one place the snapshot's `scenario` block is narrowed
(it arrives as `unknown` through `RunConfigSnapshot`'s index signature). It gates
on `run.type === "scenario"` as well as the key, so a load run whose raw body
happened to carry a `scenario` the engine ignored is never described as one.

The collection and run sections gate on `tab.entityId` as well as the type: a tab open on nothing renders no pane either, and a section there would query nothing while lighting `ContextRail` over an empty bar.

**`collection-last-run` was deferred twice before it landed** (specced in #377, deferred in PR #394 as "no runs exist until #354", re-deferred in PR #400 once the runner existed), each time for the same reason: a collection's runs were not addressable. `GET /runs` filtered by `requestId`, a collection run links none, and the only route to the row was a substring search of every stored snapshot for the collection id - a scan per open bar. #422 added `GET /runs?collectionId=`, which matches the scenario snapshot's own field as JSON rather than its text, and the section is one filtered query for exactly the row it shows.

**There is still deliberately no "last result" section**, and `recent-sends` is not one. Status, duration and age of the *last* send are what `ResponseStatusBar` already paints in the response pane on the same screen - same `StatusCodeBadge`, same stored run, since the builder restores that run into the pane whenever nothing is in memory. A section with no state in which it says something the pane does not say better is a duplicate, not a summary, which is why the specced one was built and removed in #344. What the pane structurally cannot show is *more than one send*, and that is the whole content of `recent-sends`: if it ever narrows to the latest run it is the removed section again. Its id is new rather than reused, so the `last-result` guard in `registry.test.tsx` keeps guarding.

That section is affordable because the paginated `GET /runs` now carries each design run's outcome on its row (`resultSummary`: `statusCode` + `latencyMs`), added for it in #380. Before that, N rows meant N `GET /runs/:id/report` calls, and that path loads and JSON-parses every result's `trace_data`. A terminal collection run's row carries `{passed, failed, skipped, errored, stopped, verdict}` there too (#2954, #3397); the history row reads `failed` and `errored` (#3458) and a `verdict` of `"failed"` (#3539). A load run's (`{rps, p95Ms, errorRate, verdict}` plus the stored `assertions` block and `assertionsPassed` / `assertionsFailed` over its two populations on a run that asserted or errored (#3458, #3537), and `capacity` `{stopReason, maxHealthyConcurrency, kneeConcurrency}` on a capacity run, #2130, #2820, #2930) comes from its stored summary rather than its results - those are unbounded, and the engine's design-result query cannot read them even if asked.

**Freshness is wiring, not polling.** `runs.recentDesign(requestId)` is its own key family (like `runs.lastDesign`, and for the same `InfiniteData` shape-clash reason), so nothing under `runs.lists()` refreshes it: the builder's send path, the run view's replay, the MCP `run` event and the delete/clear-history paths each invalidate it explicitly. A new invalidation point for runs needs to touch it too, or the section silently shows the sends from before.

#### Variables used (`variables`)

`VariablesSection.tsx` - the variables this request references, resolved or not, with the full in-scope set behind a disclosure and a quick editor over them (below).
The `id` stays `variables` - it keys the collapsed state.
Quiet (`{empty:"none"}`) only when the request references nothing *and* nothing else is in scope; a request that references none while the workspace defines some still gets the disclosure, so it stays `"content"`.

#### Auth (`auth`)

`AuthContextSection.tsx` - the effective auth mode and where it came from, via the shared `resolveAuthSource` walk, so it cannot disagree with what is sent.
A mode the engine does not execute reads "not sent by Vayu", and a bearer token or API key name that is empty once variables resolve (spaces and tabs trimmed, as the engine does) reads "empty, nothing sent (as configured)" / "no name, nothing sent (as configured)" instead of "Sending": the pre-send mirror of the engine's `authNotice` (#3203), judged on the effective (inherited) auth.
For OAuth 2.0 it embeds `TokenStatusRow` (the Auth tab's own control) for token state, fetch and clear - or, when a pre-request script may change a name the as-written config uses (`useOAuth2DeferredNames`, which asks `useDeferredVariables` only while the config holds a `{{token}}`; #2742), for a sentence saying the token is fetched at send instead of a state, with Get token and Clear still live.
Declares no `useRelevance`, always `"content"`.

#### Cookies for this host (`cookies`)

`CookiesSection.tsx` - the active environment's jar filtered to the request's host, with a per-scope clear.
Host filtering is an **approximation**, stated in the UI: libcurl applies the real domain/path/secure rules at transfer time.
Hidden before the URL resolves to a host; quiet (`{empty:"none"}`) for a host with an empty jar.

#### Code (`code`)

`CodeSection.tsx` - copy-as-curl / copy-as-fetch (below), composed from the editor's draft as Send composes it.
Declares no `useRelevance`: it is the one section whose answer costs a `POST /compose` round trip, so a hook that decided whether it had anything to say would have to compose to find out, on every request tab, for a section that is collapsed by default (see above).

#### GraphQL (`graphql`)

`GraphQLSection.tsx` - schema status, the age of the schema in hand, the endpoint, and an outline of the operations the stored document defines.
It carries **no Refresh**: the one it had stood beside the Query header's whenever the body panel was on screen with the bar open, and could never stand without it, since the button was gated on a schema-cache field only `GraphQLBody` set, and only for a non-empty URL (#1224).
Status belongs in the bar; *browsing* the schema does not - that is the explorer docked beside the query editor (below).
`appliesTo` sees only the tab, which carries no body mode, so it still applies to every request tab; `useGraphQLRelevance` narrows that afterward and hides the section outright off a non-GraphQL body, rather than rendering to say the request is not GraphQL.
Because that verdict answers from the same `useRequestQuery` data the section itself reads, a REST tab never requests the section's lazy ~320KB chunk (#1146) at all - it used to arrive the moment the expanded section mounted just to say so (#1310).
The outline reads the **stored** request, since the bar sits outside `RequestBuilderProvider` and cannot see the editor's live buffer; autosave keeps the two within a second or two.
Each outline row is a button that **scrolls the query editor to that operation** and focuses it, from a hidden Body tab too - the provider brings the tab forward first, because the editor is unmounted anywhere else and revealing into an editor nobody can see is the silent-failure alternative.
The row sends the operation's *name*, not the line it drew, and `findOperationLine` resolves it against the live buffer; an operation renamed since the outline was drawn reaches the polite live region instead of scrolling to whatever now sits on that line.
The channel is `lib/graphql/reveal-store.ts` (below).

#### Recent sends (`recent-sends`)

`RecentSendsSection.tsx` - the last five design runs of this request, newest first: status chip, latency and age, each row opening that run in a History tab.
One `GET /runs` call and no report fetch - status and latency ride on each row as `resultSummary` (see below).
A run with no stored result reads "Sending…" or "No result" rather than a status-0 chip, which the wire uses for "reached no server".
Quiet (`{empty:"not sent yet"}`) when nothing has been sent - the list query behind the verdict is the section's own, the one page of `GET /runs` it would make on expansion anyway, so a collapsed section costs one list call and an expanded one costs nothing extra.

#### Variables in this collection (`collection-variables`)

`CollectionVariablesSection.tsx` - the definitions this collection owns (not a resolved set), editable through the same commit path as the request tab's list.
A disabled definition is shown and marked `off` rather than hidden.
Rows are ordered oldest `createdAt` first through `lib/variable-order.ts`, the function `VariableTableEditor` orders and saves by, so the section and the Variables tab list a collection's variables identically (#3252).

#### Auth (`collection-auth`)

`CollectionAuthSection.tsx` - the mode this collection is set to, and what a descendant set to Inherit would pick up: the same `resolveAuthSource` walk, so a collection set to plain No Auth names the ancestor that answers instead.
A mode the engine does not execute (`isEngineExecutableAuthMode`), on this collection or on the ancestor it names, says Vayu does not send the type and requests go out without auth rather than "send this" (#3203).
While the Auth tab holds an unsaved pick, mounted or not, this reads it (`useCollectionAuthDraft`, #1483) rather than the last-saved mode, so the two panes agree, and its sentences end "(unsaved)" while that pick differs from the stored auth (a request below still sends the stored row until Save).

#### Last run (`collection-last-run`)

`CollectionLastRunSection.tsx` - how this collection's most recent run went: the outcome word in its status colour (a completed run with a failed or errored step, or a missed budget, reads in the error colour, from `rowOutcome` through `runStatusTone(run)`, as its History row does, #3496), the plan's size (`3 steps`, `× 2` only when more than one pass ran; a `TruncatedText`, so a clipped label shows in a tooltip), and the age, opening that run in a History tab.
The row's accessible name carries all of it ("Open collection run, completed, verdict failed, 11 steps, 5 minutes ago"); a `failed` run says "failed" once and adds no verdict word (`verdictBesideStatus`, #3643).
One `GET /runs?collectionId=&limit=1` call and no report fetch - the server's `start_time DESC` makes the single row the answer.
A run still going reads "Running" rather than an outcome, and a run stored before the engine sent the `scenario` descriptor shows no size rather than "0 steps".

#### Run config (`run-config`)

`RunConfigSection.tsx` - mode, duration, target RPS, virtual users, iterations, ramp and requested protocol, read from the run's stored `configSnapshot`.
Words come from `loadTestModeLabel` / `formatConcurrency` ("64 virtual users"; the one spelling of the unit is `constants/load-test-modes.ts`).
A design run has no `mode` key and reads as "Single send".
A **collection run** has none of those keys at all - it reads its `scenario` block instead (`run-scenario.ts`) and shows "Collection run", the plan's step count, iterations, whether sub-folders were included, and a **Data file** row naming the file the run's rows came from (issue #2051; the display name, never a path, read through `lib/run-data-file.ts`'s one reader of the name/hash pair).

#### Source (`run-source`)

`RunSourceSection.tsx` - the environment the run used (`Run.environmentId`, which nothing rendered before) and a link opening the request it ran from.
A deleted environment is named as deleted rather than folded into "No environment"; a deleted request (`isRequestNotFound`, never a transport failure) drops the link.
A **collection run** links no request - its source is the folder - so the row names the collection and opens *that* tab.

### Variables section

Leads with the variables **this request references** (#1308), not every name in scope: the section walks the stored request's templated fields (`lib/request-references.ts` `referencedVariableNames` - URL, params, headers, body and form parts including a file part's `src`/`fileName`/`contentType`, the auth it sends with `inherit` walked, and a script's `pm.*.get()` names) and splits the result into the references that resolve - each a row with the name (`TruncatedText`), its winning scope (`VariableScopeBadge`) and value (secrets masked) - and the references nothing defines, marked `not defined` in the editor's destructive tone with no input. Everything else in scope sits behind a collapsed `All in scope (N)` disclosure, so the quick-edit-anything path is not lost. A request that references none says `This request uses no variables` above that disclosure; only a request with nothing referenced and nothing in scope says `No variables in scope`. Value inputs are named `Value of <name>`. The reference set is read from the **stored** request via `useRequestQuery`, so it lags the live editor buffer by the autosave interval, the same lag the GraphQL outline documents - the bar sits outside `RequestBuilderProvider` by design.

**Editing:** a blur (or Enter) commits the value back to the definition the resolver picked - looked up by `ResolvedVariable.sourceId`, not re-derived (see [variable resolution](../variable-resolution.md#getvariableoriginsname)). The payload is read from the query cache at commit time and patched into it optimistically, so a second blur before the first mutation settles cannot re-send the first one's old value. Commits register with the save store, so a quit flush waits for one in flight.

The row and the commit are shared, not per section: `VariableRow.tsx` draws it (the remount key, the Escape restore, the uncontrolled input a rejected save depends on) and `variable-commit.ts`'s `useVariableCommit` writes it, so the collection tab's list gets the same fixes. Its rows are the collection's own definitions with that collection named as the source, which lands in the same place a collection-scope edit from the request tab does. A secret row draws the shared `SecretInput` primitive (#1308) - masked, read-only, with a keyboard-reachable eye that reveals the value in place rather than the old `••••••` that could never be looked at; reveal state is keyed by the definition's identity (name:scope:source), so an environment or tab switch re-masks. The collection tab reuses `VariableRow`, so it gets the reveal for free.

### Code section and `services/codegen/`

Snippets are generated from **`POST /compose`'s output** - the request with `{{variables}}` substituted and `inherit` auth walked by the engine that will send it - so what you paste is what Vayu would put on the wire, except for a name a pre-request script sets at send: that stays `{{name}}` in the resolved snippet, and Resolved mode says so in a note under it ("`{{token}}` is set by a pre-request script at send.", plural for several), read from the answer's `deferredVariables` (#2521). The query (`compositionOptions`) and the sentence (`deferredNote`) live in `code-composition.ts` because the Params panel's **Sends** line reads the same cache entry and says the same words (#2741). **What is composed is the editor's draft, not the saved row** (#2638): the bar sits outside `RequestBuilderProvider`, so the builder publishes its draft and collection chain through the `editorDraft` live surface (`EditorDraftSurface.tsx`, see [the command registry](command-registry.md#command-registry-libcommands) below), and `code-composition.ts` builds the inline body with `buildComposeBody` from the inputs Send gives it - the same request, unsaved edits included, and the `stream` flag and jar note read from the draft too. With no builder holding the request (one still mounting) it composes the stored row by id and says under the snippet that it is the saved request's, since that trails the editor. A **Templated** mode generates from the stored request instead, references intact, for pasting into a bug report; it stays on the stored row (there is no `RequestState` to `Request` mapping to feed it the draft without a second field list) and carries the same saved-request note. Composing happens on every expand (an editor-held snippet recomposes on mount, so a collapse, edit, re-expand is current), on an explicit recompose, when a builder takes the request on, and on a committed write's invalidation (the autosave PUT included, which re-reads the draft), never per keystroke (the section only mounts while expanded, and the query is `staleTime: Infinity`).

`services/codegen/` holds the generators, closing the symmetry with `services/curl/`, which parses curl *in* and generated nothing out. Each target is a pure function of a `SnippetRequest`; `CODE_TARGETS` is the registry, and adding a target is one entry plus one function. Auth is flattened into headers/query/`-u` in `prepare.ts` rather than per target, because the engine keeps `auth` beside the request and applies it at send time: a snippet built from the composed *headers* alone would authenticate in Vayu and 401 in a terminal. Modes no static command can reproduce produce a note instead of a silent drop: OAuth 2.0 (the engine fetches the token at send time) an `mcp` body (the engine derives its `Content-Type`, `Accept`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` and `Mcp-Param-*` headers and stamps `params._meta` into a bare call, none of which a snippet reproduces, so `prepare.ts` sends the content as stored, adds no header and says so in a note; #3762), and the modes Vayu does not send at all (digest, AWS, NTLM, Hawk, OAuth 1.0, EdgeGrid, JWT bearer), which the note names with their registry label and says Vayu does not send, so the snippet matches the request Vayu sends without auth (issue #2474). `prepare.ts` skips an auth header the request already carries (bearer or basic over a typed `Authorization`, an API-key header over a typed header of that name, matched case-insensitively and leaving `basicAuth` empty so `-u`, `-a`, `auth=` and `btoa` stay unused), as the engine's `apply_auth` does, so a snippet never sends two lines where Vayu sends one (issue #2475; pinned by `engine/tests/fixtures/auth-header-precedence.json`). A `user:pass@` in the URL is taken off the URL in every target and becomes the same structured Basic credentials (split at the authority's last `@` and its first `:`, percent-decoded as libcurl does with a malformed escape left literal, a `{{token}}` kept whole), so fetch never meets a URL with credentials and no target sends them twice; it is dropped with a note when a typed `Authorization`, bearer or basic auth, an API key written as `Authorization`, or OAuth 2.0 already authorizes the request, as libcurl lets a set `Authorization` header win, and its password is masked as a secret either way (issue #3197). The fetch and Python targets add a note when a header value (an auth-derived one included) holds a character above U+00FF, which those clients cannot send, or one in U+0080 to U+00FF, which they send as Latin-1 where Vayu sends UTF-8; the value is never transcoded, and curl carries no such note. `prepare.ts`'s implied Content-Type table mirrors the engine's exactly - `json`, GraphQL and JSON-RPC as `application/json`, XML as `application/xml` - so a snippet of a json-mode body carries the header the engine would add, and pasting it back through `parseCurl` reads it as json rather than text (issue #1445). The body is the engine's wire body for the two modes whose stored content is not what is sent (issue #3198): `wire-body.ts` restates `jsonrpc_wire_body` and `graphql_wire_body`, so a bare GraphQL document is wrapped as `{"query": ...}` (an object with a string `query` is left as typed, and so is unparseable text that opens as an object with a quoted key, a `{{variable}}` template) and a JSON-RPC call object without a string `jsonrpc` gets `"jsonrpc":"2.0"` and, with no `id` member, `"id":1` after the author's members (a batch, a finished frame and unparseable content are left as typed). It runs in `normalizeBody`, before masking, and the masker also matches a secret's JSON-escaped spelling since the wrapping can change it. A GraphQL GET has no body (issue #3211): the engine sends the document as query parameters, so `prepareRequest` appends them to the URL after auth has added its own and drops the body with its implied Content-Type. `graphqlGetQuery` restates `graphql_get_parameters`: a bare document is the `query` parameter, an envelope is one parameter per member in the author's order with `variables` and `extensions` as the engine's compact dump, all escaped as `curl_easy_escape` does (`curlEscape`, not `encodeURIComponent`, which leaves `!'()*` raw), and an envelope the URL cannot carry (an unsupported member, a mistyped `operationName`, `variables` that is not an object, unparseable text) keeps the JSON body. The masker matches a secret in that escaped spelling too. A completed JSON-RPC call is the engine's compact `dump ()`, so `compact-json.ts` is an order- and number-preserving reader rather than `JSON.parse` + `JSON.stringify`, which would hoist integer-like keys and rewrite numbers; for JSON-RPC it also reads an unquoted `{{token}}` in value position (`[{{a}},{{b}}]`) as an opaque value written as typed, because the snippet completes the call before variables resolve where the engine completes the resolved text (GraphQL's envelope probe does not, so `{"query": {{q}}}` stays an envelope); it differs from nlohmann where Grisu2's spelling is longer than the shortest round-trip one: floats of 16-17 digits in roughly 0.1% of cases, and integers at or above 2^64 with trailing zeros in roughly 10% (`10300000000000000000000` is `1.0300000000000001e+22` from the engine and `1.03e+22` here). Both spellings parse to the same double. `SnippetRequest.params` carries a request's path rows (issue #1764), and `prepare.ts` fills the URL's `:name` segments from them with `substitutePathVariables` - the engine's rule: the last enabled row with the key answers, and its value is percent-encoded with Postman's path encode set (`postman-url-encoder`'s `PATH_ENCODE_SET`: controls, non-ASCII, space, `"`, `<`, `>`, `` ` ``, `#`, `?`, `{`, `}`; a `/` makes more segments, `@ : % !'()*` and the rest go out as typed, and a `{{variable}}` token is kept verbatim); an empty value or no enabled row leaves `:name` literal, and a `.suffix` after the name stays. The templated view and the builder's Copy as cURL pass the rows; the resolved view's composed URL is already substituted. `prepare.ts` then runs `resolveUrlTemplate` over the substituted URL with the `{{token}}`s left in place (issue #2465), so the snippet carries the line Vayu sends - the literal text around a token encoded by its component's set, a head backslash a `/`, the host lowercased and punycoded - and under `disableUrlEncoding` the URL as typed. A request with `disableUrlEncoding` (issue #1765) passes the flag on `SnippetRequest`, and `prepare.ts` then substitutes each value as typed - no path encode set at all, as Postman's `toNodeUrl (url, disableEncoding)` skips `encodePath` - and appends a query-located API key raw, as the engine does (an API key's name and value are trimmed first, for the header and the query placement alike, as the engine's `apply_api_key` does); a bearer token is trimmed the same way and an empty one writes no `Authorization` header, as `apply_bearer` does (#3438), while the secret masker is handed the trimmed token; otherwise that key and value are written with Postman's query rule (`encodeQueryComponent`, issue #1771: `|`, `+` and `=` in a value go out raw), the engine's `append_query_param`; the Code section's jar note says the jar is off for a request with `disableCookies`, since the snippet is then the whole request. `followRedirects` is the same split curl's own default forces the other way from `verifySSL`: curl does not follow unless told to, so `-L` is emitted for the common (following) case rather than only the departure from it.

**Every target carries the request settings its client can spell, and says so where it cannot** (#3195). `prepare.ts` reads `followRedirects`, `maxRedirects`, `verifySSL`, `timeout` (milliseconds, `null` or absent when the request states none) and `httpVersion` once into `PreparedRequest`, and each target maps them. A cap is stated only for a request that follows, and a timeout only when the request names one: with none, the engine's `defaultTimeout` setting decides at send time and a snippet has nothing true to say, so nothing is emitted and no note is added. A client's own redirect default decides what is written: Vayu follows, so curl and HTTPie need a flag for the common case, while `fetch`, `requests` and `Invoke-RestMethod` follow unasked and are written only when the request does not. The protocol is curl's alone (`--http1.1` / `--http2`, nothing for `auto`); no other target mentions it. A hop cap for `requests` and `fetch` is a note rather than an argument, because neither has a per-request spelling. `parseCurl` reads back `-k`, `-L`, `--max-redirs` and `--max-time` (#3426); `--http1.1` / `--http2` are not read back, so a pasted curl snippet reports them as dropped.

| Target | Follow redirects | Max redirects | Verify TLS off | Timeout (seconds) | HTTP version |
| --- | --- | --- | --- | --- | --- |
| `curl` | `-L` when following | `--max-redirs N` beside `-L` | `-k` | `--max-time <s>` | `--http1.1`, `--http2`; `auto` writes nothing |
| `fetch` | `redirect: "manual"` when off | note (fetch follows up to 20) | note (dispatcher option or `NODE_TLS_REJECT_UNAUTHORIZED=0`) | note suggesting `AbortSignal.timeout(ms)` | not stated |
| `python` | `allow_redirects=False` when off | note (set `max_redirects` on a `Session`) | `verify=False` | `timeout=<s>` (connect and each read) | not stated |
| `httpie` | `--follow` when following | `--max-redirects=N` beside `--follow` | `--verify=no` | `--timeout=<s>` | not stated |
| `powershell` | `-MaximumRedirection 0` when off | `-MaximumRedirection N` when following | `-SkipCertificateCheck`, with a note that 5.1 lacks it | `-TimeoutSec <s>`, rounded up to whole seconds, at least 1 | not stated |

**Quoting is per target, never a flag on another one** - that is why PowerShell is its own generator rather than "curl with different quotes". Each language's escape rule and its form-body switch differ in ways that fail silently:

| Target | String rule | Multipart vs urlencoded |
|---|---|---|
| `curl` | POSIX single quotes, `'` → `'\''` | `--form-string` (or `-F` for a typed text part) vs `--data-urlencode` |
| `fetch` | `JSON.stringify` (it *is* the JS literal grammar) | `FormData` vs `URLSearchParams` |
| `python` | `JSON.stringify` - JSON's escapes are a strict subset of Python 3's | `files=` vs `data=` (a multipart body passed as `data=` is silently urlencoded) |
| `httpie` | POSIX, shared with curl | `--multipart` vs `--form` (`--form` alone is urlencoded) |
| `powershell` | Single quotes, `'` → `''`; a POSIX `'\''` would put a backslash in the data | `-Form` vs `-Body` |

A multipart body is written in the rows' order (#3198). `normalizeBody` keeps the enabled rows as one ordered `parts` list, text and file parts interleaved as the editor shows them, and every target emits that list as it stands: the engine adds parts to the libcurl multipart tree in row order (`attach_multipart`), so a snippet that wrote every text part before the files would send a different body. Python writes `files` as a list of `(key, part)` pairs rather than a dict, so it carries the order too and a key several parts share keeps every one of them (#3206); a urlencoded `data` is a list of pairs for the same reason.

A repeated header (issue #2466) stays one flag or word per line: curl writes `-H` once per line and HTTPie one `Name:value` word per line - except `Cookie`, which both fold into one `"; "`-joined line at the first row's position (`foldRepeatedCookies`, #3198), because that is the single line the engine sends (`typed_cookie_value`: a row that reaches no wire is skipped, each other row is trimmed of its edge space and tab, and no line is written when none is left - `typedCookieValue` restates it for every target), and with no note since the folded line is what Vayu sends. `fetch`, `requests` and `Invoke-RestMethod`, whose header map holds one value per name, get the lines joined into one entry (`foldRepeatedHeaders`: `", "`, `"; "` for `Cookie`) and a note that Vayu sends them as separate lines (`Cookie` rows go out as that same `"; "` join, issue #2788). HTTPie takes headers as bare `Name:value` words and a body as `--raw`, so the composed bytes go out unchanged rather than HTTPie building a new JSON object from `key=value`. PowerShell emits `Invoke-RestMethod`, not `curl` - on Windows PowerShell `curl` is an alias for that cmdlet, so a snippet saying `curl` runs something else than the reader expects, and a multipart snippet carries a `# requires PowerShell 6.1+ (-Form)` line because 5.1 has no `-Form` at all and builds its body as `[ordered]@{}`, because `-Form` sends the parts in the order the hashtable enumerates and a plain `@{}` promises none. A hashtable holds one entry per name, ignoring case, and a literal that repeats one does not parse, so a multipart body in which a name repeats is written as a `System.Net.Http.MultipartFormDataContent` passed as `-Body` instead (#3206): one `$body.Add(...)` per part in the rows' order, a note saying why, and a file part opened with `Get-Item -LiteralPath ... .OpenRead()` and named by its declared name or its path's basename. That form can carry a text part's Content-Type and has no extension guess for a file part's, which a note states. A urlencoded body is the same case (#3216): when a name repeats, ignoring case, `-Body` is one pre-encoded string in the rows' order (`'a=1&a=2'`, every name and value percent-encoded as the engine's `curl_easy_escape` writes it, so a space is `%20` and `!'()*` are escaped) with `-ContentType 'application/x-www-form-urlencoded'` on the call (left off when a Content-Type header is declared, which already carries it) and a note saying why; with distinct names it stays the `@{}` hashtable.

**Quoting is not the end of it: a client can read its own argument as a path.** The bytes survive the shell and the *client* then interprets them, so curl's `-F` uploads a local file for any value starting with `@` or `<`, and HTTPie's item grammar reads `=@` the same way (plus `==` as a query parameter, and a `:` or `@` in a key as a header or a file upload). curl form fields therefore use `--form-string`, which has no such grammar, and HTTPie items escape `:`, `=` and `@` with a backslash on the key and on a leading separator in the value. A backslash is not special to HTTPie, so one in a value is sent as written, never doubled (#3197); the one thing it cannot say is a backslash directly before `:`, `=` or `@`, which the snippet reports in its notes. `--data-urlencode` encodes only what follows the first `=`, so the field *name* is percent-encoded here and the value is left to curl.

**The form-data editor's `Content type` column** (#3022, `KeyValueEditor/ContentTypeCell.tsx`, mounted by `BodyPanel` as the table's `rowExtra`) sets any part's own Content-Type by hand, on a text part as well as a file part, and takes `{{variables}}`. Empty is the old behaviour and drops the member rather than storing `""`: a text part sends none and a file part's type is derived. A file part's pencil button beside its file chip sets the name the file is sent under (`fileName`, also `{{variables}}`); empty sends the file's own name. The case the column exists for is Salesforce's ContentVersion insert, whose `entity_content` part must be `application/json` beside the file part `VersionData`. **A text part that declares its own Content-Type** (a Postman import keeps one, #2539, or the column above) is sent with it, so the snippets carry it where the client can: curl needs `-F` for the `;type=` modifier, which `--form-string` cannot take, and writes the value double-quoted (`-F 'k="v";type=application/json'`) because curl reads a quoted value as text whatever it starts with, where a bare `@` or `<` would be a file; Python gives it requests' filename-less tuple `(None, value, type)`. HTTPie, `fetch` and PowerShell's `-Form` have no spelling for a text part's type (`FormData` would add a filename), so they send the part untyped and a note names it (`untypedTextPartNote` in `prepare.ts`); PowerShell's `MultipartFormDataContent` form, used when a part name repeats, does set it. `parseCurl` reads the same `;type=` back from a text `-F`, so the curl snippet round-trips.

**Secrets are masked by default in resolved output**, revealing is explicit, and masking happens *before* quoting - after it, a value containing a quote no longer matches itself. What is masked: every variable the resolver marks secret (and its URL-encoded forms - the query encoding the engine writes, the URL-text form a `{{token}}` takes substituted into the path, query or fragment, each by its own encode set (`&` and `=` left raw; in the host, the value as typed and as the composed URL writes it, lowercased and punycoded (`encodeHost`; a secret that is only part of a label is rewritten with the whole label by punycode and is not matched, #2591)), and `encodeURIComponent` - because a value substituted into a path or query reaches the payload encoded), the credential the auth mode carries, and the value of any header row whose *name* is sensitive, whether or not a secret variable holds it (`lib/sensitive-headers.ts`: `authorization`, `proxy-authorization`, `cookie`, `set-cookie`, `x-api-key`, `x-auth-token`, `x-csrf-token`, plus the header the request's API-key auth names; pinned to the engine's redaction list by the `sensitiveHeaderNames` key of `log-redaction-conformance.json`). One list builder, `collectSecrets`, and one masker, `createSecretMasker` (`prepare.ts`), so a second surface showing the resolved request hides exactly what the snippet does. Jar cookies are never in a snippet (libcurl attaches them at transfer time) and the section says so.

## `Dock` (`components/layout/Dock.tsx`)

Footer bar (`--dock-height`, shrink-0): status in the centre, controls on the right. #1615 moved its two switchers onto the rails above and left it status-only; #1711 amends that to admit a right-aligned cluster that acts on the *active tab's* view, rendered only while that tab is a request tab; #3635 adds the one control that is not per-tab, the bottom panel's button, which leads the cluster on every tab and with none. Every item here has a non-footer path (the response position has its chord, its palette row and its Settings row; the bottom panel its chord and its palette row), so the system Dock covering this strip on macOS costs a glance, never a click.

- **Engine connection status:** green dot + "Connected" once `engineStatus` is `connected` (a tooltip too: it names the engine's address, which is a fallback port when another program held 9876, issue #2118); a dim "Starting…" while it is `starting`, since the window paints before the engine answers and that is not yet a failure. Only `unreachable` turns the indicator into a focusable tooltip carrying `engineError` - the health poll's reason, which was previously recorded and rendered nowhere, so a refused connection, a timeout and a TLS failure all read as one word. When the main process reports a start failure (`engineStartFailure`, every engine port held) its sentence replaces `engineError` there and a Retry button appears beside the light, the same `EngineRestartButton` the pending-restart control uses. The version string is itself a focusable tooltip once the first health poll answers, carrying the `workers` count (issue #1508) - the `workers` setting's effective value, which `GET /health` had always reported and nothing in the app had ever read.
- **Running services:** a dot plus "2 services" whenever at least one local service (a running webhook inbox, an OAuth issuer) is up, and **nothing at all when none is** - the Dock's middle is ambient, and a standing "0 services" would spend a permanent line on the ordinary case. An engine that is not `connected` - starting or unreachable alike - **counts as none**, whatever the query cache still holds: services are engine-*process* state, so they died with it, and the gate lives in `useRunningServiceCount` rather than here so no later reader has to re-derive the caveat. Clicking it **reveals** the Services drawer (`revealDrawerView`, never `activateDrawerView`) - an ambient chip pointing at a surface must not be the thing that hides it, and on the toggling call it closed the drawer whenever it was already on Services. → `Dock.services.test.tsx` (mutation-checked: rendered unconditionally, the absent-case tests fail; on `activateDrawerView`, the reveal case fails).
- **Pending restart:** once a setting the engine marks `requiresRestart` has been saved, a "Restart pending" button appears beside the connection status and restarts the engine in place (`useEngineRestart`, shared with the Settings banner so the two cannot diverge). With a run live, every Restart asks first and Cancel changes nothing (issue #3604). It tracks saves made since this renderer connected - not a comparison against the engine's running values, which it does not report - so it says *saved*, not *in effect*, and does not survive a renderer reload. A failed restart leaves the signal standing and reports the reason as a toast.

## Right-click menu (`electron/context-menu.ts`, `lib/context-menu.ts`)

Electron draws no context menu of its own. `electron/context-menu.ts` composes one in the main process from Chromium's `context-menu` params (`isEditable`, `selectionText`, `linkURL`, `editFlags`) plus a target the renderer announces on the way past - a capture-phase `contextmenu` listener installed once by `useMenuActions` (mounted in `App`), through `installContextMenuBridge` in `lib/context-menu.ts` (issue #1359).

| Under the pointer | Menu items |
|---|---|
| An editable field | Cut / Copy / Paste (enabled per `editFlags`), a separator, Select All - all Electron roles, so the OS supplies the accelerator |
| The URL bar | The above, plus "Paste as curl" / "Paste as wget" when the clipboard holds one - imports through `UrlInput`'s existing paste import |
| A `{{token}}` | The above, plus "Edit variable" - clicks the token, the popover's own way in |
| A link (http/https only) | "Copy Link" and "Open in Browser" |
| Read-only text with a selection | Copy |
| A Monaco editor | Nothing - it draws its own menu |
| A row or a tab | Nothing - the row or tab draws its own |
| Anything else | No menu |

The renderer marks what a surface means with `data-context` ("url-bar" | "monaco" | "own-menu", spread from `contextProps`) and `data-context-variable` (spread from `variableProps` on the token in `EditableVariable`); the main process reads only those markers plus what Chromium's params already say, since it has no way to read the DOM itself. `own-menu` is answered exactly as `monaco` is, with an empty template, and it is the only refusal that reaches the main process for a different reason than Monaco's: Chromium raises `context-menu` on the web contents whatever the page's own listener does with the DOM event, so a row's `preventDefault` never gets there, and the marker is what stands in for it (issue #1360).

## Row and tab actions menu (`components/shared/RowContextMenu.tsx`, `row-actions.ts`)

A row's actions are one list, drawn by two menus: `RowActionsMenu` (the `⋯` trigger, a `DropdownMenu`) and `RowContextMenu` (right-click, a Radix `ContextMenu` - a second family rather than the dropdown positioned at the pointer, since a context menu anchors to the click point and answers Shift+F10 on its own). Both render the same `RowAction[]`; `row-actions.ts` holds the one rule about the list (the first destructive action gets a separator above it) and `RowActionBody.tsx` holds what one item draws (icon then label, plus the `disabledReason` a gated item carries at its trailing edge - issue #1690, where a tooltip would fight the menu for the keyboard), so neither menu can drift from the other. Environment rows and history rows (`RunItem`) take `RowContextMenu`; the collection tree opens one menu for all its rows instead (`CollectionTreeContextMenu`, below), drawing it with the same `RowContextMenuContent`; history rows had no menu at all before it, since pin and delete were hover-revealed buttons only, and the handlers those buttons call now take an optional event for the same reason a menu selection is not a click on the card. **Every row that names an entity also carries "Copy for agent"** (#2047): the item's `hint` is the reference line from `lib/agent-reference.ts` and `onSelect` copies it through `useCopy()` as "Reference", placed before the destructive item. Duplicate uses the `CopyPlus` glyph so the two copy items differ at a glance.

`RowContextMenu` wraps rather than replaces the row (`asChild`), marks it `own-menu` so the main-process menu above stands down, and focuses the row on the way past so Escape returns focus there instead of `<body>`. It does not select the row - selecting would mean opening a tab, which no file manager does on right-click - each row's actions already close over that row's own entity. While a row is renaming or deleting, both the menu and the marker stand down together, so a right-click inside the open rename field gets the platform's own Cut/Copy/Paste rather than neither.

`TabStrip` uses the same `RowContextMenu` for its own right-click menu; see its entry below. The collection tree is the one surface that does not wrap each row (#2543): a thousand rows were a thousand Radix roots, so `CollectionTreeContextMenu` makes the `role="tree"` element the single trigger and keeps every behaviour above row for row - the row is resolved from the click, the row (not the menu) carries the `own-menu` marker so it still comes off with a rename, and a right-click with no row of ours under it is stopped before the trigger, so the platform keeps its default there.
