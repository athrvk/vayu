# Load Test Dashboard (`modules/dashboard/`)

Live load-test metrics. Entry: `modules/dashboard/index.tsx`.

Connects to the engine SSE metrics stream (`/runs/:runId/live`, via the load-test service / dashboard store), shows live metrics while running, and converges on the final report on completion. Stop action supported. A run that finishes any way at all - `completed`, `failed` and `stopped` alike (issues #1932, #2136) - renders History's own [`LoadTestDetail`](history.md#history-moduleshistory) over its report once the report has arrived (issue #2220), so the same run shows the same numbers, labels and verdict here as when it is reopened from History. Above it the dashboard keeps only an identity row (Back and the status pill with the run's outcome); the crumb, the request line, the configuration and the "Not judged - Stopped before it finished" verdict are the report's own. Until the report arrives (a stopped run's, which the Stop click precedes, or one whose fetch failed) the live layout stays, with the "Couldn't load the run report" Retry. The live view has no tab bar.

The header's pill and Stop button read the store's `phase` through two derivations (#3351, see `docs/app/state-management/run-live-state.md`): **Running, with Stop, while `isDashboardRunLive`** - streaming, a lost stream, or awaiting the report of a run the user did not stop - and otherwise the run's ending from `dashboardRunEnding` (Completed, Stopped or Failed), or no pill before anyone knows it. A lost stream is live because the engine keeps executing the run, so the pill says Running beside the "Lost the live metrics stream" callout and its Reconnect. A report that still says running after every fetch attempt ends on that callout too, not on the report Retry, since the engine is still generating load. Reconnect, and the re-attach the dashboard makes on mount, ask `canReattachLoadRun` first: while a collection run streams, attaching would take its stream, so Reconnect opens that run's tab with the "A collection run is already running." toast and the mount re-attach does nothing. The header takes both answers as primitives (`live`, `endedAs`), since it is memo'd on `Object.is` (#1714).

The dashboard is **mode-adaptive**: a `useMode()` discriminator maps the run config to one of `constant_rps` / `constant_concurrency` / `iterations` / `ramp_up`, and the hero row + stat row + charts render the surfaces appropriate to that mode. `MetricsView` is a thin orchestrator over a modular tree:

While a run streams the app can hold a system wake lock, so the OS does not
suspend the machine under a test the user walked away from (issue #1357). It is
off by default and turned on either standing (Settings > Load testing) or per
run: a load run of ten minutes or more asks once as it starts, through
`components/shared/KeepAwakePrompt.tsx`, which is mounted at the app root
because the question is about whichever run is streaming rather than about the
surface that started it. The
lock is a request, not a guarantee - a closed lid overrides it - so a suspend
that happens anyway is marked on the time-series charts at the point the run
reached, labelled with how long the machine was gone. The record is the app's
own (`stores/host-sleep-store.ts`, keyed by run id): the engine was suspended
too and its report has no field for it.

A run reaching its end also posts a system notification when the user has
opted in and Vayu is not the window in front (issue #1358). A load test's body
leads with the banner's verdict (`reportOutcome`), then the numbers: "Failed. 1
of 3 budgets missed: p99. 12,400 requests, p95 210ms, 0.3% errors". The kind
follows the verdict, so a run that completed but missed a budget posts as
"Load test failed" (and marks the Dock or taskbar failed); a pass, or a run not
judged, posts as finished with the reason in the body (issue #3546). A stopped
run posts "Load test stopped" with its numbers alone, whoever stopped it and
however this window learns of it (a frame, the stored report, the settle wait);
a collection run posts "Collection run stopped" with its step counts (issue
#3606). The end-of-run cue (the taskbar flash) follows who stopped the run:
a load test's own Stop from this window is silent, a stop from MCP, History or
another client raises it, and every collection-run stop raises it (that service
has no `stopMonitoring`, so its Stop arrives as a stream frame).

The run's progress is also mirrored onto the OS chrome: the Windows taskbar
button and the macOS Dock icon fill as it advances and clear when it ends, and
a failed run flashes the taskbar's error state on Windows, which macOS has no
equivalent of (issue #1362). Linux paints nothing - Electron 44 dropped Unity
launcher support. A collection run now fills too, from the size the engine
publishes on its stream as the run opens (issue #1398), and stays indeterminate
only where that frame never reaches the client - an older engine, or an attach
after the frame left the run's retained ring.

both fields are optional props, absent on a run stored by an older engine), `AchievedThroughputCard`, `ThroughputCard` (the `iterations` hero's second card: throughput and a "mean iteration" sub-line that reads `DashboardDerived.meanIterationTime`, the pass wall clock on a collection run and one request's latency on a single-request run, `-` where a sequence has no pass time yet; `ModeStatCards`' Mean iteration time stat reads the same field, #3570), `ThroughputTwinCard` (draws the verdict `utils/dispatchLag.ts` hands it: live, its printed rates are cumulative and the verdict is on the windowed pair, #2802; a finished run prints `sendRate` beside `receivedRate`, the completions counted when sending ended over the sending window, captioned "received while sending", and falls back to the whole-run `throughput` as "received, whole run" for a report that lacks the count, #2882), `CurrentConcurrencyCard`, `ConcurrencyUtilCard`, `CapacitySearchCard`, `SaturationCard`, `ProgressCard`, `ErrorRateCard`, and `LatencyPercentilesCard` (p95 and p99 with mean/median beneath, all over the run so far while it is live - the tick's `cumulative_p*_ms`, the span the mean covers, where the tick's own `latency_p*_ms` are only its last ~100 ms window - and the report's once it ends; each figure and its unit from `formatLatencyParts` so 1234 ms reads `1.23 s`; added by `HeroRow` for the throughput-led modes - `constant_rps`, `constant_concurrency`, `iterations` - which therefore carry no p99 stat; `ramp_up` and `capacity` keep theirs as p99 at peak in the stats row; for a scenario load run the figures pool every step, so the card takes `DashboardDerived.pooledLatency` (`utils/pooledLatency.ts`, set by `reportToDerived` from `report.scenario.steps`) and adds the caption "All steps pooled - slowest step: <name>, p99 <ms>" under the mean line and the `latencyPercentilesPooled` tooltip in place of `latencyPercentiles`; a single-request run passes none and draws neither, #2823). Throughput on these cards prints through `formatRate`, so 3940 reads `3,940`; virtual-user counts go through `formatNumber` (10000 reads `10,000`), percentages through `formatPercent` (one decimal: `94.0%`), a mean count through `formatOneDecimal` (`4.2`) and seconds (the ETA, the ramp span) through `formatSeconds`, which carries its unit, so no card writes an `s` beside the number. `SaturationCard` prints the breakpoint p99 with `formatLatency`, the same figure the chart breakpoint line's hover shows, and words the line it was judged against by `Breakpoint.sloSource`: "the 200ms SLO" for the run's own, "the 200ms threshold in Settings" for the Settings threshold (#2939; the breakpoint marker and the Breakpoint stat's sub-line follow the same rule). It is `ramp_up`'s card ("healthy" / "degrading" off the ticks); `capacity` mounts `CapacitySaturationCard` from the same file, which never says "healthy" and reads the search's stop reason instead (#2816): **searching** while live, then from `DashboardDerived.capacity` (set by `reportToDerived`; the stop reason exists only in the report) **degrading** for `slo_exceeded` / `errors_exceeded`, **saturated** for `plateau`, **no limit found** in a neutral colour for `cap_reached` / `deadline` / `stopped`, and **no result** for a report without the section or an unknown reason. Errors that were not the stop reason are counted on a line of their own and never colour the card. The reasons come from the `STOP_REASONS` table in `components/shared/capacityStop.ts`, which the [Capacity Summary](shared-run-results.md#capacity-summary-componentssharedcapacitysummarytsx) words its badge from too. The closed-loop count reads "virtual users" on every card ("Active virtual users", "Virtual user utilisation", "Throughput per virtual user", "Peak virtual users"); under `constant_rps` the same series counts requests, so that mode's stat says "Peak in-flight requests". `isClosedLoopMode` and `concurrencyMeasureLabel` in `constants/load-test-modes.ts` make that call, and the card components and their props keep the `Concurrency` identifiers. `ConcurrencyUtilCard` paints neither its number nor its bar with a tier: idle virtual users describe the run's shape, not a failure, so healthy 40% utilisation is not red (#2245). Under `constant_concurrency` the card reads the **mean** requests on the wire, not the instant: `DashboardDerived.avgInFlight` is the live tick's `window_avg_in_flight` (the trailing window, `MetricsView`) or the report's `summary.avgInFlight` (the whole run, `reportToDerived`), drawn as "4.2 of 10 on the wire" with one decimal (`formatOneDecimal`) and "42.0% utilisation", because the instant `current_concurrency` is 0 or N for virtual users that wait in step (`timer.think`, `timer.pacing`) and `peakConcurrency` made History read 100% by construction (#2821). A tick or report stored before the mean existed carries no such key, and the card then draws the instant (live) or the peak (finished) as "N of M active" as before; `capacity` mounts `CapacitySearchCard` instead (#2929): live, the level being measured, the time into it and the levels judged from the frame's `capacity` block (`DashboardDerived.liveCapacity`); finished, "41 virtual users held" and "gave out at 51 of up to 100" from `DashboardDerived.capacity`, with the ceiling stated only as a bound, and the dashboard header says "up to 100 virtual users" for a capacity run. `concurrencyUtilInstant` remains the tooltip for a stored run that lacks the mean. `ramp_up`'s `CurrentConcurrencyCard` stays instantaneous live ("Active virtual users") and reads the peak once finished, titled "Peak virtual users" with no "active" unit ("-" when the run recorded no peak, #2963); its "lag" clause on a finished run comes from the stored series (`LoadTestDetail` runs `buildRampOverlay` over it) and is left out when the run stored none (#2870). The "Peak virtual users" stat keeps the peak.

`ErrorRateCard` shows the engine's one error definition (issue #2124): a response outside 2xx/3xx, or no response at all; a 3xx is a success and is drawn in the green `2xx/3xx` segment. Its percentage is `failedRequests / totalRequests`, and the card is told the split rather than recounting it: the legend's **HTTP errors** and **No response** come from `DashboardDerived.httpErrors` / `noResponse`, read off the live tick (`http_errors`, `no_response`) or the report's `summary` by `utils/errorBreakdown.ts`. Its status bar buckets `DashboardDerived.statusCodes`, which `MetricsView` takes from the latest tick's `status_codes`, so the bar fills during the run instead of staying empty until the report loads; a finished run's card reads the report's distribution through `reportToDerived`. The report (`history/main/components/OverviewTab.tsx`) prints the same two words beside "Total errors" in the shared [`ErrorSummary`](shared-run-status.md#error-summary-componentssharederrorsummarytsx), fed `httpErrors` / `noResponse` from the same split. The card's colour follows the digits it prints: red for any rate above zero, success for a printed zero. A rate under 0.1% takes a second decimal (`0.01`), and one that rounds to nothing even then reads `<0.01`, through `formatErrorPercent` in `utils/format.ts`, so a nonzero rate is never `0.0` in red. A request cancelled by a user Stop (issue #2136) is not an error and is in neither the rate nor the bar: the engine keeps it outside `totalRequests` and the status-code distribution, and reports it as `summary.cancelledRequests`. The report says so in one muted line, "N requests cancelled by Stop", from `components/shared/CancelledRequestsNote.tsx` (silent for zero and for an engine that predates the count), placed outside the error card so a stopped run with no errors still shows it. An `mcp` run's failed replies by class (`summary.errorClasses`, #3828: `transport`, `protocol`, `tool`, and the JSON-RPC `protocolCodes` behind `protocol`) are the History Overview's **Error classes** card (`history/main/components/ErrorClassesCard.tsx`), drawn after the status-code distribution only when a class was counted: the key absent is a run stored before the engine counted them and `{}` one that saw no failed reply, and both draw nothing, never a card of zeros. Its labels are `error-classes.ts`, not `httpStatusClass`, since a class is not a status. The live dashboard draws none: the engine's tick does not carry the classes, only the report does.

It is one plugin because the vertical labels of both lists share one layout (`labelLayout.ts`, #2696): each takes the first of two lanes under the plot's top edge where it clears the labels already there (markers first), and a label that fits neither is not drawn - its rule or band still is, and an annotation's full text stays in the hover tooltip. The breakpoint's vertical line is labelled `p99 > SLO <n>` for the run's own line and `p99 > <n> threshold in Settings` for a Settings-judged one (the threshold, never the observed p99) and carries the observed p99 and the load at the crossing as its `hover`. The primitive's y scales start at zero (`yMin`, default 0; `yRange.ts`), so a series wobbling around 500 does not fill the plot and read as a collapse, and data below the base moves the floor down rather than being clipped; `ServerVitalsChart` and `CustomMetricsChart` pass `yMin={null}` to keep uPlot's auto-range, because their values are in the target's or the script's own units and may be negative. The secondary axis is labelled through `y2Label`: `RequestRateChart` names the ramp overlay's axis with `concurrencyMeasureLabel(mode)` ("Virtual users"), so it takes the run's `mode`. The x axis ticks where uPlot spaces them unless a chart passes `xSplits`, an explicit list of tick positions each labelled by `xFormat`: `HdrPercentileChart` passes the six percentile marks (0, 50, 90, 95, 99, 99.9%) so each prints once at its own place on the log-scaled axis, not once per tick a nearest-mark lookup would have relabelled (#2859). A horizontal marker whose value is outside the visible y range (an SLO the run never approached) is drawn pinned to the plot's top or bottom edge with " (above range)" / " (below range)" appended to its label, shortened to fit the plot; a vertical marker off the plot is still skipped, since that is the user zooming past it. Hovering a shaded `Annotation` adds its label to the tooltip (an instant is reachable within a few pixels; an annotation with an empty label is not listed). A vertical `Marker` with `hover` text is listed the same way within a few pixels of its line; one without is not hoverable. Outside `uplot/`, `TimingWaterfall.tsx` draws the five phase rows. The live `MetricsView` draws it, `PhasePercentiles` and `HdrPercentileChart` in Row 3 (`LiveDistributionRow.tsx`) from the latest gate frame's `cumulative_latency` / `cumulative_phases` (#2782); all three take `Pick<RunReport, ...>`, which `utils/liveDistributions.ts` builds from the frame (the phases in the report's `timingBreakdown` shape, `maxMs` becoming `max`), so the live view and History's Performance tab share the components. A card holds one line ("Waiting for the first response", or "Phase timing is off for this run" for a run with phase histograms off) until its data arrives. Two plain-DOM readouts render in History's Performance tab: `PhasePercentiles.tsx` (per-phase percentiles over every completion; the live view's timing card draws it too) and `StreamMetrics.tsx` (issue #576 - what a streaming run's transfers delivered: events/sec, the per-completion event distribution, the time to each stream's first event - its own row from `report.stream.timeToFirstEvent`, not the First byte phase, which ends at the response headers, and absent when no stream delivered a timed event, #3234; an API that opens with a preamble event reads near zero on it, so a request's first content marker gets a **first match** row beside it from `report.stream.timeToFirstMatch`, drawn only when present, #3774, and left off the live panel, whose frame carries no match - then two rows of how each stream paced itself, drawn only when the report carries them and each independently of the others and of the first-event and first-match rows: **max gap**, from `report.stream.maxEventGap` (the largest pause between two consecutive events in one stream, as a distribution over the streams, in the same duration cells), and **events/s**, from `report.stream.eventRate` (each stream's own rate, unlike the whole-run events/sec above it, through `formatRate` in `utils/format.ts`: the engine's `format_run_figure` rule of 2 decimals below 10 and none above, a positive rate below 0.01 reading `<0.01` rather than a zero), both absent when no stream had two timed events to measure between and report-only, since a live gate frame carries neither, #3776 - and how many streams a cap ended rather than the server). **`stats/`** - `ModeStatsRow.tsx` routes to the per-mode Row 4 stat set (three cards for the throughput-led modes, four for `ramp_up` / `capacity`); `ModeStatCards.tsx` (its latency stats pass the `unit` of `formatLatencyParts` to the card, so the unit follows the value into seconds), `StatCard.tsx`, `LatencyStat.tsx` (one figure of the HDR plot's footer, shared by `MetricsView` and the History Performance tab; value and unit from `formatLatencyParts`, so a tail past a second reads `1.23s`), and the seconds-valued stats (Duration, Elapsed, Remaining) go through `formatSeconds`, which carries its unit, so those cards pass no `unit`. Latencies, rates and percentages in the run cards, the History header tiles, `LatencyMetric`, the step table, the baseline comparison and the chart value formatters in `charts/uplot/formatters.ts` (ticks included, through `formatFixed` / `formatTrimmed`, so the decimal mark follows the locale) go through `formatMs` (or `formatLatency`, which adds the unit), `formatSeconds` (a span in seconds), `formatRate` and `formatPercent` in `lib/format-number.ts`, beside `formatNumber`, so one value prints one way (issue #2217). The live status card's receive rate goes through `formatByteRateParts` there (a size is `formatBytes`, 1024-based; a rate is decimal): KB/s below 0.1 MB/s and MB/s from there, in decimal units, so a rate of a few KB/s keeps its digits (#2860). The axis tick formatters stay compact, but `axisMs`, `axisRate` (`/s`) and `axisVitals` (`k` / `M` / `G`) label each tick with its unit and pick their decimals from the whole tick array (`UPlotChart` passes `yFormat` the splits), so a 0 to 3 ms axis reads `0ms 0.5ms 1ms 1.5ms` and a rate axis over 1200 to 1220 reads `1.2k/s 1.21k/s 1.22k/s` rather than a run of repeated numbers.

**`hooks/`** - `useMode.ts` (run-config → mode discriminator).

**`utils/`** - `metricsTransforms.ts` (SSE history → chart series, including `buildCustomMetricsOverTime` for a run's declared custom metrics), `reportToDerived.ts` (stored `RunReport` → the same `DashboardDerived` shape, so history reuses the live components), `computeBreakpoint.ts` (also `sloSourceOf`, which marks a breakpoint's line `"run"` or `"settings"`, #2939), `p99AtPeak.ts` (the worst whole-second p99 among the ticks at the run's peak load, the "p99 at peak" stat for `ramp_up` and `capacity`: latched in `dashboard-store` as `p99AtPeakMs` live, derived over the stored series in History, falling back to the cumulative p99 until a tick at the peak has a reading, #2802), `dispatchLag.ts` (the Send / Throughput chip's verdict from two rates, a tolerance and held / settled gating: the live windowed pair with the streak `dispatchLagSinceSeconds` that `dashboard-store` folds per tick, the finished run's sending-window pair in History, #2802, #2882), `tickPercentiles.ts` (the one reading of a tick's percentiles: `secondPercentiles` per second, `cumulativePercentiles` for the run so far, #2385), `liveDistributions.ts` (the latest gate frame from the live buffer and its adapters to the HDR chart's, the waterfall's and the percentile table's report shapes, #2782), `detectAnomalies.ts`, `computeEta.ts`, `chartGeometry.ts`. `types.ts` holds the shared dashboard types (`DashboardDerived`, etc.).

`detectAnomalies.ts` names the run's degradation windows. It is derived once per view - `MetricsView` for the live buffer, `LoadTestDetail` for a stored run - and passed down, so no card or chart re-derives it. The rules, the two entry points (a pure one-shot for a series that arrives whole, an incremental detector for a buffer handed over on a timer) and the invariant that keeps them in agreement are in `app/src/modules/dashboard/README.md`.

## `DashboardHeader.tsx`

Run status, method and URL, stop button, and the config summary line (virtual users, mode, a data-driven run's row count and the file it came from, elapsed over the configured duration as `00:18 / 00:15` while the run is live, or elapsed alone for a run with none or one that is no longer live).
While the engine reports the run `draining` (#3568: the primitives `draining` and `waitingOn`, set only then) the pill reads **Finishing**, the line adds "waiting on N requests" and Stop reads **Stop waiting**.
A collection load run has no URL, so the collection's name and its step count ("Checkout · 12 steps") take that place (#2270); they arrive as the primitive props `collectionName` / `stepCount` from `hooks/useCollectionRunTarget.ts`, which reads the run's row (its snapshot's scenario manifest) and resolves the name through `useCollectionName`, falling back to the id once the collection is deleted.
The run's comment is the `comment` prop, drawn under that line by the shared `RunComment` ("Comment" label, one truncated line with the full text in its `title`): from the launch config while live, from the report's `configuration` once the run has finished - the report body no longer draws it, so this header is where a finished dashboard run shows it.
Once that report is on screen the dashboard also hands the header `exportRunId`, with the report's `requestUrl` / `requestMethod` as `exportRequestUrl` / `exportRequestMethod` (primitives, for the memo), and the header draws the run's **Export** menu ([`RunExportMenu`](history.md#history-moduleshistory), #2139) where the live header has Stop; a streaming run never mounts it

Orchestrator - composes the hero row, stat row, and charts per mode; hands `LiveStreamPanel` the newest frame, the history buffer and the latest first-event block when the frame carries `stream_events`

## `LiveDistributionRow.tsx`

Row 3 of the live view: the latency distribution (HDR plot, its min / mean / p50 / p95 / p99 / max footer and an "N completions so far" caption) and the request timing card (the average waterfall with History's per-phase percentile table under it), from the latest gate frame; a scenario load run's distribution card is titled "Latency distribution (all steps)" (#2823)

## `LiveSequencePanel.tsx`

Row 1.5 of the live view, between the hero row and the charts, for a **scenario load run** only (#2823): the shared `SequenceBadge`, "N steps per iteration", the iterations started / completed / abandoned (`ScenarioFacts`; abandoned only while non-zero) and a Step / Executed / Errors table drawn from the same cells as History's Steps tab (`StepLabelCell`, `ExecutedCell`, `ErrorsCell`).
Its data is the gate frame's `scenario` block (`LoadTestMetrics.scenario`; its one timing is `meanIterationMs`, the mean completed pass, which the iterations hero and the Mean iteration time stat read through `DashboardDerived.meanIterationTime` rather than the pooled request latency, #3570), read from the latest frame that carries it (`utils/liveScenario.ts`) and passed down as the block itself so this memo'd panel re-renders when a gate lands and not at the tick rate; a run whose frames carry none draws nothing, and the hero latency card, the Response-time percentile card and the distribution card read "pooled" / "(all steps)" for the same run.
A live row has no "(n short)" marker (a step in flight is always behind the one before it) and no method badge (a frame names the step, not its request), but an mcp step's row carries the frame's `label` beside its name (#3987)

## `LiveStreamPanel.tsx`

Row 1.6 of the live view, after the sequence panel and before the charts, for a **run whose frames carry `stream_events`** only (#3236): a single-request load run with `stream`, or a collection load run with a streaming step (#3304), whose "streams open" counts its streaming steps' transfers alone.
A "Stream events" `Card` of `StreamStat` tiles - events so far, events/sec now, streams open and the time to first event as "p50 / p95" - over a `StreamRateChart` of events/sec on the run's timeline (`pickEventsPerSecond`, `CHART_SYNC.live`).
The gate is the frame carrying `stream_events` (`utils/liveStream.ts`), not a run-config field and not the store's `streaming` phase, which only says the SSE connection is attached.
A figure the frame lacks gets no tile and no point, never a `0`; a measured `0` is drawn.
The cumulative figures come from the newest frame, the time to first event from the latest gate frame that carries `stream_time_to_first_event` (it rides gate frames alone), and it counts finished streams only, so the tile appears after the first one ends.
Its wording is not the First byte phase (`TOOLTIPS.liveStreamFirstEvent`).
`StreamStat` (`charts/StreamStat.tsx`) is the tile the finished report's `StreamMetrics` draws too
