# Variables and Settings

## Variables (`modules/variables/`)

- **Sidebar (`sidebar/VariablesCategoryTree.tsx`)** - tree of variable scopes (globals, environments, collections); fetches both lists itself, like the drawer's other views. A WAI-ARIA tree on `useRovingTreeFocus`, so the tree is one tab stop and an environment row answers F2, Delete/Backspace and Shift+F10 / Menu / Shift+Enter - Rename, Duplicate, Copy for agent (`environmentReference`, #2047) and Export as Postman environment live only in that row's ⋯ menu and had no keyboard path before #1217. Export as Postman environment (#2253) calls `POST /export/postman-environment` with the id alone, so secret values are written blank, saves the file the engine names and, once it is written (#3246), toasts what was left out (secret values blanked, `json` variables written as `default`); a second pick is ignored until the first settles. Right-click opens that same menu through `RowContextMenu` (issue #1360), the pointer route beside the keyboard one. A sub-collection in the Collections group shows its ancestor path as a muted, truncating prefix before its name, and its accessible name is the whole path (#3495), so two same-named folders are told apart. The section headers are the level-1 rows; "Add environment" stays a tab stop of its own, since the tree has no "create" key. See [Tree Navigation](../../design-system.md#tree-navigation-roving-tabindex). Delete - from the row or the editor header's button - moves the environment to the Trash (#2970): the confirm dialog says it can be restored, and a delete that lands raises the same `Moved "<name>" to the Trash` toast with Undo the collection tree raises (`hooks/useTrashUndo.ts`, shared by both modules). The Undo restores it inactive and selects nothing.
- **Main (`main/`)** - `VariablesMain.tsx` (screen `"variables"`) hosts `VariableTableEditor.tsx`, the table editor for the selected scope, including the active-environment selector.

**`VariableTableEditor` does not mount the [shared key/value table](shared-key-value-editor.md#shared-keyvalue-editor-componentssharedkeyvalueeditor), and that exclusion is permanent** (decided in #564, re-examined and confirmed in #587). It is not a copy of that table - it is a different one: a per-row type select and secret toggle, a masked value cell, text committed on blur while toggles save immediately, and rows ordered by a `createdAt` stamp (`sortVariableEntriesByCreatedAt` in `lib/variable-order.ts`, which the collection tab's context-bar section shares) rather than by a trailing-blank rule. Mounting the primitive here would mean giving it a dynamic column model, a commit model, and variables-domain fields on `KeyValueItem`, redesigning a primitive for one consumer at the expense of its three others. What the "a hand-rolled copy of a primitive does not receive the primitive's fixes" rule *does* bind is the reveal control: `ui/secret-input` was extracted from this cell and then received fixes (the `tabIndex={-1}` removal, `aria-pressed`) the leftover copy never got, so the value cell mounts `SecretInput`. `main/key-value-parity.test.tsx` pins what the two tables must keep in common - control height, checkbox clearance and sizing, the shared `rowActionDestructive` variant, and that reveal control - each read off the primitive rather than off copied literals, so a fix to either side that skips the other fails.

**Rows carry an editor-local id, and it is what React keys them by.** Reveal state lives inside `SecretInput`, so reconciliation decides which row owns it - and while rows were keyed by array index, deleting a revealed secret handed its mounted field to the row that shifted up, which then rendered unmasked (#621). A variable has no identity of its own to key by (`key` is editable, `createdAt` may be absent), so each row is stamped with a session-monotonic id at load and at insertion. The id is UI state and is never persisted: `performSave` builds each entry field by field. A reseed of the **same** scope carries the ids over, matched by variable name - a reseed is usually the cache echo of a save this editor just made, and fresh ids there would remount every row, re-masking a revealed secret and pulling focus out of the field being typed in. A **different** scope mints fresh ids, since those are different rows that merely share names. `main/secret-reveal-identity.test.tsx` pins both halves.

**A save merges the user's edited rows onto the freshest map rather than replacing it with the editor's own copy** (#1439), through the same `lib/variable-merge.ts` primitive the context bar's `useVariableCommit` uses - see [state-management/module-local-stores.md](../state-management/module-local-stores.md#a-variable-map-write-merges-onto-the-freshest-map-never-onto-its-own-copy). An MCP agent's `update_environment` landing on a key the table has not touched survives the next save regardless of how stale the table's own copy of that key is; a key both the user and an agent touched shows a `Callout` naming it, with a "Take theirs" action, rather than resolving silently either way.

**`main/VariableRow.tsx` is `memo`-wrapped, keyed by `variable.id`, for the same reason `KeyValueRow` is** (issue #1716). Rendering every row inline in a `.map`, with no row component of its own, would have `updateVariable` rebuilding the whole `variables` array on every keystroke re-render every row's `Input`, `Select` and `SecretInput` regardless of which row was typed in. `updateVariable`, `removeVariable` and the `commitNow` wrapper around the ref-held `performSave` are all in `VariableTableEditor.tsx` id-based and ref-backed (`variablesRef`), so their identities survive a keystroke; `handleBlur` reads `hasPendingChangesRef` for the same reason, since a dependency on the `hasPendingChanges` *state* would change its identity on every dirty/clean flip and defeat every row's memo on that flip alone. Only the row whose own `variable` object actually changed re-renders - `main/variable-row-render-count.test.tsx` pins it. The row's "Copy for agent" button (`variableReference`, #2047) reads its scope from a `scope` prop that `VariableTableEditor` memoises on the owner's id and name, so it is one reference across a keystroke and does not defeat `memo`.

**The variables table never writes a name the engine would refuse or a map would fold** (#3251). The payload is keyed by name, so `main/variableRowNames.ts` judges every row on its *trimmed* name (the engine's `trim_variable_name` set: space, tab, CR, LF) before a save is built. A row with no name is `unnamed` ("Needs a name") and a row spelling a name another row already holds is a `duplicate` ("Name already used"); of two rows sharing a name, the one the server already stores under it keeps it, so renaming `token` to an existing `host` marks the renamed row and leaves `host` untouched. `VariableRow` shows the verdict as a `FieldError` under the name field (`aria-invalid`, `aria-describedby`, `border-destructive`), passed as a `nameError` string so it never defeats `memo`. A marked row is left out of the payload but stays on screen with its value, the variable it stood for is *not* reported deleted (`VariableRowData.baseKey` records the stored name; `computeUserChanges` counts an invalid row's `baseKey` as present, unless that stored name is itself one the engine refuses - a legacy blank or padded key is dropped from the blob, because sending it back is a `400` on every save, while its row stays on screen to be named), and the editor stays dirty after the save (`finishSave`'s `heldBack`) so the reseed cannot drop the row and the Dock reads "Unsaved changes". Only the row's Delete button removes a stored variable. Names are trimmed when a save runs (blur, a toggle, Cmd+S), never per keystroke, so a space typed mid-name survives; a whitespace-only name does not promote the trailing blank row. `VariableTableEditor.duplicate-name.test.tsx` pins it.

## Settings (`modules/settings/`)

Same nav/content split as Variables: the category tree renders in the **Drawer** (`settings` view), not inside the settings tab. Selecting a category sets `useSettingsStore.selectedCategory` **and** opens the settings tab, so `SettingsMain` shows that panel. There is no `SettingsLayout` two-pane wrapper anymore - the Drawer is the left pane.

- **Sidebar (`sidebar/SettingsCategoryTree.tsx`)** - settings category navigation and the search over every setting; rendered by the Drawer.
- **Main (`main/`)** - `SettingsMain.tsx` (screen `"settings"`) hosts the app-settings category panels under `main/panels/`: `AppearancePanel.tsx`, `DashboardPanel.tsx`, `LoadTestingPanel.tsx`, `GeneralPanel.tsx`, `McpSettingsPanel.tsx` (its Port field and restart notice are `McpPortSection.tsx`, whose copies of the main process's port limits, default and engine ports live in `mcp-port-copies.ts`, held to them by `electron/mcp/port-copies.conformance.test.ts`), `NotificationsPanel.tsx`, `EditorPanel.tsx`, `KeyboardShortcutsPanel.tsx` and `FilesPanel.tsx` (Settings > Files: the engine's allowed folders for request-body files, added only through the system folder picker - `electronAPI.allowFolder` through `hooks/useAllowFolder.ts`, which main allows with the grant secret (#2356), so there is no typed-path field, and the picker's title and starting folder are main's (#2378) - and removed), plus the shared `ClientSettingsPanel.tsx` wrapper, `FontPicker.tsx`, and `SettingControls.tsx` primitives. The pick-one tile grids (`OptionButtons`, and the font tiles including "Custom…") are one radio group built on the Radix `ToggleGroup` primitive directly (`TileGroup` / `TileItem` in `SettingControls.tsx`, not the segmented `ui/toggle-group`): each tile is a `role="radio"` with `aria-checked`, arrow keys move the selection with the focus (the WAI-ARIA radio pattern; Radix roves focus only, so `TileGroup` adds the pick for focus that follows a key press and leaves a pointer press to Radix's click), and pressing the chosen tile again does not clear it (issue #1865). The group is named by its setting: `label` is a required prop on `OptionButtons`, `FontPicker` and `TileGroup` (the `aria-label` on the `radiogroup`), and each call site passes the same constant its visible heading renders (`THEME_MODE.label`), so a screen reader hears "Theme, radio group" rather than an anonymous run of radios (issue #1997). `NotificationsPanel.tsx` now carries two cards: the opt-in for OS notifications while Vayu is in the background, and the four toast preferences (issue #1358). Each card carries exactly one **Preview**, and they are deliberately the same control - same word, same icon, same row under the settings it demonstrates, and the same shape of hint when it cannot fire (a severity floor on one, a build that cannot post on the other). Only the accessible name separates them, since a screen reader hearing "Preview" twice on one screen learns nothing. The system one is disabled while its toggle is off, the same as the toast one is while its severity floor hides everything: trying it means turning the setting on, pressing Preview, and turning it off again if it does not fit, rather than a button that contradicts the switch beside it. `GeneralPanel` composes three cards of its own: `UpdatesCard.tsx` (the version line, **Check for updates**, and a **Third-party notices** button beside it that opens the installer's `THIRD_PARTY_NOTICES.txt` through `electronAPI.openThirdPartyNotices` (#2693); a failure becomes a toast, and outside Electron the button is absent), `StartAtLoginCard.tsx` and `CookiesCard.tsx` (the engine's cookie jar - what it holds per environment, and the button that empties it). `StartAtLoginCard` is the switch for opening Vayu at login (issue #2098): the value lives in the OS and is read through `electronAPI.getLoginItem` on mount and after every `setLoginItem`, never held in a store. The card always renders, with its search anchor; where the main process says the switch cannot work (an unpackaged build) it prints the reason, and outside Electron it prints a one-line fallback, each with no switch. A login item macOS holds for approval adds a hint pointing at System Settings > General > Login Items. Its Data management card's **Clear run history** is one `DELETE /runs` (`apiService.clearRuns`, #2429): the engine keeps a pinned baseline and a run still in flight, so `planClear` reads the same split from the cached list ahead of the call. The confirm dialog counts only the runs that will go and names what is kept ("One pinned baseline is kept.", "One run still in progress is kept."), the button is disabled with a reason when nothing but those is stored, and the tabs that close are the `deletedIds` the engine answers with. Its Storage paths card's Logs row carries an Open button (`electronAPI.openLogsFolder`, issue #1558) beside the path text - `<data-dir>/logs/` holds `engine_*.log`, `cli_*.log` and the app's own `app_*.log` side by side, and a failure to open it (no file manager configured) becomes a toast rather than a silent no-op; absent, not disabled, outside Electron. `app-panels.ts` is the panel registry/metadata and `main/app-panel-components.ts` the map from a category to its component - two files rather than one because the registry is read by the Drawer's category tree and the command registry, both mounted on every tab, so a component named there loads at startup rather than with the settings surface (#1146). `app-settings.ts` is the catalogue of the settings inside those panels and of the engine categories' `Cards` (see Search), and `engine-categories.ts` the engine-side registry. An engine category may also declare `Cards` - components rendered above its `/config` entries, in order, for engine surfaces the generic entry renderer cannot draw because `GET /config` does not describe them; Network & connectivity declares `ClientCertificatesCard.tsx`, the host-to-certificate registry for mTLS endpoints (issue #707; a row the list reports `usable: false` - its file moved, its format edited around the routes - wears a **Not presented** chip and prints the engine's `problem`, since the engine drops such a row from every send without a word, #3260), and `ConnectionTestCard.tsx`, which sends one request under the settings on that screen and reports which hop answered - proxy, TLS or the endpoint (issue #708) - and which proxy carried it, the environment's included when libcurl chose it (`proxy.source`, #3258; the engine strips credentials from the URL). Both read their anchor and heading from the `app-settings.ts` catalogue (`panel: "network_performance"`), which is what makes them searchable: no `/config` entry describes them (issue #1869). The test card also holds this screen's half of system-proxy resolution (`useSystemProxyRefresh`), so the resolved `proxySystemUrl` row above it is true for whoever is reading it. (The former monolithic `UISettingsPanel.tsx` was split into these panels in PR #55.)

**`AppearancePanel`'s Interface card carries a Density toggle** (issue #1670): `Default` and `Comfortable`, from `UI_DENSITIES` (`constants/appearance.ts`) and rendered through the same `OptionButtons` primitive as Roundedness. `useAppearance`'s `density`/`setDensity` persist the choice under `STORAGE_KEYS.UI_DENSITY` and call `applyDensity` (`stores/appearance-store.ts`), which sets `data-density` on `documentElement` before first paint - the pattern `setTheme` and `applyRadius` already use for the other appearance stores. `index.css`'s `[data-density="comfortable"]` rule is what actually moves the layout: it restores the `--spacing` value Tailwind defaulted to before this setting existed, so Comfortable reproduces 0.30.0's spacing and row heights exactly, while Default is the denser value every other Tailwind spacing utility in the app now computes against.

**Density scales rhythm, not chrome, interactive targets or icons** (issue #1679, superseding #1676's "the shrink applies to icons too" decision). A chrome band (the tab strip, drawer header, notification banners), an interactive target (a button, a checkbox, a toggle) and an icon each carry their own floor - ten named steps outside the `--spacing` multiplier, `--spacing-band`/`-band-md`/`-band-lg`/`-banner`/`-control`/`-control-sm`/`-control-xs`/`-target`/`-icon`/`-icon-sm` in a plain `@theme` block in `index.css` (not `@theme inline`, which bakes a literal into each generated utility rather than a `var()` reference and would silently disable the Comfortable override) - so Comfortable no longer means "the tab strip and the toggle switches get taller too" the way #1670's single unit implied. See [Chrome, Target and Icon Floors](../../design-system.md#chrome-target-and-icon-floors) for the values and which components read which step, and [Spacing Scale Conventions](../../design-system.md#spacing-scale-conventions) for the rhythm unit itself.

The engine categories render from `GET /config` metadata alone - no per-key branching in the component. Two flags on each entry shape the screen: `requiresRestart` draws the "Restart Required" chip (and, once saved, the "Pending" chip plus the banner and the Dock's signal), and `advanced` moves the entry into a collapsed **Advanced** section at the bottom of its category. Both are read as fields; the `"(Requires Restart)"` label substring they replaced is gone, and `config_route_test.cpp` guards it from coming back. The collapsed state is deliberately not persisted, and resets when the category changes.

**Units come from the entry, not from the key.** `ConfigEntry.unit` (`ms`, `sec`, `days`, `bytes`; absent for a count) is passed straight to `NumberSettingRow`'s `unit` prop, which renders it inside the input - the one place a unit is stated, so no label appends `(ms)` and no description spells it out. `bytes` also selects `formatBytes` (`lib/format-number.ts`, the app's one byte-size formatter: 1024-based `B` / `KB` / `MB` / `GB`) and `formatSizeRange` (`utils/format-size.ts`) for the value, the range hint and the default line, so `104857600` reads as `100.0 MB`; anything else is shown verbatim, and a unit this app has not heard of still reaches the screen. That last branch reads the engine's declaration (`isByteUnit(entry.unit)`) rather than a hardcoded list of keys: a list would re-derive what the engine owns, and a byte-valued entry seeded engine-side would render a bare number until someone edited the array. Entries sort **by label**, not by key: the key is an internal name, and seed order is not a stable alternative because the engine rewrites a changed setting with `INSERT OR REPLACE`, which reassigns its rowid.

**A `dependsOn` entry nests under the entry it names, out of the label sort** (issue #1610). `correlationIdHeader` carries `dependsOn: "correlationIdEnabled"` because the header means nothing until the id is switched on, and the label sort above once put every entry from D through R between the two. `SettingsMain`'s `nestDependents` sorts everything with no `dependsOn` by label as before, then splices each dependent immediately after the parent it names, indented (`ml-6`) and rendered with its control disabled and a "Turn on \<parent label\> to use this" hint while the parent reads `"false"` - read live off the parent's own (possibly unsaved) value, so toggling the switch enables the dependent before the page is saved. A dependent whose named parent is missing from the payload renders standalone at its own alphabetical place rather than vanishing.

**`KeyboardShortcutsPanel` is the registry, drawn** (#951). Every row comes from `SHORTCUT_GROUPS` in `constants/shortcuts.ts`, its name from that chord's own `label` field, and its key-caps from `chordKeys` - the same function `ActivityRail`'s tooltips render through, so the screen cannot advertise a chord the handler does not listen for or spell a modifier the platform module would spell differently. A second table of names and keys here is the exact defect #938 removed from the Shell. It is read-only: rebinding needs a store, a persistence format, a conflict check against the native menu and a matcher that reads user data, and #951 scoped this to the list. Adding a chord means adding it to a group in that file; `shortcuts.listed.test.ts` walks the registry's exports and fails when a declared chord reaches no group or carries no label, and `KeyboardShortcutsPanel.test.tsx` compares the rendered row count to the registry's own. Two groups are not window handlers: "Window" (zoom in and out, reset zoom, full screen, close window, quit) is the native menu's and "Collection tree and tabs" the focused tree row's and tab's, so the screen lists every chord the app answers to, not only the ones `Shell` hears (#3325). The menu half is one definition rather than two: `createMenu` takes every accelerator string from `menuAccelerators` in `electron/menu-accelerators.ts` (the main process cannot import `constants/shortcuts.ts`, so the keys are plain shapes there), and `electron/menu-accelerators.test.ts` requires each to equal `chordAccelerator` of the chord the panel prints, on all three platforms, and scans `createMenu` for a literal. Full screen is the `togglefullscreen` role's own default (F11, ⌃⌘F on macOS, the one chord that uses `Chord.ctrl`) and so has no accelerator of its own; Quit's accelerator is set explicitly so Windows has one too. The Settings item on Windows and Linux carries no accelerator: the renderer's `SETTINGS_CHORD` handler answers ⌘, and a menu accelerator on the same key printed "Ctrl+Comma" beside it. Settings search finds the panel by any chord's label ("zoom", "rename", "full screen"), because `app-settings.ts` derives the panel's keywords from `SHORTCUT_GROUPS`. The palette reaches the screen through the section command the registry already generates from `APP_SETTINGS_PANELS` - no palette entry of its own, so there is one place a shortcuts row is defined.

Adding an app panel is four edits and no branching: a member on `ClientSettingsCategory` (`types/domain.ts`), one entry in `APP_SETTINGS_PANELS`, the panel file, and its line in `main/app-panel-components.ts` - which the compiler demands, since that map is keyed by `ClientSettingsCategory`. The sidebar tree and `SettingsMain` both read the registry. The engine half works the same way: `ENGINE_SETTINGS_CATEGORIES` (`modules/settings/engine-categories.ts`) carries each category's label, description, icon and sidebar order, and both the tree and the settings header render from it - so neither holds a hand-maintained map of the same five names.

**The six engine categories** (#586), in sidebar order, which is by likelihood of visit rather than by seed order: **Core** (base capacity, threading, storage internals), **Network & connectivity**, **Services** (streaming requests, webhook inboxes, mock servers, OAuth issuers - the Dock's word for that group, and its `Radio` icon), **Observability** (server monitoring and live metrics), **Data & retention** (capture and truncation budgets, run retention: `maxRunsRetained` for load and collection runs, `maxDesignRunsRetained` for design Sends, `runRetentionDays` for every kind), **Scripting environment**. Labels are sentence case, matching the app panels they sit under in the same sidebar. The set is closed on the engine side too - a seeded entry in a category this registry does not declare is dropped from the index and rendered nowhere, which `config_route_test.cpp` pins against the seed. "Observability & Data" held 24 of 48 entries before the split; "Database Performance" was a sidebar row for three, and folded into Core. App-side, the MCP panel reads **AI agents (MCP)** - the sidebar's only unexpanded acronym, kept in the parenthetical so it stays findable by eye.

**One knob, one editor.** A `/config` entry whose editor is an app panel row is listed in `ENGINE_SETTINGS_EDITED_IN_APP` (`modules/settings/engine-settings-edited-in-app.ts`) and drops out of the engine list: `liveReplayWindowMs` rendered both as "Live chart window" here (staged edit, Save bar) and as "Chart window" in Dashboard (autosave option buttons), so one value carried two labels, two save models and two search results, and staging one while flipping the other left this row showing a value nobody saved. The entry stays seeded, on `GET /config` and writable through `POST /config` and MCP; only the second editor is gone. Search folds the engine key into the owning row's keywords rather than indexing it separately, so `liveReplayWindowMs` - the name the docs, the logs and `update_config` use - still finds the setting, lands on the row that edits it, and returns one result. Related: General › Data management links to Data & retention, because that card shows and clears stored runs while the knobs bounding them live in the other section.

### Search

`lib/settings-index.ts` is a **pure** module: `buildSettingsIndex` flattens three catalogues into one list - the app panels (`app-panels.ts`), the settings inside them and inside the engine categories' `Cards` (`app-settings.ts`, whose `panel` may be an engine category) and the engine entries from `GET /config` - and `searchSettings` filters and ranks it (label, then id, then keywords, then description, then category label; an empty query means "not searching" and returns everything). It is deliberately free of React and stores.

`modules/settings/useSettingsIndex.ts` is the half that names the catalogues and reads the `/config` query. Both consumers call it - the sidebar's search box and the palette's `useSettingsItems` source - rather than each assembling the four inputs inline, which is the "one branch defines it, the other re-derives it" wiring defect this repo keeps finding. One index, one ranking, two UIs. The sidebar's query text lives in `settings-store` (`searchQuery`) for the same reason the index is shared: the palette's escape row hands its query over, so the drawer opens already filtered.

**Index the settings, not the screens.** The first version held panel titles and engine entries only, and a user searching "theme", "color" or "font" got nothing - the panel that holds all three is called "Appearance" and describes itself as "the look and feel of the application". `app-settings.ts` is the app-side catalogue that fixes it: one `AppSettingDescriptor` per setting (`anchor`, `panel`, `label`, `searchText`, optional `keywords` for the words a user types that the copy never uses - "dark mode", "accent", "zoom"). A new app setting needs an entry here, or it is unfindable - and so does a new `Card` on an engine category, whose descriptor names the engine category as its `panel` because no `/config` entry will ever index it.

**Both halves carry keywords, and neither renders them.** The engine sends its own on each `/config` entry (`ConfigEntry.keywords`, always an array, empty for the entries that declare none) - "ram" for `dbCacheSize`, "deadline" for `defaultTimeout` - so an engine setting is findable by a word that is in neither its label nor its description, which it was not while the index passed `[]` for that half. The field is a match term and has no reader in any component: it is the one deliberate exception to "grep for a reader before adding a field", and both type declarations say so. Adding a keyword that repeats a word the entry already carries is a defect, not a freebie - label, id and description all rank above keywords, so the duplicate only lifts the entry over better matches; the engine guards its seeds with a test.

**The catalogue owns the name; the panel owns the prose.** `label` is not a description of the heading, it *is* the heading - every panel renders `appSetting("<anchor>").label` rather than typing the string a second time, so a rename happens once and reaches both the screen and the search result. That is why the labels read as they do ("Font", not "Interface font"): the result row already prints the owning panel underneath, so qualifying the name here would only offer a title the panel never shows, and the qualifier a user might still type goes in `keywords` instead. `searchText` is the one field that stays hand-written, and it is **match text, not display text** - nothing renders it. A panel's own copy is markup (`<Kbd>` chips, live counts, conditional notices), so there is no string to lend; the catalogue writes a one-sentence summary of the block instead.

Both halves are checked rather than trusted, by `app-settings.drift.test.tsx`, which renders every panel and every engine category's `Cards`: a declared `anchor` has to be on screen (it is the `data-setting-anchor` the panel puts on the block), and the block's heading has to equal the declared `label` **exactly** - "Theme Modes" contains "Theme Mode", and a guard that accepts that is not a guard. A heading is one of four shapes and the block cannot say which, so the test resolves them in reading order: a row that names itself (`data-setting-row`, which `NumberSettingRow` and `ToggleRow` write from the same prop they print), then a `CardTitle`, then an `Eyebrow`, then a row nested inside. Rendered, not source-scanned - both the anchor and the label arrive through props, which no scan of a panel file would see.

Revealing a result is one mechanism for both halves: the sidebar passes the result's `anchor` as `useSettingsStore.highlightedKey`, and `useRevealedSetting` (mounted by `SettingsMain` and by `ClientSettingsPanel`) finds `[data-setting-anchor="<key>"]`, outlines it for `HIGHLIGHT_MS` and clears the key. It waits for the block through a `MutationObserver`, because the panel usually mounts after the key arrives. The one thing the attribute cannot do stays in `SettingsMain`: an entry inside the collapsed **Advanced** group is uncollapsed first, or there would be nothing to reveal.

**It scrolls the pane's own scroller, never `scrollIntoView` on the anchor** (#1612). Both panels wrap their cards in a `[data-setting-scroller]` div nested inside `overflow-hidden` columns (the pane itself and the shell around it); `Element.scrollIntoView` walks *every* scrollable ancestor until the target is satisfied, and Chromium counts `overflow: hidden` as scrollable for that purpose even though no user gesture can move it back - so a call that needed more travel than the inner scroller had left pushed the category header (with Reset to Defaults / Save Changes) out of the pane for good. `scrollWithin` (`@/lib/scroll-within`) instead finds the nearest `[data-setting-scroller]` ancestor and scrolls only that container, computed from `getBoundingClientRect`. An anchor with no such ancestor is not scrolled at all, rather than falling back to a guess. `SchemaExplorer`'s own reveal-on-search uses the same helper against its own list container, for the identical reason.

### Row primitives and save models

`SettingControls.tsx` holds the shapes every panel shares, and panels use them rather than re-rolling one - a hand-rolled copy never receives the primitive's fixes. Their reach is not the settings screen: the request builder's [Settings tab](request-builder.md#request-builder-modulesrequest-builder) renders three of them (issue #702), which is why a change here is checked against that tab too.

- `OptionButtons` - the pick-one tile grid. `preview: (isSelected) => ReactNode` per option draws the theme badge, the accent swatch or the roundedness shape, so Appearance no longer re-implements the selected-card style three times.
- `ToggleRow` - label (a node, for the MCP tool rows' `<code>` and counts), description, `disabled`, `title`. Takes an `anchor` like `NumberSettingRow` does, for the switches search reveals individually (Word wrap, Line numbers, Minimap), and names its box with `data-setting-row` from the same string that names the switch. A string label is wired to the switch with `htmlFor`/`id` as well as naming it through `aria-label`, so the words are part of the hit area - a Radix switch is a `<button>`, which is labelable; a node label has no text to associate, which is what `ariaLabel` is for.
- `NumberSettingRow` - input, unit suffix, range hint, `aria-invalid` + message, and the Default line. Its `commit` prop is the one thing the four old copies really disagreed about: `"change"` for settings that apply live, `"blur"` for owners that do real work per write (the MCP caps cross IPC). An unparseable draft is never committed - it stays in the field until it is a number again, unless the owner treats empty as a state of its own and commits it from `onDraftChange` (the request timeout, whose optional `placeholder` says what empty means: "Use default (30,000 ms)"). The description is pointed at with `aria-describedby` rather than only rendered (both ids, in reading order, when there is an error too), because a description like "Only applies while Follow redirects is on" is the reason the field is disabled. `data-setting-row` names the row's box. `compact` is the opt-in denser variant the element card's schema-generated form uses (`text-xs` label, `size="sm"` input, no width cap, so the field fills a half-width grid column) - opt-in because the settings panels are read one row at a time and keep the roomier default.
- `SelectSettingRow` - the pick-one row as a dropdown, for a set that reads as a list rather than a tile grid: `OptionButtons` stays the default where a user browses three or four choices, and this is for a value they already know the name of (the request tab's **Protocol**). `useId` pairs the visible label with the trigger and names it, because the trigger's text is the *chosen option*, not the setting. `onChange` hands back a `string` - a `Select` cannot promise the owner's union, so the owner narrows it (`isHttpVersion`) and decides what an unknown value means. Its second consumer is the engine view's `enum` card (`defaultHttpVersion`, `dbSynchronous`, `proxyMode`), which wrote the same row out by hand until issue #747: there the `CardTitle` is the setting's name, so it passes `labelHidden` and the label goes `sr-only` rather than away - it is what names the trigger, exactly as on `NumberSettingRow`. The trigger's width belongs to the row rather than to either caller (`w-48`, where `NumberSettingRow`'s input already stops), so the two control types end at the same place down a card; the engine's longest option label, "From environment", fits it. The card keeps its own guard for an entry whose `options` the engine omitted - rendering nothing is deliberate, and the primitive does not learn about it. It takes `compact` too, alongside `NumberSettingRow`, which drops `w-48` for the same reason that row drops its input cap. It takes an `error` as well, as `NumberSettingRow` does (#3048): `aria-invalid`, a destructive trigger border and a `FieldError` the trigger's `aria-describedby` names.
- `TextSettingRow` - the free-text row: label, field, an optional `children` slot under the field (the request Settings tab's presets for the stream text path, issue #3773) and the description, wired by `aria-describedby`. The sibling of `NumberSettingRow` for a value with no parse step, so every keystroke is the value and there is no draft. `monospace` for a value that is code, such as a path
- `DefaultValueLine` - "Default: x" plus the reset that goes there. Used by `NumberSettingRow` and by the boolean/enum/string engine cards, so every entry type has one.
- `CollapsibleText` - a description that reads as one or two lines with a "Show more"/"Show less" toggle, for the engine's per-setting `CardDescription` (every `/config` entry across all six categories) and the MCP panel's card and per-tool descriptions, both of which run to full paragraphs. Character-counted against a clamp rather than a CSS `line-clamp` plus a measured overflow, since jsdom lays out nothing for a test to measure. Callers pass the plain-string description as `text`; a description built from JSX (the Allowlist card's inline `<code>` spans) is left outside this primitive rather than forced through it.

Three save models coexist and each says which it is: app panels state `AppSettingsPanel.saveNote` (defaulting to `DEFAULT_SAVE_NOTE`, "Changes are saved automatically.") in the `ClientSettingsPanel` header, MCP overrides it, and the engine view states its staged-then-saved model beside the Save bar. Leaving an engine category still flushes its staged edits, and now **says** when one was dropped for being invalid instead of discarding it silently. A card's Revert discards a staged edit; Reset goes to the shipped default - one name each, for the two different things.

`LoadTestingPanel.tsx` is the ceilings the load-test dialog offers - the app's own policy, clamped to the engine's crash guards on the way into `client-settings-store`. The engine's bounds themselves are deliberately **not** settings; see `docs/app/api-integration.md` (Dialog ceilings are a user setting).
