# Request Builder (`modules/request-builder/`)

The request editor. Entry: `modules/request-builder/index.tsx`.

**Container (`index.tsx`)** - fetches the selected request (`useRequestQuery(selectedRequestId)`), maps the stored `Request` (discriminated-union `body`/`auth`) into flat UI state, and provides callbacks through `RequestBuilderProvider` to `RequestBuilderLayout`. Responsibilities:

- **Execute:** resolves `{{variables}}` in URL/headers/body, resolves auth, composes scripts, and calls the engine via `useEngine()`. It adds **no** headers of its own: since issue #1229 the engine adds `User-Agent`, a negotiated `Accept-Encoding` and an opt-in correlation id on every send path, and derives the `Content-Type` a body mode implies when none is declared (`text/plain` for `text`, none for a bodyless POST, issue #2464); the builder only passes on the names a send refuses (`disabledDefaultHeaders`, ticked in the Headers tab and never persisted).
- **Auth inheritance:** for `auth.mode === "inherit"` it walks the collection ancestor chain **leaf-first** (`useCollectionAncestors`) via the shared `resolveAuthSource`, taking the first collection that defines auth and stopping at one explicitly set to `noauth` (see [variable resolution → auth inheritance](../variable-resolution.md#auth-inheritance)).
- **Script composition:** scripts are not concatenated. Each level's `script.pre` / `script.post` is its own element, ordered root→leaf with the request's own last and stamped with the `origin.scope` (`collection`, `folder` or `request`) it came from (`elementsParts`, issue #1514; Send and code generation take it through `sendElementsParts`, which leaves out the request's own disabled and incomplete draft elements, #3066). The engine runs one script per level, and a test result or console line reports the level that produced it (issue #2522).
- **Load test:** opens `LoadTestConfigDialog`, then starts the run (`apiService.startLoadTest` + `loadTestService.startMonitoring`) and navigates to the dashboard.
- **Save:** `buildUpdatePayload` rebuilds the `RequestBody`/`RequestAuth` unions from flat UI state via `useUpdateRequestMutation`, and includes only the fields `RequestBuilderProvider` says the user touched (issue #1436) - an untouched field is omitted, which the engine's partial update reads as "leave it alone", rather than being resent unchanged. `name` keeps its own rule inside that: sent trimmed, and omitted even when touched if it is blank, so a partial update leaves the stored name alone rather than clobbering it - see [the draft adopts an external write per field](../state-management/draft-hooks.md#the-request-builders-draft-adopts-an-external-write-per-field) for why sending it at all took a fix in the provider first.
- **A request deleted while its tab is open** (issue #1436) does not unmount the builder: `index.tsx` keeps `RequestBuilderProvider` mounted and swaps `RequestBuilderLayout` for `DeletedRequestBanner`, so the draft the user had is still reachable through context. The banner offers **Copy as curl** (built locally, from the draft alone - `inherit` auth resolves against no ancestors, since the collection may be gone too) and **Close tab**, and its detail points at the Trash: the delete is soft, and a restore invalidates `requests.all`, which holds the tab's detail query, so the tab loads again with the draft (#3449). A request that 404s on its *first* load, with no draft ever seeded, still gets the plain "no longer exists" pane - there is nothing to preserve - and the same pointer to the Trash.

> **cURL / wget import:** pasting a `curl` or `wget` command into the URL field auto-populates the whole request (method, URL, params, headers, body, auth). Auth maps `-u`/`--user` (and wget `--http-user`/`--http-password`) to Basic, curl `--oauth2-bearer` to Bearer, and `--digest`/`--ntlm` beside `-u` to those stored-but-unresolved modes rather than silently relabelling the credentials as Basic (issue #1445; `--negotiate` has no matching mode here and is disclosed instead of guessed at); an `Authorization` header is left as a raw header (to preserve `{{variables}}`). A shell variable the command wrote, unquoted or in double quotes (`$API_KEY`, `${API_KEY}`), becomes the `{{API_KEY}}` Vayu resolves, and the paste's own toast (`pasteNotices`, beside the dropped-flags one, each a single sentence, #3777) names each that reached the request so the user knows what to define (a variable read by a dropped flag, `-o $OUT`, is not named, and `-X "$VERB"` is dropped and disclosed rather than uppercased into a method): a single-quoted `$X`, `$(cmd)`, `$1`, `${X:-y}`, `\$X` and the `$` of an existing `{{$guid}}` stay literal, and Chrome's cmd copy, where `$` is ordinary, is not read for variables. Form-shaped `-d`/`--data` without an explicit `Content-Type` maps to `x-www-form-urlencoded` rows (curl's on-the-wire default, decoded once so a `%`-escaped value is not re-encoded on the next generated snippet), while a raw JSON/text blob stays a text body; `--data-urlencode` is one field per occurrence, its value kept exactly as typed. `-L`/`--location` and `--max-redirs` map to the request's redirect settings - curl's own default is *not* to follow, unlike Vayu's, so a plain command with no `-L` genuinely means "do not follow" rather than "unspecified". curl `-m`/`--max-time` and wget `-T`/`--timeout` map to the request's `timeout` (#3426): seconds with decimals allowed, stored as milliseconds and clamped to the engine's range; `0` (curl's "no limit", which the engine refuses) or a non-number states no timeout and is disclosed, and a command with no such flag leaves the request's own timeout alone. `--connect-timeout` has no field here and is disclosed. Detection + parsing live in `services/curl/` (`tokenize.ts` shell tokenizer, which rewrites those variables and also unescapes Chrome's "Copy as cURL (cmd)" carets and decodes the numeric `$'...'` escapes `\xHH`, octal, `\u` and `\U`, + `parseCurl.ts`), kept separate from the collection `importers/` pipeline since this targets the active request. The paste is a request-shape replacement - identity (`id`, `name`, `collectionId`) and scripts are preserved; a file the command reads keeps only its path, marked unresolved so the engine sends it only once it is picked again in the editor or lives under a folder allowed in Settings > Files: `-F field=@file` becomes a form-data file row (`-F 'field=text;type=application/json'` a text row that keeps its type), and a lone `--data-binary @file`, `-d @file` or wget `--post-file` becomes a `binary` body (`-d @` is disclosed, because curl strips the file's newlines and Vayu does not), as does `-T`/`--upload-file`, which also makes the request a PUT unless `-X` says otherwise and appends the file name to a URL that names none; `--data-raw` never reads a file, a file body beside other data and a body from standard input are disclosed, and a value-carrying flag this parser has no case for is disclosed rather than risking its value for the URL that follows. The URL itself is chosen among the command's bare tokens by shape - an explicit scheme or a hostname-shaped bare address - rather than "first bare token wins", so an unrecognized flag's swallowed value (e.g. `--retry-delay 5`) can never bump the real URL out of its slot; any other bare token is disclosed as an ignored argument (issue #1445). Short flags combine the way curl reads them (`-sSL`, `-XPOST`, `-H'X: 1'`, `-sSLXPOST`): a value-taking letter takes the rest of its word, or the next argument when none is left, and a cluster with a letter the parser does not know stays one disclosed unknown flag rather than being guessed at. `curl.exe`, bare or after a path or in quotes, is recognised as curl (the URL bar's context menu uses the same rule), `-b` with no `=` is a cookie file and is disclosed instead of becoming a `Cookie` header, `-H 'Name;'` imports as an enabled header row with an empty value, which the engine sends empty, and `-H 'Name:'` (leave out a header curl would add) becomes an unticked default: the lowercased name goes into the request's stored `disabledSystemHeaders`, with no row and nothing disclosed when the name is one the engine adds itself (`Accept`, `Accept-Encoding`, `Content-Type`, `Expect`, `User-Agent`, the correlation id) or one an earlier row of the command wrote; any other removal (`-H 'Authorization:'`, a name that is not an RFC 9110 token) would be an opt-out the engine ignores, so it is disclosed (#3220, #3194). The last word on a name wins, as in curl: a later `-H 'Name: v'`, `Name;`, `-A` or `-e` lifts an earlier removal, and a later `Name:` removes the earlier rows of that name, and `--json` or `-N` do not add their own `Content-Type` or `Accept` over one. The curl snippet round-trips the empty row: a blank value is written `-H 'Name;'`, since `Name: ` is curl's removal. A command the parser cannot read (an unterminated quote, or no URL) leaves the request as it was and toasts a warning naming which (`readCommand` never throws and returns the reason, `unreadable` for a parser fault, `unreadableCommandNotice` words it, #3685): the paste is already taken over, so staying silent would make it vanish. A non-command paste of one line falls through to normal input; one with a line break is a URL wrapped by a terminal, a mail or a PDF, and is inserted with each break and the whitespace around it removed, silently, as an address bar does (#3688) - Chromium would have turned each break into a space and sent `/wrap/ /second`, or rejected `http:/ /host`. A blank that is not beside a break is the user's own and stays.

> **Body tabs** support `none` / `json` / `text` / `graphql` / `jsonrpc` / `mcp` / `xml` / `form-data` / `x-www-form-urlencoded` / `binary`, from the one table in `panels/body/body-modes.ts`. **Whichever editor a mode brings fills the pane** - the box is a `flex-1` child of the tab panel with a `min-h-40` floor and no ceiling, and the two script tabs are the same shape. It is not a fixed-height box with a drag handle under it: inside a panel that already has the request pane's full height that shows a slice of an editor over empty panel, and the drag that would fix it dies with the Radix unmount on the next tab switch (#1323); how tall an editor is comes from the request/response splitter, which persists - the picker renders it and `body-editor-completion.test.tsx` derives from it which modes to render and check for `{{variable}}` completion, so a mode added without a completion-capable language fails that guard instead of losing the feature quietly. The `jsonrpc` mode is the plain code editor with Monaco's `json` language and an auto-`Content-Type: application/json` - a JSON-RPC call is one JSON document, and the frame around it (`"jsonrpc":"2.0"`, plus an `id` when the call names none) is completed engine-side at the chokepoint every client shares, so there is no structure for this side to edit and no component of its own. It shares the `raw` draft bucket with `json` / `text` for that reason (see [state-management](../state-management/request-builder-context.md#requestbuildercontext---body-drafts)). The `mcp` mode (#3762) is that same JSON pane with `panels/body/McpToolFields.tsx` above it: a call to a Model Context Protocol server, whose `params._meta` and headers (`Accept`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, `Mcp-Param-*`) the engine writes at send time for every client, so the panel derives none of them - it says the engine adds them, where they appear (the response's Request headers, which show the lines as sent) and, while no tool is stored, that no `Mcp-Param-*` header is sent. What the mode edits is the tool a `tools/call` names, `RequestState.mcpTool` (`{name, inputSchema?, outputSchema?}`, typed by hand: a name field and a JSON editor for each schema; the output schema only seeds a new `assert.jsonschema` element, #3806). It is stored inside the body object (`toBodyPayload` writes it, `index.tsx`'s load reads it back, and a body saved without it clears it), commits only what the engine would accept (`panels/body/mcp-tool.ts`: a blank name or a schema that is not a JSON object is refused with the whole save, so the fields hold such text with a `FieldError` and the stored tool stays), and is sent unresolved beside the resolved content on Send. A History copy of an `mcp` run takes the saved request's tool and a Save to request keeps it, because a run records the content and not the tool. The mode adds no Content-Type row and no snippet header: the engine derives them, so the generated snippets carry a note instead (see the code generators below). The `xml` mode is the same pane with Monaco's `xml` language and an auto-`Content-Type: application/xml`, and shares that bucket too: SOAP and legacy-enterprise APIs are HTTP plus a document the author writes whole, so the mode buys highlighting, `{{variable}}` completion (its `xml` language is in `BODY_LANGUAGES`, #1214) and the header rather than an editor of its own - the engine sends `content` byte for byte with no envelope, and a hand-typed `application/soap+xml` survives the mode change like any other header the user wrote. **The `json` and `jsonrpc` editors validate through the same masked twin as the Variables pane** (`panels/body/body-diagnostics.ts` attaches `lib/graphql/variables-diagnostics.ts` on mount), so a `{{variable}}` outside a string draws no squiggle and a real error after it is still marked (#3137). The twin follows the *model's language*, not the mode: every non-GraphQL mode shares one model per request, so `xml` and `text` drop it, and it is re-decided on a request switch and on a language change. The `graphql` mode renders a split resizable editor: a **Query** pane (Monaco `graphql` language with diagnostics, autocomplete, hover, and formatting) and a **Variables** pane (Monaco `json` with schema-derived validation). The Variables pane badges its text when it is not strict JSON - *Templated* for `{{variable}}` tokens, which are resolved and sent, *Not sent* for text the envelope cannot carry - because the two are opposite things on the wire. The editor no longer contradicts the badge: its markers come from a masked twin of the pane (`lib/graphql/variables-diagnostics.ts`), so a token draws no squiggle and everything around it stays validated. Its in-progress text lives in `RequestBuilderProvider` (see [state-management](../state-management/request-builder-context.md#requestbuildercontext---the-headers-a-setting-added)) for the body drafts' reason: Radix unmounts the inactive tab. **The Variables pane collapses to its own header**, which is the control - the whole bar is the button, since a narrow activator in a wide box is the composite-row hit-area trap. Collapsed, it keeps its badges on screen (a *Not sent* the user cannot see the editor for is exactly when the badge matters) and the query editor takes the height back; `collapsedSize` is the header's own 32px (`--spacing-band`, held by `titlebar-height.test.ts`) rather than a percentage, so the bar is neither clipped in a short stack nor floating above dead editor in a tall one. The collapse *and* the height to reopen at are in `layout-store` (`graphqlVariablesCollapsed` / `graphqlVariablesSize`, persisted), not component state and not `explorer-store`: the panel's own memory dies with the Radix unmount, and how tall a user wants a pane is a preference like every other one in that store. An insertion that leaves variables needing a value opens the pane on its own - the one moment the badge alone is not enough, because the user now has to type into the editor it names. A document defining more than one named operation also gets an **operation picker** in the Query pane's header, which writes the envelope's `operationName` - the panes carry that field (and any other envelope key) through every edit, so an imported multi-operation request keeps executing the operation it names. The picker keeps the header's right side, and a saved request gets a copy button beside it (not inside the Select, whose trigger would open the list) that puts the chosen operation's agent reference on the clipboard (`graphqlOperationReference`); it is absent for an unsaved request, with no `operationName` set, and when there is no picker. Its **left edge carries one compound schema control, in the same place whether the explorer is open or closed**: the pane toggle, then the status badge (`panels/body/SchemaStatusBadge.tsx`, sentence in `lib/graphql/schema-status.ts`), then a standing Refresh. The toggle sits at that edge because the explorer is the first panel of the horizontal group and so opens on the **left**, and its icon names that side (`PanelLeftOpen` / `PanelLeftClose`, `aria-expanded` bound to `explorer-store`); at the far right a `PanelRight*` pair would point away from the pane it opens (#1224). Only the toggle's icon and label change with the pane's state; nothing moves. *One standing Refresh* holds by construction - this is the only Refresh for the subject anywhere, the explorer's and the context bar's having gone - rather than by transparency: a Refresh invisible until hover or keyboard focus (#455, #507) answers the duplication with a control the user has to know about already, and leaves a real duplicate (the context bar's) standing in a combination no single-component test could see. **Scripts** are two separate panels - pre-request and test - not a single tab.

> **The Body tab's Resolved view masks secrets** (#1813). In the json, text, jsonrpc, mcp and xml modes it prints `resolveField(request.body, bodyFieldContext(mode, body)).text` with every secret variable value replaced by `••••` at render, after the stable-resolve memo (so a `{{$randomInt}}` stays put), through `useVariableSupport`'s `maskSecrets` - the same masker the Params "Sends" line and the key/value peeks use. Source text and non-secret values stay as written; GraphQL has no resolved display (its resolved URL and auth only key the schema cache). With a data row picked, a cell is written for the body's mode as the bind writes it (escaped in a JSON string, escaped for its place in XML), and a row the send would refuse - a token in an XML comment or processing instruction - is named in a warning `Callout` above the view (issue #2639).

> **The schema explorer docks beside the query pane** (`panels/body/graphql-explorer/SchemaExplorer.tsx`, opened and closed from the one toggle in the Query header). **Its header carries only what belongs to the pane**: the search box and the descriptions show/hide, in one row. It held five - status and freshness, Refresh and the close as well - which needed two rows, because in a pane that can be 18% of the editor area the search box, the only control that wants width, competed with the status text for it. Those three are the subject's rather than the pane's and moved to the Query header (#1224), where they stand in one place whether this pane is open or shut; the search box has the row to itself again. It takes the cache's `SchemaEntry` as one prop rather than status, schema and freshness as three, for the reason the body reads it as one: they are four faces of a single state and separately they can render a frame apart. A WAI-ARIA tree over the endpoint's Query / Mutation / Subscription / Types, where a field row draws its name, its result type and a muted argument count rather than the argument list itself - the full signature leads its tooltip instead, ahead of the description - and a field that takes arguments expands into an **Arguments** group, one row per argument, above the fields of what it returns; inline descriptions, struck-through deprecations and a search that spans the whole schema (`/` focuses it) round it out. The search ranks in **three tiers - name, then signature, then description** - reports which of the three found each row, and marks the matched run wherever it found it, so every row says why it is in the list. **Results are grouped under the same Query / Mutation / Subscription / Types headings the tree uses, and every field row names the type that declares it** (`App.accessScopes`, the owner in muted text beside the name rather than inside it, so highlighting still marks the name alone). Flattened, three types declaring `accessScopes` were three indistinguishable rows and nothing on screen said which one Query could reach; the branch and the owner are the address the tree carried in its shape, and the results now carry it in text. The headings are `role="presentation"` rather than a `role="group"` per branch, because the roving treeview reads parentage off the DOM and a wrapper holding several rows would make the first of them read as the parent of the rest. It spans the whole schema literally, enum values and input-object fields included, and inside the name tier the closest match comes first (earliest offset, then shortest name) so the row the user typed is not cut off by the result limit. Descriptions are a tier rather than more haystack because they are prose: folded in with signatures, a common word matches most of the schema through them and drowns the type matches that tier exists to surface. A row matched only through its *signature* stays unmarked, which is the difference showing rather than being hidden; a row is drawn with its full description only when the **description is why it matched**, because clipped to one line that description is usually cut off before the word that put the row in the results. That asks the tier, not the offset: both offsets are reported whatever the tier, so `Query.search` - named `search`, described "Search across users and posts." - answered the looser question yes and drew its whole paragraph over the results the user was reading. Descriptions are otherwise clipped to one line, with a **show/hide in the pane header** (remembered per schema in `explorer-store`) for reading them in full - one pane-level control rather than a per-row disclosure, since a third target inside a 24px row is the composite-row hit-area trap `drawer-row-hit-area` was written against. It is *beside the editor rather than in the context bar* because the bar clamps to 220-480px and because insertion wants to be next to the cursor it inserts at - the bar gets the status half instead (`GraphQLSection`, above). Rows are windowed with `useGrowingWindow`, not a virtualisation library, and keyboard navigation reuses `useRovingTreeFocus` rather than a second copy of the treeview pattern - which is what the per-row `aria-level` buys beyond the announcement. This tree renders every row, at whatever depth, as a direct child of the `role="tree"` element, so its nesting says nothing about what owns what; the hook reads the level for parentage, and until it did, Left-arrow here found no parent to step out to and silently did nothing (#1237). **A result row carries no expand toggle**: it is derived from the index and has no children to show, so the chevron flipped `aria-expanded` with nothing appearing beneath it - the "clicking the row does nothing" of #1226. Its leading control **shows the row in the tree** instead (`treeLocationOf` reconstructs the address from the ids the tree itself builds; `revealPath` opens that path as a union and spends the search term), and it takes the row-actions slot the treeview already reaches from a keyboard rather than adding a second tab stop inside a single-tab-stop tree. **A row that holds rows opens on activation** - a branch, the "Returned by" container, and the "Arguments" container - since Enter on a container had nothing to insert and therefore did nothing at all. Activating an **argument** row writes it onto its field as a `$variable`, declared on the operation, inserting the field first by the ordinary rules when the document does not select it yet; an argument the selection already carries selects the existing one rather than writing a second, and one under a subscription field is refused by naming the subscription, not the argument. Activating a row calls `insert-skeleton.ts`; the resulting query **and** variables are written in one `serializeGraphQLBody` call, since two writes would each re-serialise the envelope and the second would undo the first. The caret is placed in an effect keyed on the new query, because the pane is `value`-controlled and Monaco's model still holds the old text at the moment of the click. Activating a row whose leaf the selection set **already holds** writes nothing: the existing line is selected and revealed instead, and the live region says it is already selected. Duplicate fields are valid GraphQL - they merge - so this is not the never-produce-an-invalid-document contract but the second click adding a line the user cannot tell from the first; the narrowing is deliberate, since a field with required arguments can honestly repeat and an object field's second copy brings its own selection. Every insertion, every already-there, and every refusal (a subscription, an enum value, a field nothing in Query or Mutation can reach) reaches a polite live region - the same mounted-empty pattern as `ResponseAnnouncer` - **and a refusal also lands visibly in the pane** as a `Callout`, cleared by the next activation that succeeds. The other two show themselves: an insertion is text in the editor, an already-there selects the line it means. A refusal reaching `sr-only` text alone was a click that, to a sighted user, did nothing. The explorer performs **no introspection of its own**: it renders the schema cache, and it offers no Refresh - the one standing Refresh is the Query header's (above), on screen in both states, so the pane never has to be opened to reach it.

> **The Event stream toggle, the Events tab and the Stop button** (issue #574). Turning on **Event stream** in the Settings tab makes Send consume a `text/event-stream` endpoint live: `POST /execute` answers `202 {runId, eventsUrl}` at once and the upstream's events arrive over `GET /runs/:id/events`. It is a *setting*, not a `BodyMode` - the request's body semantics are untouched, and a stream is a GET as often as it is a POST - and it is stored on the request (`requests.stream`), because it describes the endpoint rather than one send. Turning it on arms `Accept: text/event-stream` through the same reversible-side-effect rule the body mode's `Content-Type` uses, extracted to `utils/auto-header.ts` so there is one copy of it (see the GraphQL note below for the rule itself). While a stream is open the URL bar's **Send becomes Stop** (`POST /runs/:id/stop`) and the status band reads *Streaming - N events*; the status band's time counts up from the stream's start (`ResponseState.sentAt`, stamped by `startStream`) instead of the placeholder's `0 ms`, and gives way to the run's own time once the stream ends (#3775); the eighth, always-rendered **Events** tab shows the rows, each with its offset from the send and its gap from the previous event beside the wall-clock time. A request can also declare a **stream text path** (`requests.stream_text_path`, `RequestState.streamTextPath`, issue #3773): a JSONPath, read by the engine on each event's JSON `data`, with two presets in the Settings tab's field under Event stream (`$.choices[0].delta.content` OpenAI-compatible, `$.delta.text` Anthropic-style) and any other path typed in. It is declared, never detected, so the app holds no provider shape. The engine puts what the path read on each event as `text` (`parseMessageFrame` whitelists it) and on the stored node as `streamText`, joined over every stored event; the store joins the live ones into `streamText` as batches land, the stored string wins at the swap because the stored item list is capped, and the Events tab shows it in a **Text** view beside **Rows**. Turning the stream off empties the path (`streamPatch`), since the engine refuses one beside a buffered request, and the path is stated in the execute and load-run payloads only while the request streams (`streamTextPathOf`), because an inline compose carries none. A request can also declare a **first content marker** (`requests.stream_first_content_marker`, `RequestState.streamFirstContentMarker`, issue #3774): a literal, with two presets (`content_block_delta`, `"delta":{"content":"`) beside the text path's field, that a **load run** matches against the stream's raw bytes to time `stream.timeToFirstMatch`. It is kept verbatim (never trimmed), emptied with the path when the stream goes off, and stated in the load-run payload only (`streamFirstContentMarkerOf`), since a Send times nothing with it. Live rows come from `stores/execution-events-store` via `hooks/useExecutionEvents` - a per-endpoint `EventSource` with its own reconnect and `?lastEventId=` resume, the inbox capture stream's shape (`services/inbox-watch-service.ts`) rather than the `SSEClient` singleton, which belongs to load and scenario runs and deliberately never reconnects. When the stream ends the provider fetches the run's report and `restore-response.ts` swaps in the stored `events` node, which is the record and the only copy carrying the truthful `totalEvents` / `eventsTruncated` markers - the same two-sources-one-list handoff `ScenarioRunView` makes. That finalisation (`context/stream-finalization.ts`) is addressed to the request that streamed, not the one on screen (#3382): a stream that ends while the user is on another request still lands in its own request's stored response (the live pane is touched only if that request is the one showing), and the provider invalidates the run lists, `runs.recentDesign(id)` and `runs.lastDesign(id)` so the restore on return reads the finished run. A run whose feed another request's stream took over has no relay left to say it ended, so the builder watches it by polling `runDetailOptions` (every `RUN_IN_PROGRESS_POLL_MS` while the run is in progress) and finalizes it the same way, with the Send snapshot the store kept for it, once the engine reports a terminal status. A send of the same request that began after the run was claimed wins over the late swap (`sendCounts`), and another request's Send emptying the store mid-fetch does not drop it. The claim that keeps each run to one finalisation lives in the store, not the provider: `Shell.tsx` unmounts the builder on every tab that is not a request, and a remount neither fetches a finalized run again nor loses a run that ended while it was away, which it finalizes on mount. A report that cannot be fetched gives its claim back, so the next mount tries again. Only a builder given a stream handler finalizes: the History run view's `RequestBuilderProvider` has none and leaves the store alone. The store holds one feed, so a stream Send from another request closes the running one's relay but not its run, which the engine keeps consuming until its own end rule (#3352): `handOver` holds that request's run as `displaced` and `startStream` records it in `replacedFeeds` once the new stream has actually opened (a Send whose stream is refused or never starts takes nothing over), and its response pane shows an info `Callout`, *Live feed taken over*, above whatever it would otherwise draw (the empty state, or an earlier run restored in its place), saying the stream kept running and that History shows its events once it ends. The request's own next Send drops the note (`beginSend`), and the pane leaves it off once it shows that run's own stored record. A stream Send empties the pane and the request's stored response, and the pane is not refilled from the previous design run while the stream is held or afterwards: a stored response adopted at mount or on a request switch counts as the answer to the backend restore (`restoredFor`), and the restore also waits while the store holds a stream for the request (#3421). Every termination names itself (`completed`, `stopped`, `maxStreamEvents`, `maxStreamDurationMs`, `idleTimeout`, `shutdown`, `error`; `shutdown` is the engine going down, which the Events tab tells apart from the user's Stop, #3342) and every cap is disclosed in band. A streaming design run does **not** block a load test and is not blocked by one: they are independent surfaces. Scripts run on a streaming send (issue #575), split around the transfer - Pre-request before the stream opens, Tests once it has terminated, reading the retained events as `pm.response.events` - and the Settings panel says *when* rather than warning that they are refused, because Send has returned long before the results reach the Tests and Console panes. Every stream request keeps the bytes it received as its Body (issues #3238, #3770): the engine stores them once, as the trace's `response.body` (up to `maxDesignResponseBodyBytes`), and the Body tab shows them as received once the run is stored - an event stream's `event:`/`data:` lines as much as a JSON 404's text - while the stored `events` list is parsed back out of those bytes when the trace is read, so Pretty, Raw, Copy, Download and Save as example all read the stream's text. The placeholder built from the `open` frame has an empty body until then. A stream the engine's read cap cut carries `bodyCapped`, and its notice words what was read by the prefix held (`cappedReadExtent`, `utils/response-bytes.ts`), because the size chip counts the wire and a stream is read past the cap. When the reply was **not** an event stream (a JSON 404, NDJSON), the Events tab says `The server answered <type>, not an event stream - see Body.` instead of "No events received" (`ResponseEvents`' `contentType` prop, read from the open frame's headers while live and the stored response's after, matched case-insensitively with any `; charset=` ignored; no `Content-Type` keeps the generic wording; issue #3238). The flag and the `Accept: text/event-stream` row are written together by `streamPatch` (`utils/auto-header.ts`), the one patch the Settings switch and the Body tab's buffered-reply callout both send to `setRequest`, so the two cannot drift. `sentAt` is the renderer's stamp when the `202` landed, carried through the finalisation claim onto the stored response; a stream reopened from History takes the engine's `startedAt` from its stored `events` node instead (#3805; `eventsFromTrace`, the same engine clock as `receivedAt`, carried and never recomputed), so its rows and Timing tab count from the transfer start; the renderer's own stamp wins when both exist, and a node stored before the field existed has neither, so its rows show gaps only and its Timing tab no first event. The size chip counts the bytes the stream delivered (`response.bodyBytes`, a UTF-8 byte count since #3423, a size and not a truncation flag) and is left off the band while the placeholder built from the `open` frame is all there is, because the relay carries no body to count.

> **The `binary` mode sends one file as the whole body** (`panels/body/BinaryBodyPanel.tsx`). The editor holds a path in `RequestState.binaryFile`, never bytes - the engine opens the file at send time. The file is dropped on the panel, picked with Choose file, or typed into a `VariableInput` path field (so `{{fixturesDir}}/a.bin` gets the same completion as every other field); the drop and the pick go through `components/shared/file-pick.ts`, the piece `FilePartCell` uses too. Only the drop and the pick choose the file (#2356): the preload reports the path to the main process, which records it as picked, and the panel sets `unresolved: false` until the engine's next read answers for it. A typed path is not a pick; it carries no flag and reads as not chosen. `unresolved` is otherwise the engine's own answer, derived on every read and never sent back (`lib/file-trust.ts`, [API integration](../api-integration/http-client-and-service.md#request-bodies)). The rule the engine applies: Vayu sends a file picked on this machine, or any file under a folder you allowed. So a warning `Callout` titled *Not chosen on this machine* offers **Relink** and, inside Electron, **Allow folder…** (the system picker opened at the file's folder; main allows what is chosen) for a path the engine would refuse or has not answered for yet, a *Path has a variable* one offers **Allow folder…** for any path with a variable in it (sent only from an allowed folder), and either turns into a positive note when the path already sits under an allowed folder (`isUnderFolder` in `lib/file-path.ts` - a text comparison for display; the engine's check is on canonical paths). The file line shows the name and the size the main process reports (`electronAPI.statFile`, which never reads contents and answers only for a picked file or one under an allowed folder, #2357), or *Not found on this machine* - which is also what a typed path outside every allowed folder that was never picked shows. The Content-Type field is the file's own `contentType`; `body/binary-content-type.ts` states what goes out - an enabled `Content-Type` header row, then that field, then the engine's extension table, which is not copied app-side, so the editor says "from the file extension" rather than guessing. The mode writes no Content-Type header row of its own.

> **Choosing GraphQL writes a header, and leaving GraphQL removes it.** GraphQL is sent as a JSON envelope, so picking it appends `Content-Type: application/json` to the Headers tab (unless an enabled `Content-Type` is already there) and says so in a notice with an Undo. The next mode change that no longer needs that header takes the row back out. The row is tracked **by marker, not by value or id** - a `Content-Type` the user typed carries no marker and always survives, and retyping a marked row's key or value clears the marker (`KeyValueEditor`'s `handleUpdate`), so it too survives from then on. The marker (`KeyValueEntry.source: "body-mode"`) lives on the row itself rather than in a provider-held record, so it survives a reload, which a ref the provider held could not (issue #1481). The rule itself lives in `utils/auto-header.ts` (`switchAutoHeader`), because the Event stream toggle needs the identical one for `Accept` (marked `"stream"`) and a hand-rolled copy of a primitive does not receive the primitive's fixes; `panels/body/content-type.ts` is what maps a body mode to the value it requires: `json`, `graphql`, `jsonrpc` and `xml` only, since the panel writes no row for `text` (the engine derives `text/plain` at send time) or `mcp` (the engine derives its `Content-Type` with the other MCP headers, and a row for one of them would copy a derivation that is the engine's). `implied-content-type.conformance.test.ts` pins the panel's table, the code generators' and the mode chips to the engine's from one fixture. The engine's importer asks the same question at import time (`with_required_content_type`, see [import-collections](../import-collections/postman.md)), because an imported GraphQL request never passes through the mode picker and would reach the wire with libcurl's default `application/x-www-form-urlencoded`.

> **Choosing GraphQL on a default GET also moves the method, and leaving GraphQL puts it back** (issue #1228). A new request is a GET, and GraphQL-over-HTTP means something different on one - the document travels as query parameters, and a mutation cannot be sent that way at all - so picking the mode alone would build a request the server answers with a bare `400`. The mode sets `POST` the same reversible way it sets the header above, tracked **on the request itself** rather than in a provider-held slot: `RequestState.methodSource?: "graphql"` (issue #1505, mirroring `KeyValueEntry.source`) marks `method` as still GraphQL's, so it survives a reload the way a stale provider-held record could not (the same gap issue #1481 closed for the Content-Type row). `switchGraphQLMethod` in `panels/body/graphql-method.ts` is the rule - only from GET, only to POST, and a method the user chose is never overridden in either direction, the same "no longer ours" check `switchAutoHeader` makes on an edited row; `MethodSelector` clears the marker in the same call that sets a hand-picked method, the way `KeyValueEditor`'s `handleUpdate` clears a retyped header row's marker. A GET still reaches GraphQL by another door - the user picks it back, or an import wrote one - so the Query pane header carries a `BadgeText` reading "Sent as query parameters" whenever the method is GET, naming the transport rather than reporting an error: GET is a legitimate way to send a query, and the wrong one for a mutation.

## `components/OAuth2LoadTestGuard.tsx`, `components/oauth2-load-test-coverage.ts`

Warns when a duration-based load test would outlive its access token, in the cases the engine will *not* renew mid-run - a request's load run and a collection's alike (a query-placed token, `autoRefreshToken: false`, an `authorization_code` grant with no refresh token): offers **Refresh** when a fresh token would cover the run, or **blocks Start** (with a "Start anyway" override) when even a fresh token can't.
A run the engine will keep current gets an info line, not a warning.
The pure coverage decision lives in `oauth2-load-test-coverage.ts`, whose `isMidRunRefreshable` mirrors the config-and-token cases of the engine's `plan_oauth2_refresh` - not the check `plan_auth_refresh` adds to it, a user-supplied `Authorization` header that beats the token, which the guard is never handed the headers to see - and not the two collection-step cases (a step whose auth waited on its scripts, one writing the token under another `headerPrefix` than the first step sharing its cache key), which it cannot know either.
Change one, change both.
The request's load dialog renders one guard; `RunCollectionDialog` renders one per *distinct* token its run sends (#3199).
Under load the token it judges is the one fetched once before any script, from the stored values (#2742); with an OAuth 2.0 name a script may change the verdicts say "fetched before scripts" (`scriptMayChangeSettings`), so they never read as a verdict on the token a Send would acquire.
While the token status is loading, or the check failed, the guard says so ("Checking for a cached token…", "Couldn't check for a cached token") rather than "No token cached"; it takes the split from the shared `noTokenState` in `shared/OAuth2Form/token-phase.ts` and neither state gates Start.
A status already on screen keeps its verdict through a failed refetch, and a token the engine flags expired reads as lapsed (`tokenPhase`) A config discovered from a server URL that no sign-in has filled yet (`awaitsDiscovery`, #3766) has no token a run can fetch headless, so the guard says "Sign in before running" whatever the run's length, without gating Start

## `shared/BulkEditor.tsx`

The table/text toggle above a `KeyValueEditor`, and the textarea it swaps in - `ParamsPanel` and `HeadersPanel` had a copy each.
It stayed in the module when the table left for [`components/shared/`](shared-key-value-editor.md#shared-keyvalue-editor-componentssharedkeyvalueeditor) (issue #567): the shared bucket is what *several* features share, and only these two panels bulk-edit.
The formats are the callers' - headers are `Name: value`, params are `key=value` - so a parse, a format and the syntax note are what it takes in.
A leading `// ` on a line disables that row, and only the key is trimmed - a value's whitespace, past the one conventional space right after the separator, is sent exactly as typed (issue #1480).
`BulkEditor` is controlled (`draft`, `onDraftChange`, `onCommit`) and always commits the draft on the way back to the table (that is the staging contract `BulkEditor.test.tsx` pins).
The request builder holds the draft per request in `RequestBuilderProvider` (#3666, see [state management](../state-management/request-builder-context.md#requestbuildercontext---bulk-edit-drafts)), so it survives a sub-tab switch, returns with its request in text mode and is never shown to another; Send writes an open draft into the request and closes it, Save writes it and leaves it open.
Every commit goes through `bulkTextPatch` (`utils/bulk-drafts.ts`), which skips the update when the text describes the same rows the table holds, so opening and closing the editor without typing cannot re-enable a row or dirty the request, and a params draft rewrites the URL by the table's own `queryTablePatch`; a line the parser drops (a header with no `:` or `=`, a param whose key is empty) is never a silent loss: the Table toggle and Send raise a warning toast naming up to three of them by line number, blank lines counted (`unreadLineNotices`, #3694, from the same `scanKeyValueLines` the parsers read through), while the rows that did parse still commit, and it speaks even when the text changes no row; Save and autosave leave the draft open and say nothing; the **Sends** line describes an open params draft.
**`after` renders in both modes.** The engine's declared headers and the resolved URL are not part of `children`, so they do not vanish the moment you switch to text - exactly when a pasted block most wants checking against what it will actually send; only the table itself and its empty-state `tableHeader` are table-only.
A **Discard** button appears beside the mode toggle once the draft diverges from the rows it opened against, leaving text mode without committing - the toggle itself still always commits, which is the contract above
