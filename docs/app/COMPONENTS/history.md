# History (`modules/history/`)

Past runs (single executions and load tests), split into a sidebar list and a main detail view.

**Sidebar (`sidebar/`):** `HistoryList.tsx` (filter/sort all runs; state from `useHistoryStore`, data from `useRunsQuery`; search, type, status, outcome, origin and pinned are asked of the engine so they reach runs older than the loaded pages, and only the MCP-client narrowing and the sort are client-side) and `RunItem.tsx` (one run row - status glyph, method badge (a collection run shows a folder glyph instead), request name or URL, load-test chips; the start time and the status word are the row's time card, on its stretched activator). Its pin and delete take no width until the row is hovered or focused (`ROW_ACTIONS_REVEAL` in `components/shared/row-actions.ts`, #3495): a pinned run keeps its pin showing and a deleting one its spinner. The list mounts a **growing window** of what it has loaded (#2980), not every row: `useGrowingWindow` shows the first 200 and adds a step as the "Showing N of M runs - scroll for more" line scrolls into view, because the rows vary in height (a result line, a comment) and so cannot be a fixed-height virtual list. Each mounted row sits in a `skip-offscreen` wrapper, and `RunItem` is `memo`ised, so a filter, sort or selection change re-renders only the rows whose props changed - which holds because the handlers `HistoryList` passes are `useCallback`s and the day groups are keyed by their label, not by their first run (a run landing at the head of Today must not remount the group). The window's key is the question being asked (search, filters, sort), so a poll or "Load older runs" lengthening the same list does not shut it, and **Load older runs** appears only once every loaded run is mounted. Focus landing on the last mounted row (`useHistoryListFocus`'s `onReachEnd`) grows the window, so Down and End never stall at its edge while a sentinel sits just outside the scroller. A **finished load run's** row also says how it went (#2130): its glyph is refined by the verdict (`rowOutcome`: the category is the row's stored `outcome` when the engine sent one (#3547), and the reason and every row stored before that column come from `resultSummary.verdict`, `.errorRate` and the `.assertions` block alone, read through `rowAssertionsOf`, which takes a pre-#3537 row's flat `.assertionsFailed` as exact - the tick only for a run that passed, a ringed exclamation for failed, a ringed question mark for not judged), a result line under the identity ("485 req/s · p95 42ms · 0.0% errors", each figure left out when the run did not record it, and ending with the failed checks in the verdict's words, "4,580 assertions failed", "4 assertions failed in the sampled replay", "3 elements errored", "1 teardown script failed", #2820, #3458, #3537) and the verdict in the activator's accessible name. A **completed collection run** with a failed or errored step is marked the same way (#3458): `rowOutcome` answers `failed` from `resultSummary.failed` and `.errored`, and from a `.verdict` of `"failed"` (a missed budget, #3539, with or without "Fail the run": the reason reads "Budgets missed", joined with the counts when both apply), the line under the identity is the step counts (`collectionSubtitle`: "2 passed, 1 failed, 4 errored", zero counts left out, with "budgets missed" ahead of them when a budget was missed) and the activator's name gains ", verdict failed". A clean collection row (one whose budgets were met included), and one a Stop ended, keeps its status glyph and has no line. A row whose **status is `failed`** is `failed` for every run type, with or without a `resultSummary` (#3643): the status is the verdict, so a design run, a load or collection run that failed before a summary was written and a crash-recovery orphan all wear it, with the reason "The run failed before it finished" (or "Budgets missed" when the row's own `verdict` says so). The engine stores the same `failed`, so the Outcome filter lists them; a row stored before the column (schema 11) derives `failed` here though its stored `outcome` stays NULL, so `GET /runs?outcome=failed` pages do not list it. A **capacity run's** line is the search's levels instead (`capacitySubtitle`, #2930): "held 41 · gave out at 51", "gave out at 51" when the first level already breached, "plateaued", or "held at least 200" for a stop on a bound the caller set; a search with no level prints no line, never the run-average rate, and a row from an engine that sends no `resultSummary.capacity` keeps the average-rate line. Its meta line leaves out the deadline and virtual-user ceiling (the search stops when it finds the limit, so neither describes the run) and keeps the mode. The run's **comment** is a visible line of its own (two lines at most) for every run type, not a row of the time card: it is what tells two runs of one URL apart, and a hover is the wrong place for that. Right-click opens the row's pin/delete actions through `RowContextMenu` - a second route to the same hover-revealed handlers, since a history row had no menu at all before issue #1360 - plus **Copy for agent** (`runReference`, #2047), which has no hover-revealed button to mirror and is the menu's own.

**Who started a run** (#1817) is two marks on the row and one Select in the filter row. The engine records `origin: {kind: "app"|"mcp"|"other", client}` on every run (the renderer stamps `app` in `apiService`'s four run-starting calls, the MCP server stamps `mcp` with the client's handshake name). A run whose `requestId` is null and that is not a collection run (`type: "scenario"`, or a scenario load run, which carries `summary.scenario`) shows **Unsaved**: it came from a tab that was never saved, or from an agent that sent the request inline, so there is no request to open it from. A collection run never links a request, so it is exempt. An agent's run (`origin.kind === "mcp"`) shows a neutral chip with the client's product name from `mcpClientDisplayName` (`lib/mcp-client-names.ts`), the raw identifier when the table does not know it, and "MCP client" when the agent sent none; the app's and `other` runs show nothing, and the chip is in the activator's accessible name. Both marks are their own `shrink-0` elements beside the identity span, which stays the only thing that gives way. Every spelling in the table is one a client was seen to send, read from the client's source or from the community registry of `initialize` requests (apify/mcp-client-capabilities, snapshot 2026-10-06), and none is captured from a client talking to Vayu (the file's header says which row rests on what; #1819 stays open for the captures and for whether each client echoes `Mcp-Session-Id`). A wrong row costs a raw label rather than a wrong name. The third **Select** (All origins / App / Agents) sends the kind as `GET /runs?origin=` and re-applies it in `filterRuns`; once the loaded runs name more than one agent, each client is an entry under Agents too, narrowing client-side. "Clear the filters" resets the origin with the rest, and an origin that empties the list counts as a narrowing filter for the empty-state copy.

The **Outcome** Select (All outcomes / Failed / Not judged / Passed, #3547) answers "which runs missed a budget", which the Status Select cannot: a run that missed one is still `completed`. It sends the verdict as `GET /runs?outcome=` (`failed`, `not_judged`, `passed`; the engine stores it on the row, so a failure past the loaded pages is found) and re-applies it in `filterRuns` from the row's stored `outcome`, or from `rowOutcome` for a row without one. A row the history draws no verdict for - a design run that did not fail, a clean collection run, a run still in flight, a run stored before the column that did not fail - matches none of the three. A run whose status is `failed` is `failed` whatever its type or summary (#3643); one stored before the column wears that verdict from `rowOutcome` but has no stored `outcome`, so the engine's `outcome=failed` page does not return it and the filter will not list it. The Status Select is unchanged. "Clear the filters" resets it, and a chosen outcome counts as a narrowing filter for the empty-state copy.

The filter row also carries a **Pinned** toggle, a filter of the same kind as the Selects in that it changes what is *fetched* (`GET /runs?baseline=true`, see `useRunsQuery`) rather than only what is shown, so a pin old enough to sit past the loaded pages is still findable - which is the whole point of a filter for pins. It is applied a second time client-side, because unpinning patches the loaded pages in place instead of refetching them; without that pass the row just unpinned would linger in the pinned-only list until the next poll.

Every run's row carries the pin: a Pin action beside Delete (`useSetRunBaselineMutation` → `PUT /runs/:id/baseline`), on the row itself and in its right-click menu, and once pinned a chip that stays visible rather than appearing on hover - the pin is state, not an affordance. Only a load run's pin is also its request's (or collection's) **baseline** for the vs-baseline comparison strip: a baseline exists to be diffed, and only a load run has percentiles, throughput and an error rate to diff, so its chip reads "Baseline - kept past retention" and its action "Pin as baseline" / "Unpin baseline - kept past retention" (#2163: the pin's second meaning was only in a tooltip), where a design or scenario run's read "Pinned"/"Pin". The long chip is not `shrink-0`: it truncates at a narrow drawer (capped at half the identity line) and keeps its full text in a `title`, so the identity span stays the line's main text. Every pin, regardless of type, exempts the run from the engine's retention and keeps it findable under the Pinned toggle - the promise the toggle already made to every row. `DesignRunView.tsx`'s header offers the same action, for a run open on screen without going back to the list. No confirmation dialog, unlike Delete - both directions are one click from being undone. Delete's own dialog adds "This run is pinned as a baseline." for a pinned run, because naming the run deletes it where Settings' *Clear run history* would have kept it.

A **collection run's** row is a different shape, because it has no url and no method: a folder icon and the collection's name, over a chip line of step count, iterations (omitted when 1, the default) and sub-folders. The badge slot beside Delete is deliberately **empty** for one. That slot marks the types whose identity line would otherwise look alike - load and design both print a bare URL, so load carries the ⚡ - and a collection run's identity is already unmistakable, so a badge there would be the third glyph in one card saying the same thing, after the folder icon and the step count. Guarded by a test asserting no two icons in the card are the same glyph.

A **collection run** row has no url and no method - its work is a sequence - so it renders `summary.scenario` (`GET /runs`) instead: the collection's name, the plan's step count, and iterations when there was more than one pass. The name is not on the wire; `HistoryList` resolves it from the loaded tree with one shared `useCollectionsQuery` and passes it down, so the row stays presentational over already-shaped data and the page does not become one query per row. A collection deleted since its run falls back to the id it does have. The type filter carries all three run types - `filterRuns` compares its value to `run.type` directly, so a type the dropdown cannot name is one the list can only show under "All".

**Detail (`main/`):** `HistoryDetail.tsx` routes by run type to `DesignRunView.tsx` (a single request execution, opened as an editable copy), `ScenarioRunView.tsx` (a collection run's step list) or `LoadTestDetail.tsx` (load-test report), or - for a load run the engine is still executing - `components/LoadRunInProgress.tsx`.

A run the engine answers 404 for renders "This run no longer exists" with **Close tab** and no retry. The detail names both causes, because the 404 cannot tell them apart: the run was deleted, or History's retention removed it (it keeps only the newest Send runs, and the limit is a server-side setting, so the text states no number).

`HistoryDetail` fetches the **run** (`useRunQuery`) and asks for the report only when the run is a load run, or a finished scenario run whose pill it judges. `GET /runs/:id/report` is a load-test aggregate: against a design run its percentiles all come from one sample and `metadata.configuration` is absent, so it cannot say what a design run's auth, scripts or redirect settings were. `GET /runs/:id` can, and for a design run it also carries the stored exchange. The header is the run tab's one `h1` for every run type (#2270) and is titled by what the run ran, not by its type and id (`run-heading.ts`'s `runTitle`): the request's name (`configSnapshot.requestName`, else the list row's `summary.requestName`; the default "New Request" says nothing and is skipped), else the collection's name for a sequence - including a collection *load* run, which is `type: "load"` - falling back to the collection's id once it is deleted, else the type's name (`RUN_TYPE_NAME`). Beside the title sit the status and the start time (`TimeValue`, so the hover card gives the zone). Under it a small line holds the type (omitted when the title already is it) and the run id in mono with an icon button, **Copy run ID**, to copy it; under that, the run's **Comment** (`runComment`: the snapshot's, else the summary's; the shared `components/shared/RunComment.tsx`, which draws nothing for an empty one). `LoadTestDetail`'s "Test config" box does not draw it, so a run whose only config is a comment opens no box. The header shows **no** URL - the builder below renders its own URL bar, and two stacked read as a bug. Beside the title sits a text **Copy for agent** button (#2047), once for every run type since the header is above the per-type views: it copies `loadedRunReference` (`lib/run-reference-input.ts`), which reads the run's name, method and path off `configSnapshot` because `GET /runs/:id` carries no `summary`, and names a collection run by its collection from `useCollectionsQuery`. Beside it, for a finished load run only (the `showsReport` case: the engine exports nothing else), sits the **Export** menu, `main/components/RunExportMenu.tsx` (#2139, below). A **scenario** run's pane is not gated on its report, for a different reason: while the sequence is still executing the live `step` stream is the content, so waiting for a report that does not yet describe a finished run would hold the tab on a skeleton for the length of the run. `ScenarioRunView` asks for the report itself. `HistoryDetail` reads the same report (one query key, so one request) for a *finished* scenario run only, to judge the status pill (#3543); neither the skeleton nor the error state waits on it, and a live run's pill stays the plain status.

A **load** run that is still live (`useRunLiveness`: `running` or `pending`, or, before its status is read, held live by this window's dashboard) is the opposite case, and it is not shown as a report either (#1934). The engine serves `GET /runs/:id/report` for a live run, but the numbers are the requests so far, and a tab that rendered them kept them: the report was cached as final and nothing told the tab the run had ended. So the pane fetches no report until the run has finished and renders `LoadRunInProgress` - a sentence saying the run is in progress and its results appear when it finishes, a **Stop** (`StopRunButton`, through `useStopRun`) and, only when `dashboard-store.currentRunId` is this run, an **Open dashboard** action (a run started in another window or before a relaunch is not on this window's dashboard, and the button would open an empty one). `runDetailOptions` polls the run's status every 3s while it is live, so the pane turns into the report on its own when the run ends; `LoadTestService` invalidates the run's detail, report and series on a close it watched, so that tab does not wait for the poll.

`DesignRunView.tsx` renders `RequestBuilderProvider` + `RequestBuilderLayout` with starting values from `design-run-seed.ts` (`seedFromRun`), the stored exchange as `initialResponse`, and the elements the run recorded for its collection chain as `seed.inheritedElements` (the run's own are the copy's Elements tab, both read from the snapshot's stored `elements`; a run from before #1514 is rebuilt from its retired script parts). It **holds the pane until `useRequestQuery` settles**, and tells a genuine deletion from a transport failure before seeding: `seedFromRun` reads a falsy live request as "deleted", so a query in flight, a deletion and an unreachable engine all look alike unless kept apart. The provider re-seeds only on a change of `initialRequest.id` - null for every detached copy - so an early or wrong seed would stick. Loading holds the pane behind a `DetailSkeleton`; a genuine deletion (the `RequestNotFoundError` sentinel from `useRequestQuery`, matched via `isRequestNotFound` not a message string) seeds the orphan copy that replays the recorded wire headers; any other settled error is a transport failure and renders `ErrorState` with a retry rather than guessing a copy. The run's recorded auth **mode** (`seed.recordedAuthMode`, all that survives storage) is shown read-only beside the copy, so a user can see when the request's current auth differs from what the run sent. A run whose body was a `binary` file shows the file it sent - name, size and the start of its sha256, the full hash on hover - from the trace's request node (`request.bodyFile`, read through `lib/sent-body-file.ts` and drawn by `components/shared/SentBodyFileNote.tsx`, which a scenario step's expansion in `ScenarioStepCard.tsx` renders too); the path is never recorded there, and the hash is what tells whether the file on disk has changed since. Save to request writes a binary body's file reference back, unless the snapshot recorded no path, when the saved body is kept. A run recorded before script parts existed passes its one glued string as `legacyPreScript` / `legacyPostScript`; `LegacyScriptNotice` shows it whole with a note that its parts cannot be separated, and the replay sends it as a single request-origin part. A recorded script with no script text (missing, not a string, or whitespace only) is left out of the seed and the replay (`isBlankScriptElement` / `scriptPartToElement` answer null, #3066): the engine refuses a script element with no script, which would 400 the whole resend. **The copy is detached** by two independent gates - `id: null` and no `onSave` - so editing it cannot rewrite the saved request. Sending again replays the recorded inherited elements unchanged plus the copy's own (edited) elements, under the same `requestId`. `SaveRunToRequestDialog.tsx` + `save-run-to-request.ts` write chosen values back behind a confirm; they never write auth (only the mode survives storage) and never write scripts for a run stored before script parts existed. Otherwise the copy's own elements are written, with the saved request's disabled elements kept (`elementsToWrite`: a send never records a disabled element). They never seed or write what the engine withheld from the snapshot (`<redacted>`, `lib/withheld-value.ts`): a credential header's recorded value is never a row (the request's own row of that name stands in, so a header the user typed still replays and saves unchanged), and a url, params or body holding the marker is left off the save as a kept row, the way a truncated body is. Those three are seeded as recorded, so the copy shows a `WithheldValuesNotice` (`history/main/components/`) warning that sending it sends the marker literally. The header also carries a Pin/Unpin button (`useSetRunBaselineMutation`, the same mutation the sidebar row uses) so a run open on screen can be kept past retention without returning to the list first. **A run an agent started that no saved request stands behind** (`run.origin.kind === "mcp"`, no `requestId`: `send_request` runs inline and the run is the only record) has nothing to overwrite, so there the header leads with Save to request as the primary action (`SaveAgentRunButton.tsx`, gated by `isUnsavedAgentRun`), and it creates a request instead. It hands `save-run-as-request.ts`'s `presetFromRun` to `useNewRequest` - the same flow as every other "New request" (the remembered collection, a new one when there are none, `CollectionPicker` when it would be a guess), which opens the new request in its own tab. The preset is `createFieldsFromRun` (`save-run-to-request.ts`), the update's field rules shared by one function so the two cannot disagree about what is safe to write (no auth, nothing withheld, no truncated body; a withheld url is saved empty), plus a name (the request name the run recorded, else `METHOD url` without the query) and the description `Saved from a run started by <product> on <date>` (`savedFromRunDescription`: the product name from `lib/mcp-client-names.ts`, an unmapped identifier as sent, `an MCP client` when none; the run's start date through `formatInstant`) so the provenance outlives the run. The run keeps its null `requestId`, so the button stays after a save and a second press saves a second copy. A linked run keeps the overwrite button, second in the header and unpromoted.

`LoadTestDetail.tsx`'s scrolling body, above the tabs, carries `main/components/BaselineComparison.tsx`, the **vs-baseline strip**: the open run's p99, throughput and error rate against the run pinned for the same request - or, for a collection load run, the same collection - each delta coloured by `MetricDelta.direction` rather than by its sign (latency up is a regression, throughput up is not). It resolves the pin itself through `main/components/usePinnedBaseline.ts`, the lookup the Export menu's comparison toggle shares (`useBaselineRunQuery`: by `requestId`, by the `collectionId` of a scenario load run's snapshot (which has no `requestId`), or by url+method for a run of an unsaved request; `runIdentity` in `lib/run-reference-input.ts` picks the first two, the url and method read off the loaded run's `configSnapshot` through `runReferenceInput`, the report's `metadata` standing in where the snapshot has neither) and fetches the run from the shared cache the pane above already filled, so it stays self-contained instead of threading a prop through every call site. It renders **nothing** when no run is pinned, when the open run *is* the pin, or before the baseline's report has loaded - a strip of zeros would claim "nothing changed" about runs that were never compared. Under the deltas it lists the **comparability warnings** (#2162), one `AlertTriangle` row per entry of `RunComparison.comparability`, each the message followed by the baseline's value and then this run's ("Run durations differ by more than 2x. 20 s vs 3 s, stopped."): run type, mode, virtual users, target rate, duration, status, HTTP version, data file, request, compression negotiation and whether `Expect: 100-continue` was allowed (#2516), because a short stopped run against a long one always reads as a throughput and tail-latency regression. A like-for-like pair draws no list. When both reports carry `metadata.runType`, a mode, virtual-user count or target rate only one recorded is a warning whose missing side reads `not recorded` ("Virtual users differ. not recorded vs 10."); otherwise a field a report does not carry is never a warning (#2438). The list is computed in `compareReports`, so `compare_runs` returns the same entries. The diff comes from `lib/run-compare.ts`, mirrored by the MCP tool's `electron/mcp/compare.ts` and pinned to it by `compare.conformance.test.ts`. A run flagged `summary.summaryMissing` or `summary.partial` (#2895) is judged per side (#2904): when the **baseline** is the flagged one, its figure reads as unrecorded, so the cell keeps this run's real figure and its change reads "baseline not recorded" rather than a delta against a 0 (`summaryMissing` for all three, `partial` for the p99 only); when **this** run is, the strip drops the tile it did not measure, as below. Three metrics, deliberately: it is a glance above the report's tabs, and the rest of the diff (every percentile, both throughput measures, the status-code merge) is the **Compare** view below. Its label row carries a text **Copy comparison for agent** button (#2047): `runComparisonReference` over the baseline row and the open run, both mapped through `runReferenceInput`, toast "Reference copied".

**Export a finished run** (#2139). `main/components/RunExportMenu.tsx` is a `DropdownMenu` behind a text **Export** button (the `Download` glyph, styled like Copy for agent), mounted by the run tab's header and by the post-run `DashboardHeader`, each only for a finished load run. Its items are `runExportActions` from `lib/run-export-formats.ts`, the list the palette's export commands are generated from: a **Save as …** item per format ("Save as JSON", "Save as Markdown", "Save as HTML report") and a **Copy as …** item per format marked `copyable` ("Copy as Markdown"; JSON and HTML are not offered on the clipboard). The HTML report is one self-contained page with the run's charts, for a person to open or print; the engine writes it from the whole series whatever the request says, and it is the one format the MCP `export_run_report` tool does not offer (`mcp: false`). A copy goes through `useCopy` once the engine has answered, so "Markdown report copied" appears only when the clipboard took the text and a refused write toasts `Couldn't copy: <reason>` instead; a save hands the engine's `text`, `fileName` and `mimeType` to `downloadTextFile`. **Include comparison with baseline** is a checkbox item, ticked by default and present only when `usePinnedBaseline` finds a pin other than this run; ticked, the export sends that run as `baseRunId`. A foot note under a `border-rule` divider (the content declares `bg-card surface-card`, `--popover` and `--card` being one colour) says what the file carries: the target URL, names and comments, no request or response data. A save asks `useRunReportExport` (`POST /export/run-report`, the series at its default, which the HTML report needs and reads in full regardless) and only once the engine answers hands its `text`, `fileName` and `mimeType` to `downloadTextFile` untouched, and only once the file is written (#3246) toasts `Exported <file>` (the name the user saved under, which the dialog may have changed from the engine's `fileName`, #3607), plus ` - N URL credentials left out` when `notes.urlCredentialsOmitted` is above zero; a cancelled save dialog toasts nothing and a failed write toasts `Couldn't save <file> - <reason>` (`saveFailedMessage`). A failure toasts `Couldn't export the run - <engine message>` and downloads nothing. The items are disabled while an export is in flight. The mounted menu also fills the palette's `exportRun` slot ([Command Registry](command-registry.md#command-registry-libcommands)).

**Compare any two runs** (#2164). The header's **Compare** action (beside the breadcrumb, drawn only for a run that has a `runIdentity`, a `requestId` or else the `collectionId` of a collection load run: a comparison needs one of them to find its sibling runs by) and the History row's **Compare with…** menu entry (`RunItem`, for a finished load run with a `runIdentity`, read off the row's `summary.scenario` for a collection run; it opens the run's tab with a `compare` `navIntent` in `tabs-store`, which `LoadTestDetail` takes) open `main/components/RunComparisonView.tsx` in place of the report's tabs. It is in-pane state of `LoadTestDetail`, not a tab type, so Back to report returns to the report. The view diffs the open run (the target) against a run chosen in a `Select` (the base): `useRequestRunsQuery` lists the request's load runs (`GET /runs?requestId=&type=load`, or `collectionId=` for a collection load run), and `comparableRuns` keeps the completed and stopped ones other than the open run, adding the pinned baseline when it is older than the page. The default is the pinned baseline (`useBaselineRunQuery`) when it differs from the open run, else the newest other run. Option labels are the start time, the status and, for the pin, "Baseline", so two runs of one request tell apart. Under the comparability warnings it draws one table of **every** `compareReports` row (P50 to max latency, throughput and response rate - both labelled "(whole run, drain included)", which the engine's export copies, #2882 - error rate, total requests) and one of the status-code merge, a code only one run saw counting zero on the other side; the change column is coloured by `MetricDelta.direction` like the strip, and a status-code count change is neutral, since counts follow how long a run ran. Beside the status codes a third table, **Error classes** (`ErrorClassTable`, #3828), lists the `transport`, `protocol` and `tool` counts of both runs in that order with the same columns; `compareReports` gives `errorClasses` only when **both** runs recorded `summary.errorClasses`, so a baseline stored before the engine counted them draws no table rather than a column of zeros that reads as a regression, and `protocolCodes` is not compared. The strip and the view share `run-comparison-parts.tsx` (`DeltaCell`, `DeltaChange`, `ComparabilityWarnings`) and `run-comparison-format.ts` (`METRIC_LABELS`, `formatValue`), so a fix to a unit, a tone or a warning lands on both. A run flagged `summary.summaryMissing` (no counts, no latency) or `summary.partial` (no latency) reads as unrecorded on its own side only (#2904): `compareReports` nulls the figures it did not record, so that run's cell reads "not recorded" (`NOT_RECORDED`) and the change cell "-", whether it is the compared run or the open one, and the other run's figures are still shown; the view reads the flags nowhere itself. A chosen run deleted since the list loaded shows "This run no longer exists" with the picker still open; a request with no other finished run shows an empty state.

**The request across runs** (#2165). The Performance tab ends with `main/components/RunTrend.tsx`, three small charts - p95 latency, throughput, error rate - with one point per run of the open run's request (or collection), so "is this request getting slower" reads as a line, not as ten rows to compare by eye. It is mounted by `LoadTestDetail` beside `PerformanceTab` (the tab is a view of one report; this reads the request's other runs), and it is built from the runs list's `resultSummary` (#2130) through `useRequestRunsQuery`, the query the compare picker shares: no report is fetched per run. `buildRunTrend` (`run-trend.ts`) keeps the load runs that have a summary and ended (completed, failed or stopped), takes the newest `RUN_TREND_LIMIT` (20) and orders them oldest first. **Stopped runs are included, not dropped**: a run the user ended on purpose is often the latest state of a request they stop routinely. Each is marked with a dashed rule on the charts and "stopped" in the hover heading, and the card says so, because a shorter window averages differently. The open run carries a "This run" rule, and the card says so when it is older than the plotted window. A run that did not record a figure is a gap, never a zero; a chart with fewer than two recorded runs is left out. The component renders **nothing** for a run with no `runIdentity` (an unsaved request's) and until two runs have a summary: one point is not a trend. A failed list fetch draws an inline `ErrorState` with Try again. The x axis is the run's position, not time (runs are minutes or days apart); the hover heading is the start time through `formatInstant`. The wrappers (`RunP95TrendChart`, `RunThroughputTrendChart`, `RunErrorRateTrendChart`) live beside the other charts in `modules/dashboard/components/charts/uplot/RunTrendCharts.tsx` and use the same role per metric as the per-run charts (warning, categorical, destructive).

`ScenarioRunView.tsx` is the collection-run tab: the sequence, step by step, plus a four-number summary. It is deliberately **not** `LoadTestDetail` - a scenario run's `results[]` are step executions of *different* requests, so the load report's percentiles and status distribution would describe a sequence as though it were one request repeated. When the finished report's `summary.httpVersionDowngraded` is above zero, the header also carries the `NotNegotiated` warning (exported from `RunConfigSummary.tsx`, labelled "HTTP/2 not negotiated") with the count in its hover; 0 and absent draw nothing (#3262). Above the step list it draws `ThresholdVerdict` ("Pass/fail budgets", with the stopped-run note) from the report's `thresholdValidation`, so the missed budget that marks the run's list row failed is named where the run is read (#3539); a run with no budgets, or a report still in flight, draws no card. The run's terminal notification names it too, after the step counts ("12 passed, 0 failed. 1 of 2 budgets missed: p99", in `stepOutcomeLine`), so `ScenarioRunService` posts it once the stored report is read rather than on the stream's last frame, and with the counts alone when that read fails.

Its list has two sources and `scenario-steps.ts` collapses both to one `ScenarioStepRow`:

| Source | Carries | When |
|---|---|---|
| `step` SSE events (`services/sse-client.ts` → `scenario-run-service.ts` → `stores/scenario-run-store.ts`) | Identity - including the `requestId` the step ran (issue #831) - outcome, status code, latency. **No exchange.** | While the run streams |
| `RunReport.results[]`, each with the step identity the engine stamps onto its trace | The stored design-mode trace, so the row expands into a response | Once the run is over |

Stored rows win the moment there are any, which is also what makes a re-opened tab honest: a completed run has no live steps and reads entirely from storage. `ScenarioRunService` refetches the report on `complete`, which is the changeover.

The header names the data file the run's rows came from (issue #2051), from the snapshot's manifest, followed by `(numbers read as numbers)` when the run cast them (issue #2540, `dataFileDisplayName` in `lib/run-data-file.ts`, which every surface naming a run's file shares), and appends `(file changed since this run)`, `(number reading changed since this run)` or `(file no longer at that path)` from the status `hooks/useDataFileStatus.ts` returns (`changed`, `readingChanged`, `unchanged`, `missing` or `unknown`). It asks the main process for the remembered file's digest (`dataFile:hash`, on mount and on window focus) and compares the run's `dataFileHash` with it (the same hash with a different `dataFileCastNumbers` against the binding's `castNumbers`, each off when absent, is `readingChanged`; a different hash is `changed` whatever the reading), or with the hash the app last recorded when there is no hash bridge. The reply is `{ status: "found", hash }` or `{ status: "missing" }` (issue #2057): "gone" rides the reply because an error crossing IPC keeps only its message. `missing` needs nothing from the run, so a run recorded before hashes still reports a moved file; a browser build, with no bridge, can never say it. Every other answer - a request the main process refused, a hash still in flight, a run recorded before hashes (for the changed and reading comparisons) - is `unknown` and shows no suffix. `lib/run-data-file.ts` holds the reads of the name/hash pair out of every stored shape and the one classification rule (`classifyDataFile`).

Three rules the list holds, each pinned by a mutation-checked test:

- **Rows key on `(iteration, stepIndex)`, never arrival order.** The SSE ring replays from `Last-Event-ID` on reconnect, so a client that resumed mid-run receives events it has already rendered; appending would double every row it re-saw. A malformed `step` payload is dropped by `parseStepEvent` rather than defaulted, because a defaulted `0:0` would *collide* with the real first step.
- **`skipped` is never `passed`.** It has its own count and its own row treatment (`SampledExchange`'s `state` prop, below). Nothing produces `skipped` until flow control lands, so it is built to render correctly before it can occur.
- **`stopped` is no failure** (#3397). A step a Stop or an engine shutdown cut short ends the run, and the engine counts it apart from `failed` and `errored`. Its row wears the Stopped glyph the run's own status uses (`SampledExchange`'s `stopped` state, read from `RUN_STATUS`) and a `stopped` chip, draws no `ERR` badge or time for the cancelled send, and leaves its stored "Request cancelled" out of the expansion's red Error block. The count chip is drawn only for a run that has one (or while it is the active filter), and `outcomeCountsFromReport` reads a summary stored before the field as `0` rather than as unreadable. The completion notification names it ("2 passed, 0 failed, 1 stopped").
- **Thinned results say so.** A run that filled `maxScenarioStoredSteps` reports fewer rows than it ran, with every non-passing step among the ones kept - so a non-zero `stepsDropped` means *successes* are missing. `ScenarioRunView` discloses the three numbers rather than letting `results[]` read as the whole run.
- **The chips count the run, not the rows** (issue #726). `outcomeCountsFromReport` reads `report.scenario.passed/failed/skipped/errored/stopped` - the engine's exact whole-run totals - and the step list's own summary is only the fallback for a live run whose report has not landed yet. Counting rows would undercount `passed` on any thinned run, since thinning drops passes alone: a 6,000-step run keeping 5,000 rows read "4,990 passed" beside a header claiming 6,000 steps, so the chip silently changed meaning with run size. The stored-row count stays the list's own disclosure line above.

- **The header says where a run is while it runs and what it did once it has** (#2824). While the run is live, `liveRunProgressText` (`scenario-run-header.ts`) reads the `plan` frame from the store and prints "Iteration 3 of 40 - 17 of 240 steps": the iteration is the one the latest `step` event reports (1 before any step lands, clamped to the plan), not `stepsRun / stepsPerIteration`, which drifts as soon as an errored step ends an iteration early or `setNextRequest` walks one in a different number of steps. A run past its plan drops the denominator ("250 steps"), and a run whose frame never arrived says only "Running". Once it has ended, `finishedRunFiguresText` prints the report's `summary` beside the iteration tally - "4.20s - 83 requests sent - 16.9% error rate" - leaving the rate out of a run in which no step sent and saying "Duration, requests sent and error rate: not recorded" for a summary the engine did not record (`summaryMissing`, #2895) rather than printing zeros. Never both: the figures wait for the run to end.
- **What errors cost is said, not inferred** (issue #2526). A script error no longer ends a collection run's iteration unless the run was started with `stopOnError`, so a run can do less than its plan only because a runner refusal ended an iteration (or `stopOnError` was set). `stepsNotRunText` (`scenario-steps.ts`) words that count once for both readers: the header prints "N steps did not run" in a muted sibling span beside the iteration tally (the report's `scenario.stepsNotRun`, the run-wide sum; the tally sentence keeps its own node), and the one step whose error ended its iteration prints "Ended this iteration: N steps did not run" in its expansion, from `stepsNotRun` on the `step` frame (`parseStepEvent`) and on the stored trace (`stepRowFromResult`) - the two layers a `ScenarioStepRow` is built from, so the line does not vanish when the stored row replaces the live one. All of them are absent rather than `0` from the engine, and a report from before the field has none, so neither line renders for 0 or `undefined`.

A live run can be **stopped** from this tab (`StopRunButton`, below), which matters most for a data-driven run of hundreds of iterations. The control is shown while `isStreaming || run.status is running|pending` - two signals rather than one, because a tab reopened onto a run that is still executing (after a relaunch, or from History) has no stream at all, and is exactly the case where waiting the run out hurts most. It calls `POST /runs/:id/stop`, which needs nothing new engine-side: the scenario runner already checks `should_stop` per *step*, settles the run to `Stopped` and closes the SSE topic, so the streaming tab flips to the stored rows through the same `complete` a normal finish takes. `useStopRun` also invalidates the run and its report itself, because a tab that is not the streaming one never receives that event.

`components/ScenarioStepCard.tsx` renders one step on the shared `SampledExchange`, restoring the response through `restore-response.ts` - the same path a design run's response pane uses, not a second reading of `trace_data`. It is `memo`ized (issue #1153): up to 200 are mounted while a run streams several commits a second, and all but the newest are rendering what they rendered before. That only bites because the list hands down props that hold their identity - one `onToggle` for every row rather than an arrow per row, which is why the card is told *which* step it is instead of the handler closing over it. `SampledExchange` gained an optional `state` (`success | error | slow | skipped`) and a `title` slot for this: its state is otherwise derived from the status code, which would read a `failed` assertion over a `200` as a success and a `skipped` step as a connection failure. Status code and latency are optional on `SampledExchange` and the row omits the badge and the time when they are absent: `ScenarioStepCard` passes neither for a `skipped` step, which sent nothing (#2824), so the stored row's status `0` and latency `0` do not draw an "ERR" badge and "0ms"; the grey `skipped` chip stays. A step whose extractors found nothing carries the shared `ExtractorMisses` in its row beside the tests chip, from `extractorMisses` on the `step` frame (`parseStepEvent`) and on the stored trace (`stepRowFromResult`), so it shows live and after the run alike (issue #3053). Beside it sits the shared `UnresolvedTokens` (`unit="names"`, "N unresolved variables"), from `unresolvedTokens` on the same two paths: the distinct `{{names}}` that step sent unresolved, absent at none (issue #3269). A step whose response is flagged `httpVersionDowngraded` shows the shared `HttpVersionDowngradeNote` above its response viewer (#3262). The response's `warnings` (#3307) draw above it too, through the shared `ExchangeWarnings`, on a step that never got a response as well → `ScenarioStepCard.warnings.test.tsx`. The step card does not draw the exchange's `authNotice`. A step that waited on its script says so in the expansion's timing breakdown: `trace.scriptMs` goes to `SampledExchange`'s `scriptMs` and draws a "Scripts" tile, a reported `0` included (#3739) → `ScenarioStepCard.script-time.test.tsx`.

**A step is no longer a dead end** (issue #730). The engine has always stamped `requestId` onto a step's trace and no renderer read it, so reproducing "iteration 501 - row 501 failed" meant hunting the request in the tree by name, and then finding that the send-with-row picker lists the first 20 rows, which do not include row 501. The card now carries an action beside its summary: **Repro row N** opens that request through `tabs-store`'s `openRequestWithDataRow`, which selects the row that iteration bound and opens the picker on it - so the repro is that click and the row's. A step of a run that bound no data set says **Open request** and carries no row, because a collection with no data file has none to select. A **live** row carries the action too (issue #831): the `step` frame names the request, so a step that has just failed on iteration 12 of 500 is one click from the request that sent it rather than a link that arrives when the run ends - which is the moment it is worth least. The expansion is still what waits for the stored row; the id is one constant-size field, which is what lets the frame carry it where the assertion list stays stored. A row that cannot name a request offers nothing at all rather than a disabled control: a step whose plan entry has no stored request behind it, and a row stored before the runner stamped one. `SampledExchange` gained an `actions` slot for this, rendered *outside* the summary button - the summary is one `<button>`, and a control nested in it would be invalid markup that fires the toggle on its way out.

**The list is bounded in cost, not in content** (issue #730). `maxScenarioStoredSteps` is 5,000, so mounting every row as a card is not an option. The count chips (four, and a fifth `stopped` when a Stop cut a step short) are buttons that filter the list to one outcome - the reader who has just read "11 failed" wants those eleven, and the number is where they read it - and the rows arrive through `useGrowingWindow`, the same growing list the response pane's console output uses (held here by `useFilteredSteps`, see below), each card marked `skip-offscreen` so the ones scrolled past cost no layout. No virtualiser, for the reason that hook records: step cards vary in height, and variable-height windowing means a scroll map to maintain forever. Filtering to an outcome whose *stored* rows are all gone (thinning drops passes) says so in its empty state rather than reading as a contradiction with the chip, which counts the run.

**A search beside the chips, matching the step name** (issue #832). The outcome filter cannot answer "show me every execution of `POST /checkout`": a 5,000-step run of a 40-request collection is 40 names repeated 125 times, and the failures a chip narrows to are spread across a dozen different steps. The box matches the **step name**, stated on the field itself (`Search step names`) rather than left to be guessed - it is the one field both sources carry, where a row's URL lives in its stored trace and a live row has none, so matching that would make the same box search less while a run streams than after it ends. The two controls are **one predicate** (`filterSteps` in `scenario-steps.ts`), so narrowing by both is the useful case rather than a special one, and there is a single empty state (`emptyStepListReason`) that names whichever combination emptied the list - the chip and the search are cleared in different places, and a reader told "no failed steps" over a list their search emptied clears the wrong control. The outcome half of that message keeps the thinning disclosure it always carried. The growing window is keyed on *which* list is shown - the run, the pressed chip and the search text - so a narrowed list starts at its own top while a live run's list, which is the same list getting longer, keeps the window a reader has scrolled open (issue #1153). `useFilteredSteps` owns that window rather than the view holding it beside the hook (issue #1297): the window is sized against the match count and the count is what says how far the window has to be produced, so keeping them apart would be two caches over the same rows with the same three ways to go stale - the filter, the list's identity, a replay - and nothing to fail loudly if they drifted. **A live run runs that predicate over the batch that just arrived, not over the run, and builds only the rows it shows** (issues #1205, #1297): `useFilteredSteps` counts what the batch added and extends the window from the source row it was last produced through, so pressing a chip or typing in the box does not cost a pass over every row the run has produced on every flush, and the cost of a narrowed list does not fall on the reader who narrowed it. Once the window is full the extension stops for good and the rows are handed back by identity, so a long run streaming past a filled window copies nothing per flush; a grown window resumes from where it stopped rather than matching the list again. What tells it the list only grew is the store's `appendEpoch`, since every commit hands the view a new array; anything else - a replay that replaced a row, a new run, the changeover to the report's stored rows - rebuilds. The rows, their order, the "showing X of Y" total and every empty state are what `filterSteps` produces for the same inputs, proven against it as an oracle over randomized streams at more than one window size, and `stepMatcher` is the one definition of the predicate that both the oracle and the window read.

For a step of a **spec-bound** collection the row also carries the shared `ValidationChip` beside its outcome chip, and the expansion renders the same `SchemaValidation` section the response pane's Tests tab does (issue #681) - both shared rather than re-laid-out here, so the three-state wording and the unevaluated-keyword disclosure cannot drift between the two surfaces. It sits *beside* the outcome and never inside it: with `failOnSchemaError` off, a step can pass every assertion while its response contradicts the contract, and those are two facts. A step of an unbound collection, or one that sent nothing, renders neither - `step.validation` is absent, and absent is never drawn as "checked, and fine".

The row carries its **assertions** the same way (issue #724): the shared `TestsChip` beside the verdict, and the expansion renders the response pane's own `TestResults` list from the stored trace's `scripts` node - the run computed every `pm.test` result and kept only a one-line summary of it, so a step's detail showed nothing where the same request's single Send showed a full Tests tab. The tally is the only half a *live* step has, because a collection run is answered `202` and its steps are viewed entirely through their stored rows; the list arrives when the run ends. The stored list wins the moment there is one, tallied by `tallyTests` in `scenario-steps.ts`, so a row does not change its numbers when its stored copy lands. Both count both scripts' assertions (issue #810) - a failing `pm.test` fails its step whichever script made it - and the list is grouped under the script's name, so an assertion made before the request went out does not read as one about the response. Every level's results are listed (issue #2522): an assertion from a collection or a folder carries its level beside its name, and the Elements list prints an errored element's message inline - a collection script that threw reads "Collection pre-request script failed - ..." on its row, not a bare chip. The step's console lines, its script requests (issue #3633) and its pre and post script errors (issue #3126) are drawn under the Tests, from the same restored response, by the response pane's own `ConsoleOutput` inside a `max-h-[400px]` scroll box (the pane gives it a flex-1 parent; the expansion has no definite height). The block renders only when there is a log, a script request or a script error, so a scriptless step or a live row adds none.

The entry point is `modules/collections/RunCollectionDialog.tsx`, opened from a collection row's ⋯ menu. Seven options (and two that appear conditionally: the stream caps, only when a step streams, #3235, and, in load mode only, **Wait out Retry-After** with its cap, #3799 - `RetryAfterFields`, held in the dialog's profile state and reset on every open, sent top-level as `retryAfterBackoff` and `retryAfterMaxMs` only while on) - Recursive, Iterations (replaced by the load profile once Load test is on), a data file, Load test, Fail steps on schema errors (issue #720, the renderer's only writer of the engine's `failOnSchemaError` - MCP's `run_collection` is the other, issue #766 - hidden in load mode because only the design-mode runner can honour it), Stop the iteration on a script error (issue #2526, the same shape for the engine's `stopOnError`: off by default, so a script error is reported on its step and the iteration moves on as in Postman; top-level, sent only when on, hidden in load mode; MCP's `run_collection` is the other writer), and Pass/fail budgets - because the scenario **is** the folder: the sequence is the tree's own ordering, and a step list authored here would be a second source of truth for it. Invalid iterations are refused in the dialog; the engine's own rejection (which names the step that would not compose) is shown in place rather than as a toast that scrolls away. While any other run is live, load or sequence (the single-run gate, #3381), Run is disabled under a blocking callout that names the live run and offers View run and Stop (`useStopLiveRun`); a failed Stop is a toast with Try again and Run stays disabled.

**OAuth 2.0 token guard** (#3199): a duration-based load run renders `OAuth2LoadTestGuard` above Run once per *distinct* OAuth 2.0 token the run sends, because the engine keeps one credential (one mid-run refresh) per token cache key however many steps send it. The hook-free `modules/collections/runOAuth2Configs.ts` (`distinctRunOAuth2Configs`, over `useRunOAuth2Configs.ts`) walks the stored requests the run sends (the folder, and its subtree under Recursive), takes each one's effective OAuth 2.0 config through `effectiveOAuth2Config` (an `inherit` walks the collection chain; a No Auth ancestor stops it), resolves its `{{variables}}` against that request's own collection chain, globals and the active environment, and keeps the first config per `computeOAuth2CacheKey`, or per `oauth2SignInKey` for a config awaiting discovery (#3766), whose guard says to sign in first. The dialog holds the gated keys as a set and disables Run (with a `DisabledHint`, "The OAuth 2.0 token check above hasn't passed.", the sentence the request's load dialog uses) while any shown guard gates; a guard that leaves (Load test off, a different folder set) stops counting. Nothing renders for a design-mode run, a Fixed passes run (no duration to judge) or a run with no OAuth 2.0 request. The per-request `OAuth2DeferredNote` is not drawn: it asks `/compose` about one request, and a run has many.

**Pass/fail budgets** (issue #1564) reuses `LoadTestConfigDialog`'s own `budgets.ts` and [`NumberField`](shared-fields.md#number-field-componentssharednumberfieldtsx) rather than a second copy - the engine judges a collection run against `thresholds` exactly as it does a load run. Unlike Timers/Scripts below, it is **not** gated by Load test: it applies to a design-mode run and a load run of the same folder alike, so the disclosure always renders. An out-of-range budget blocks Run with the same named message `LoadTestConfigDialog` shows. Its disclosure is `LoadTestConfigDialog`'s own `DisclosureCard` (not a hand-rolled copy of the same `Collapsible` chrome, #2194), so the closed card shows the same budget count and the explainer is the shared `BUDGETS_EXPLAINER`; nothing is seeded or remembered here, so it has no carried-over notice and its p99 field carries no SLO hint.

The **Custom metric budgets** rows inside it (issue #1579, the same `CustomBudgetRows.tsx` the load dialog mounts) follow the same rule as the fixed budgets above, not gated by Load test: `custom.<name>.<stat>` is judged for a design-mode collection run exactly as it is for a load run (`docs/engine/api-reference/load-runs.md`, the thresholds block), so the rows always render and reach the payload regardless of the switch. They get no "Copy for agent" button here: `CustomBudgetRows`' `referenceOwner` names a saved request, and a collection run has none.

**Load test** (issue #357) is the same plan on a different executor: the payload gains a load `mode`, and its presence is exactly what the engine reads to choose one, so a design-mode payload keeps its meaning by carrying no mode at all. It lives here rather than in the request builder's `LoadTestConfigDialog` because that dialog's target is the request that is open, and a scenario's target is a folder - picked here, by the tree that already owns the choice. Turning it on swaps the design-mode Iterations field for a **load profile**: the request dialog's own `ProfilePicker` and `ProfileFields` narrowed to the three modes a scenario accepts (`SCENARIO_LOAD_MODES` in `LoadTestConfigDialog/scenarioProfile.ts`) - Constant virtual users, **Fixed passes** and Ramp-up. Constant RPS and Capacity discovery are not offered because the engine answers a scenario with either a `400`. The picker takes optional `modes` and a per-mode `copy` override, and `ProfileFields` an `iterationsLabel`, so Fixed request count reads "Fixed passes" / "Passes through the sequence" here (the label is `COLLECTION_ITERATIONS_LABEL`, written once in `constants/load-test-modes.ts` and not in `LOAD_TEST_MODES`, which keeps the single-request name). A collection run's stored mode reads the same everywhere else: `loadTestModeLabel(mode, "collection")` - the live header (`DashboardHeader`, from its `collectionName`), the History row (`RunItem`, from `summary.scenario`), the context bar's run config (`RunConfigSection`, from the snapshot's manifest) and the report's `RunConfigSummary` (`isCollectionRun`) all pass the kind, so none of the four re-decides it (#3570); `summarise` takes a `"sequence"` subject so the line under the fields counts passes ("Runs the sequence N times across M virtual users, then stops.") and never calls one a request. The profile starts from the dialog's own numbers (10 virtual users, 30 s, 100 passes, a 10 s ramp) and neither reads nor writes the request dialog's saved config: that memo describes one request, and a sequence multiplies its load. The per-mode field selection is `profileParams` (`profile.ts`), shared with `buildLoadTestConfig`; `scenarioLoadFields` spells the same selection the way `StartScenarioRunRequest` reads it (camelCase, `"Ns"` durations, `iterations` omitting `duration`), and that one object is both the payload's load half and the seed for `useDashboardStore.startRun`, so the dashboard shows the mode and ramp the run was started with. Run stays disabled with a named message for a value outside the Settings ceilings (`resolveLoadTestLimits`) or a ramp that does not fit its duration (`scenarioProfileError`, reusing `rangeError` / `validateRampDuration` / `validateStartConcurrency`), so an over-ceiling count is refused before the request. `rangeError` is the same rule the request dialog's `validateLoadTestDraft` applies to its own fields (#3542), so both dialogs refuse a value on one wording. The line under the title follows the switch and the mode ("repeating for the duration", or "taking passes until the total is reached" for Fixed passes). It also swaps what happens after the `202`: a load run publishes `metrics` ticks and no `step` events, so it attaches `loadTestService` and opens the **dashboard**, where a design-mode run attaches `scenarioRunService` and opens the runner tab. Attaching the wrong one is not a degraded view, it is a permanently empty one.

**Stream caps** (issue #3235): the engine runs a step whose stored request has `stream` set as a stream, in a design run and a load run alike, so the dialog asks whether any request it sends does (`useFullCollectionRequests` over the audited collections, the same query `useColumnAudit` reads, so TanStack dedupes it; the whole subtree under Recursive). When one does, the same two fields the single-request load dialog shows (`StreamCapFields.tsx`: **Stop each stream after**, `profile.streamDuration`, and **Or after this many events**, `profile.streamMaxEvents`) appear - inside `ProfileFields` with Load test on, and on their own under the switches with it off - and Run sends them top-level as `maxStreamDurationMs` (seconds converted to ms by `scenarioStreamCaps`) and `maxStreamEvents`. The payload never carries `stream`: it is a `400` on a collection run, since the flag belongs to each stored request. With no streaming step the fields are hidden, nothing is sent and `scenarioStreamCapError` is not asked, so a cap typed while a nested streaming collection was included (and left in the profile when Include nested collections went off) neither blocks Run nor reaches the engine. The same `anyStreams` decides the stream budgets (#3234): the engine judges a collection run's `stream` section in a design run and a load run alike, so with a streaming step the Pass/fail budgets card offers both (`budgetFieldsFor(anyStreams)`) with `STREAM_LATENCY_NOTE` under the latency fields, and `budgetError`, `summariseBudgets` and `buildThresholds` read the same flag. A stream budget typed while a nested streaming collection was included is neither checked, counted on the closed card nor sent once Include nested collections goes off, because a stream budget on a run without a stream section is reported not evaluated, and so missed. The dialog restores no budget memo, so `carriedForRun` has nothing to do here.

The dialog also gains **Timers** (`asConfigured` | `off`) and, in Load mode only, **Scripts** (`asMarked` | `allInline` | `allDeferred`), issue #1552 - the app-side twin of the `elements` pipeline override issue #1495 defined engine-side, documented in full at [api-reference/load-runs.md](../../engine/api-reference/load-runs.md#the-elements-block-element-pipeline-override). Both are sent as a top-level `elements` object beside `mode`/`scenario`, never inside the `scenario` block itself, and only when changed from the engine's own default - the same "absent means the default" rule `failOnSchemaError` follows. `Timers` is wired to `timer.pacing`/`timer.think` end to end and applies to a design-mode run exactly as it does a load run, so it is offered regardless of Load test; `Scripts` decides whether a `script.*` element runs inline on the event-loop worker or stays deferred to the post-run replay, and has no effect on a design-mode run (which already runs every script inline), which is why that one control only appears once Load test is on. `LoadTestConfigDialog`'s single-request path gained the same `elements` attachment point in issue #1594 - its own step-level elements ride under `requestElements` instead, a distinct key from this run-level override - and mirrors this dialog's own **Scripts** control (`asMarked` | `allInline` | `allDeferred`), sent the same way, only when changed from the default. It is what makes the dialog's own pre-request-script warning conditional: `allInline` runs every `script.pre` under load and `asMarked` runs the ones marked `config.inline`, so the warning hides at `allInline`, and at `asMarked` it covers only an unmarked script (`allDeferred` skips a marked one too, so the warning returns there; the engine's `script_element_runs_inline`). The post-request sampling notice hides at the same setting, for the mirror reason: `allInline` runs a `script.post` on every response instead of replaying it on a sample. It offers no **Timers** twin, but not because the engine ignores the override there - `elements.timers` applies to a single target's own `timer.think` exactly the way it does to a scenario step's - the dialog simply has no timer control of its own on this path to pair it with yet.

`modules/collections/DataFilePicker.tsx` is the data-file half (issue #402). It reads a CSV/TSV/JSON/JSONL file through a hidden `<input type="file">` + `FileReader` - the `ImportModal` precedent, deliberately no Electron dialog IPC - decodes its **bytes** (`decodeDataFile`, so a non-UTF-8 export is named rather than parsed into question marks), parses it with `services/data-files/`, and previews the first ten rows in the `ui/table.tsx` grid. The preview scrolls inside its own box and says which rows are in it in either direction - "the first 10 of 24" for a long file, "all 8 rows" for a short one - because the box can cut a file off without looking cut off, and on overlay-scrollbar platforms it draws no scrollbar until someone scrolls it. What keeps that box from widening its host instead of scrolling is the host's, not the picker's: a width-capped grid surface has to clamp its own track (issue #701, `DialogContent`'s `grid-cols-1`; see [design-system/index.md](../../design-system/index.md)), and the Data tab's flex column already hands its children a definite width. Two things it exists to say **before** the run rather than after: everything the engine would reject (a ragged row, a duplicated column, a non-object, a line that will not parse, a set over `maxScenarioDataRows` or `maxScenarioDataBytes`) is refused here with the row, line or setting named - the two caps read live through `useDataFileLimits` rather than restated, so raising one engine-side is enough, and the **resolved iteration count** is stated, because an explicit `iterations` wins over the row count - a 500-row file with Iterations left at 1 runs once. Picking a file blanks a **pristine** `1` so the field shows what will happen - pristine and not merely equal to `1`, because a deliberately typed `1` reads the same and clearing it would turn one pass into a full pass per row, and `iterations` is then omitted from the payload entirely: the engine owns "absent means one pass per row", and a client computing the row count itself would be a second copy of that rule. The previewed rows and the sent rows are one array; the parent holds the single `ParsedDataFile`. The picker also hashes the same raw bytes (`sha256Hex`, the digest the main process takes for a re-read), and both dialogs send the file's name and that hash beside the rows as `dataFileName` / `dataFileHash` (issue #2051) - never its path. In both run dialogs a pick also declares the contract from the file's columns and Remove clears it (issue #2050), through `hooks/useDataContractWriter.ts`, the writer the Data tab uses; the rows themselves are held for the run request and no longer - neither side stores the set, and the declare-mode label says the contract records their shape rather than their values, since the values a run binds do persist in its step traces ([What is stored](../data-driven-runs.md#what-is-stored), issue #731). For a CSV or TSV the preview card carries a **Read numbers as numbers** checkbox (issue #2540). A toggle re-parses the selection's own decoded `text`, which `SelectedDataFile` holds beside the rows in memory only, so a file with no path re-parses too and the preview never reads bytes other than the ones it showed. It reaches the host through `onCastNumbersChange`, never `onSelect`, because every host treats a pick as a new file and declares it; the host keeps the setting on the collection's binding through `useDataContractWriter`'s `rememberReading`, and a pick starts it off. The selection's `parsed.castNumbers` is the setting in force. The hidden input is reset after every pick, accepted or refused, not only on Remove: a refused file leaves "Choose file" showing over an input still holding it, and the browser fires no change event for an identical selection, so the same file could not be chosen again after fixing it or raising a cap (issue #2825). The user-facing file contract lives in [Data-Driven Runs](../data-driven-runs.md).

`CollectionDetail/DataTab.tsx` is the authoring-time half of the same file (issue #599, phase 1 of #598). It reuses the picker in `mode="declare"` - same parser, same refusals, no iteration arithmetic - and turns a picked file's columns into `collection.dataSchema` through `useUpdateCollectionMutation` - the pick is the save (issue #2043), and the picker's `onRemove` (Remove only, never a refused file's `onSelect(null)`) clears the contract; the mount re-read of the bound file is preview-only and never writes a contract. **Clear** sends `dataSchema: null` and `dataFile: null`, not `{}`: the engine reads absent as "keep", so a cleared contract is only expressible as a null that survives to the wire. What is stored splits by what it is true of: the **columns** are the same on every machine and ride the engine row through import and export; the file's **path** is true of one filesystem and rides the row too (`collection.dataFile`, written in the same update as the columns, #2765), so a backup keeps it while no export or import carries it; the **rows** are true of nobody and are stored nowhere at all. The tab shows the bound path under the declared file's name, and both struck through when the re-read fails - a moved file, one never granted, or a path restored from another machine. When both a contract and a file are in hand, `services/data-files/schema-diff.ts` renders the mismatch in both directions into the picker's warnings slot - shared with the run dialog, so the tab and the runner cannot describe the same file differently.

`CollectionDetail/SpecTab.tsx` is the same two-halves split one contract over (issue #638, phase 1b of #625). The **document** and the binding (`collection.openapi` -> the engine's `spec_documents`) are the same on every machine and ride the engine; a picked file's **path** is true of one filesystem and rides the row as `collection.specFile` (#2765), a path and a file name and no spec content at all, written after the bind lands and cleared with Unbind. The bound card shows that path as the document's source, struck through once the Sync section's check has failed to read it (SpecSync's `onFileRead`). A pick is bundled before anything reads it (issue #3032): `handleFile` and `handleFetch` run `bundleSpecText` (`services/openapi/spec-refetch.ts`, the bundler Sync's `refetchSpec` also uses) so what is described, matched and bound is the bundled text, and unfollowed references and fetched files are shown by `RefDisclosure.tsx` (shared with the Sync card) beside the summary. A bundle past the engine's cap is a blocking `pickError` with no pick. Binding a collection that was not imported from a spec goes through `POST /specs/describe` - which is what the engine reads out of the picked bytes: the dialect, the title, the identities it declares and the base paths of its server URLs, so the tab parses no document at all (issue #869 retired `services/openapi/spec-operations.ts` with the last parse) - and `POST /specs/match`, which pairs them (the tab relays `described.basePaths` into it, issue #3030, so the preview counts the literal-URL requests under a server's base path that the bind stamps) - the matcher moved into the engine in issue #761 so an agent over MCP can bind a collection the same way, and it reduces both sides to a path shape (origin, query and fragment dropped; `{{petId}}` and `{petId}` flattened alike) and refuses an ambiguous pair rather than guessing. `services/openapi/operation-match.ts` kept only that reduction, and it is gone with the sync diff (issue #854) - the export took the URL split with it when it moved engine-side (issue #855), and nothing here reduces a path shape any more. The bind itself is one call (`useBindSpecMutation` in `queries/specs.ts` -> `POST /specs/bind`, issue #862): the document, the binding and both halves of the stamping - what matched, and what the new document no longer accounts for - commit together, and the pairing is worked out engine-side from the bytes it stores. It was three ordered writes from the renderer until then, which is three places for a bind to stop and, in the clearing half, a list a caller could forget (issue #718). The user-facing contract lives in [OpenAPI Collections](../openapi.md).

`CollectionDetail/SpecSync.tsx` is the read half of keeping that binding in step (issue #654, phase 2b of #625), and its whole design follows from writing nothing: `services/openapi/spec-refetch.ts` re-reads the document from the URL the binding stored or, failing that, through the `specFile:read` gate the picked file's siblings already use (it reads only a document the user picked, dropped or opened, #2357, so a binding made before that rule shows "pick the file again" until it is picked once more) - the document naming *itself* as the file beside itself, rather than a second gated channel repeating the extension allowlist and the byte cap - and runs it through `bundleExternalRefs`, because the stored document is the bundled one and an unbundled comparison would report every external `$ref` as a change forever. "Up to date" is **byte equality against the stored document**, not a renderer-side SHA-256: the engine hashes what it stores (`spec_content_hash`), and a second hasher here could only drift. `POST /specs/diff` then produces the four buckets - added, declined, removed, changed (issue #854 moved the comparison engine-side, where the reader that says what a document produces already lives) - it follows an operation by `operationId` first and path shape second, so a path moved under a stable id and an id moved under a stable path both stay one operation while both-moved is disclosed as a removal plus an addition, and it flags a field as **user-touched** three-way (what the request holds is neither the new document's value nor the bound one's), which is the flag the apply half may not overwrite silently. The section sends the collection and the re-fetched bytes and nothing else: the engine walks the subtree itself and reads the bound document from the binding, which is also why "up to date" is now that route's `identical` rather than a comparison made here.

The apply half (issue #655, phase 2c) keeps the same split: `services/openapi/spec-apply.ts` is a pure module that turns a diff plus a set of ticks into the `POST /specs/sync` body. The two rules a user's work depends on - a field marked user-touched is never written unless it was ticked, and a deletion is never a default - moved engine-side in issue #871 (`core::safe_spec_apply`), reported per entry on the diff as `safe` / `safeFields` and applied for a caller that states no rows by `POST /specs/sync`'s `policy: "safe"`; `defaultSelection` reads those marks rather than deriving them, so an agent's `sync_spec` and an untouched Apply here write the same rows. It reuses `services/importers/request-payload.ts` for the draft-to-payload mapping, shared with the import orchestrator so a field added for one write path cannot go missing on the other, and files an added operation in the tag folder an import would have used (matched by name, created once per tag). A **declined** operation - one whose request the user deleted (#3031) - is listed apart from `added`, never pre-ticked whatever its `safe` says (`SpecApplySelection.declined` starts empty), and a tick is an ordinary `create[]` row carrying its `specOperation`, which is what makes the engine forget the record. The write itself is one call and one engine transaction (`useSyncSpecMutation`): the document, the moved binding and every created, updated and deleted request land together or not at all, and the engine - not the payload - is what keeps a user-saved example out of a refresh and a request outside the bound subtree out of reach.

`modules/collections/ExportSpecDialog.tsx` is the way back out (issue #630, phase 5 of #625), opened from a collection row's ⋯ menu and from the Spec tab - one dialog, so the two entry points cannot describe the same export differently. **The assembly is the engine's** (`POST /specs/export`, issue #855): it reads the subtree, each request's examples and the bound document itself, and answers with the finished text, a file name and the notes. Keeping it in the engine keeps the parsing and patching of a large spec off the renderer's main thread. What is left here is the format choice, the bound collection's mode choice (**Changes: Values only**, the default, or **All edits**, which writes every edit into the document - a free-form collection has no contract to keep and is not asked, read off `collection.openapi.specId`, the same fact the engine picks the direction from), the summary and the download; `useSpecExportQuery` keys the read by format and mode so toggling back is free, and by the moment the dialog mounted so reopening it asks again. Because format is part of the key, switching it is a cache miss - so the read carries `placeholderData` (issue #1311) and the summary card stays on screen while the other serialization assembles, with a spinner beside the toggle and Copy and Download disabled for that one round trip, rather than the card being torn down for a one-line spinner and the dialog, which centres on itself, moving both of its edges twice. The first read has no previous answer to keep and holds the card's footprint instead, so the dialog opens at about the height it will keep.

Which of the two directions runs is not a setting but a fact about the collection, and the dialog says which before anything is written. A **bound** collection exports its own stored document, patched: operations nothing here claims are removed, request values become declared parameters' examples, stored examples become response examples where they are news to the document (one it already declares, or one the import sampled off a schema, is counted rather than written, #1442), and every member Vayu does not model - a `$ref` response among them - is carried through by simply not being visited. A **free-form** collection gets a skeleton - "a starting point" in the dialog's own words - which invents nothing: no schema that was not read off an example body, no `required` from a row's enabled toggle, no response for a status nobody saved. The summary lists only the counts a user can act on or would miss, and only when they are not zero (the requests-exported headline always), among them the credentials withheld in either mode - a `Values only` export counts them at the parameter they would have filled - and a closing line that bodies, examples and scripts are not checked for credentials and are written as they are; the engine's notes carry every count, and the rules behind them are `engine/include/vayu/core/openapi_export.hpp`. Delivery is `downloadTextFile` (`lib/download-text-file.ts`, the app's one file-to-disk path, shared with `ResponseActions` and the environment export), which in Electron goes through the `file:save` save-dialog IPC (`electron/save-file-ipc.ts`, #3246) and answers whether the file was written: the dialog closes once it is, stays open when the save dialog is cancelled, and shows a `Couldn't save the file` callout with the system's reason when the write fails. Outside Electron it is an `<a download>` click, which cannot report back and counts as saved. The user-facing contract lives in [OpenAPI Collections](../openapi.md).

`modules/collections/ExportPostmanDialog.tsx` is the other way out: the collection as a Postman Collection v2.1 document, opened from a collection row's ⋯ menu (**Export as Postman Collection**, beside the OpenAPI entry rather than in a submenu, because `RowAction` is one flat list both row menus draw) and from the Spec tab's Export menu. Built on `ExportSpecDialog`'s terms: the engine assembles it (`POST /export/postman`), the dialog is mounted only while open, delivery is the same `downloadTextFile` under the engine's `fileName`, closing only once the file is written, and `usePostmanExportQuery` (`queries/exports.ts`) keeps the previous answer on screen while the one toggle re-reads (issue #1311). That toggle is **Include credentials**, off by default: off writes auth secrets, secret variables and, by name, the credentials in headers, parameters, URLs, saved examples and cookies empty, and the summary counts them and says that bodies and scripts are not checked and are written as they are; on writes everything as stored, which is what Postman's own export does. The summary states requests and nested collections exported and lists every `notes.notCarried` entry with its count, in the engine's words, so nothing Postman has no place for is dropped without a line saying so.

`modules/collections/SpecReimportDialog.tsx` is the fork an import takes when the document is one a collection already binds (issue #680). `ImportModal` asks `services/openapi/bound-spec-match.ts` at Import time - matching `spec_documents.source_url` and the stored bytes, the two keys that catch a moved document and a re-picked file respectively - and this dialog names the collection, offers **Sync instead** (which opens that collection's Spec tab through `tabs-store`'s `spec` `navIntent`) and **Import anyway**, which does exactly what Import did before the check existed. A second copy of a spec is a real thing to want, so it is a fork and never a block; the Sync action sits on the row rather than in the footer, because a batch can carry more than one bound document and one footer button would have to guess which collection it meant.

`RunCollectionDialog` **pre-fills from that declaration** as part of mount, which is what keeps the dialog's mount-is-reset contract intact: if the collection that declared the contract has a `dataFile` binding (read by id from `data-file-store`, the store that mirrors the collections list) it re-reads it over the `dataFile:read` IPC (`electron/data-file.ts` - extension allowlist, the grant registry (only a file the user picked, dropped or opened is read, #2357) and the engine's fetched `maxScenarioDataBytes`), decodes and parses it with the same modules the picker uses, and diffs it against the declared columns. A file that has moved, or that was declared before grants existed, leaves the picker empty and a sentence saying so - a warning, never a blocker, because a run without a file is a legal run and re-picking is the whole remedy. The pre-fill is a read and declares nothing (its one write is the re-read file's hash on the binding, and only when it moved, issue #2051); a **pick** declares the contract from the picked file for the collection the run binds against, and Remove clears it (issue #2050, `hooks/useDataContractWriter.ts`, the Data tab's own writer). A declare that fails is a warning beside the picker and leaves the file selected and Run enabled. Beside the contract diff, the picker's warnings name any column the run's requests reference that the file does not carry (`hooks/useColumnAudit.ts` over the collection, and its whole subtree under Recursive).

The picker is told **which run it is for** (`loadTest`), because a row means something different in each and describing one of the two is being wrong about the other (issue #449). In design mode a row is an iteration and the file's length is the run's length. In load mode the rows are claimed from a cursor every virtual user shares, wrapping for as long as the duration lasts - so the row count says nothing about how long the run is, only that no two virtual users start on the same row while unclaimed rows remain (past the wrap they do share rows), and the resolved-iteration sentence is replaced rather than shown against a pass count a load run does not have.

`services/data-files/` is the parser: `tabular.ts` (a hand-rolled RFC 4180 tokenizer - quoted delimiters, embedded newlines, doubled quotes, CRLF - shared by CSV and TSV, which differ only in the delimiter; `parseDelimited` returns the text grid and `tokenizeDelimited` also returns which cells were quoted), `numeric-cell.ts` (the number cast) and `index.ts` (format detection by extension with a content sniff fallback, the header rules, the JSON/JSONL paths). CSV and TSV values are **strings by default**, so `007` survives; `parseDataFile(text, name, { castNumbers: true })` is the per-file opt-in that reads an unquoted integer or decimal cell as a number (a quoted cell, `1e3`, `.5`, an unsafe integer and a lossy decimal stay text; the integer and decimal subset of Newman's `--csv-auto-parse`, #2540) and the result echoes `castNumbers`. JSON and JSONL keep native types and ignore the option, and the preview states which reading is in force. The header row *is* the mapping - column names become `{{data.column}}` tokens and `pm.iterationData` keys - so an empty or duplicated header cell is a parse error rather than a column nobody can address.

A **scenario load run** lands in `LoadTestDetail`, not `ScenarioRunView`: it is `type: "load"`, publishes ticks and reports percentiles like any load run, and its target simply happens to be a sequence. Two things follow, and they are separate questions with separate answers. Whether the run *is* a collection run is `report.metadata.scenario` (its snapshot identity, which the engine writes on every collection run, finished or not, #3569) or, for a report from an engine that predates it, a non-empty `report.scenario.steps`. That decides the request bar: a collection run has no single method and URL, so the bar says what the sequence was instead of the "GET Unknown URL" fallback, which the reader cannot tell apart from a broken run - the SEQUENCE badge, then "Checkout - 12 steps per iteration - 8 virtual users". The collection's name is resolved from the tree by `useCollectionName` (`queries/collections.ts`, the one lookup `useCollectionRunTarget` shares; the id stands in once the collection is deleted, never a blank), and the step count is the breakdown's length when there is one, else the identity's `stepCount`. A run the engine did not finish has no stored summary and therefore no `report.scenario` breakdown, so it gets the bar and no Steps tab. The breakdown's presence alone decides the tab. And it stores no per-step `results` rows - one row per step per iteration per virtual user is what a load run exists not to keep - so `ScenarioStepsTab.tsx` renders the engine's per-step histogram breakdown, the only per-step record such a run has. The run's headline latency figures are one histogram over every step, so they are labelled as pooled wherever they appear: the P99 tile and the hero latency card carry an "All steps pooled" caption naming the slowest step, and the Performance tab's "Latency distribution", "Response time percentiles over time" and "Response time vs virtual users" cards read "(all steps)" (`pooledTitle`, `utils/pooledLatency.ts`); a single-request run is unlabelled (#2823). Its `(n short)` marker is the visible shape of a step that got no response, or set a jump the run could not honour, ending its iterations early, which otherwise reads as a run that simply lost requests. The line above the table counts the run's iterations three ways: **Iterations completed**, **Iterations abandoned** (a step that got no response, or a jump the run could not honour, ended them, #2974; a step whose script threw is `errored` and does not, #2947) and, when `iterations - completed - abandoned` is above zero, **Iterations cut short** - the ones the deadline or a Stop ended mid-way, derived from the three `scenario` counts and clamped at zero, with no engine key of its own (#2824). The **Errors** column is wider than that: it counts every response outside 2xx/3xx as well as the no-response executions (the run's one error definition, issue #2124), and only the latter (or a refused jump, which is not an error status either) end an iteration. The red count carries a tooltip with the split, `N HTTP errors, M no response` (`step.httpErrors` / `step.noResponse`); a report stored before the engine reported them shows the bare count with no tooltip. The **Tests** column is the deferred per-step validation - each step's own post-request script replayed after the run against that step's sampled responses - and leads with its scope, "23 of 2,270" (sampled responses of the step's `deferred` count, `deferredResponsesOf`, #2824), keeping the assertion split in the cell's title and a failed count in the cell; a report stored before `deferred` has no population and keeps the plain passed / failed form. It shows a dash, never a `0`, for a step that asserted nothing: the engine omits the object rather than writing zeros, because "no assertions" and "no failures" are different answers. The console lines that replay logged (`step.tests.console` and `consoleDropped`, #3127) are one row under the step's elements, headed "Console from the post-run replay over N sampled responses" with N the step's `tests.sampled`; the row is absent for a step whose replay logged nothing and for a report from before the field. A step's non-script elements - extractors, assertions, timers - each get their own row beneath the step's, tallied across every virtual user and iteration (`step.elements`, issue #1495); an element that never ran is omitted rather than listed at zero, the same convention `unresolvedTokens` and `tests` follow. This is the load run's counterpart to the sequential run's per-step outcomes (`ScenarioStepCard.tsx`'s `ElementOutcomes`), aggregated as counts instead of one outcome per execution because a load run has many. Each element row is named by its `name` and the collection it came from (see Element Tally below), and counts a miss under its own "N missing" bucket. A step whose extractors found nothing gets one more row after those, the shared `ExtractorMisses` ("N extractor misses", from `step.extractorMisses`, issue #3053): each miss is also filed under an extractor row's `missing` (or its `skipped`, for an optional `extract.json` over a body it could not read), and a miss a `default` answered is neither; it is summed here because each also left a later step sending that name unresolved; the engine omits the count at 0, so there is no row for none. The same row carries the shared `UnresolvedTokens` (`unit="sends"`, "N sends with unresolved variables", from `step.unresolvedTokens`, issue #3269): the executions of the step that sent a `{{token}}` unresolved, which is the other end of an extractor miss and a count of sends rather than of names. A step with either gets one row, not two; the load run always reports the field, so 0 is a real "none" and draws nothing.
A step's row header also carries the engine's `step.label` in a muted monospace beside its name (`tools/call search` for an MCP step, #3829), absent for every other step and for a report from before the field.

## `UnrecordedFiguresNotice.tsx`, `unrecorded-figures.ts`

The warning `Callout` over the Overview of a failed load run the engine could not fully record (#2895), and the one reading of the two `summary` flags behind it.
`summary.summaryMissing` (no summary was saved: the counts are not whole-run totals) reads "Counts were not recorded", puts "not recorded" on the two count tiles and "-" on the P99 tile, and removes `HeroRow` and `ModeStatsRow`; `summary.partial` (reconciled after an engine crash: the last saved tick's counts, peak concurrency and queue wait of 0 that were not measured) reads "Counts are partial", shows the counts and puts "-" on the P99 tile only, and also removes the two rows, since each of their cards reads at least one unmeasured figure.
For either flag the engine omits `latency` from the report (#2938), and that absence, not the flags, is what `unrecordedFiguresOf(report).latency` reads (`counts` still reads `summaryMissing`): the Performance tab's Latency distribution tiles read "-" through the same formatter, the HDR percentile plot card is dropped, `reportToDerived` leaves `DashboardDerived`'s four latency fields undefined, and `BaselineComparison` draws no tile for a figure the flagged open run did not measure (nothing at all when the counts are unrecorded).
A flagged run on the other side of a comparison (the pinned baseline, or the compared run in `RunComparisonView`) reads "not recorded" per figure through `compareReports` (`lib/run-compare.ts`, which mirrors this module, #2904), never a delta against a zero.
Neither flag is ever false in the report, so absence is the whole signal.
A new tile that reads `summary` or `latency` asks `unrecordedFiguresOf(report)` rather than testing the flags itself, and prints a latency that may be absent through `formatLatencyOrDash` / `formatLatencyPartsOrDash` (`lib/format-number.ts`), never `formatLatency`, which reads an absent value as `0ms`

## `SamplesTab.tsx`, `SampleRequestCard.tsx`

Sampled request/response pairs; the synthetic test-validation row (`test-validation.ts`) is dropped here so it is never drawn as a request with no response; its failures and their counts reach the screen on the Overview's Test validation card instead.
When the report says the engine cut `results` (`resultsStored > resultsCap`, #2210) a second badge beside "N samples shown" reads "N of M stored"; it is absent when every stored row is shown or on a report from an engine that predates the pair.
The tab opens oldest first (`sample-filter.ts`: stable sort by `timestamp`) and a row's `#N` is its place in that order, so a chip never renumbers it and the open row is keyed by it.
A `ToggleGroup` of status-class chips with counts over the loaded rows (All, Errors, 4xx, 5xx, No response, Slow) narrows the list; Errors is `isErrorStatus`, the classes are `httpStatusClass`, and Slow is the engine's `trace.isSlow` verdict. "N samples shown" counts the visible rows; "N of M stored" counts the loaded ones; both numbers go through `formatNumber`.
The selected chip is local unless the owner passes `filter` / `onFilterChange`; `LoadTestDetail` does, because Radix unmounts an inactive tab and a local chip would reset on every switch.
`initialExpandedNumber` opens one row at mount: an Overview error row (#2213) sets the chip and that number and switches to this tab, and any tab the user then picks clears the number, so returning to Samples does not re-open it.
Each header carries a "Copy for agent" icon button (`runSampleReference`, #2047) in `SampledExchange`'s `actions` slot, outside the toggle.
An open row also states what its trace carries (`SampleTraceDetails.tsx`, in the `details` slot): "Error type", "Data row: N" (`trace.dataRowIndex`, row 0 included, #449) and the "Failed tests (N)" list of `trace.failures` (#111); a slow sample gets the "Slow request" `Callout` with its `totalMs` against `thresholdMs`, both through `formatLatency` (the elapsed time is left out when the trace has none, rather than printing a bare unit); each header's latency reads through `formatLatency` too.
The captured bodies come from `GET /runs/:id/samples`, requested only once a row is open and joined to the row by `sample.id`; a body the engine spells `bodyEncoding: "base64"` is decoded by `capturedBody` (`sample-body.ts`) before the viewer sees it (#3159)

## `LatencyMetric.tsx`, `HistoricalChartsSection.tsx`

Metric cards + historical charts.

The first load is a labelled `DetailSkeleton`, not a spinner card (#2314).

## `MonitorSummary.tsx`

Per-series min/avg/max for the run's server-vitals scrape (scrape counts through `formatNumber`), under the Performance tab's chart.
Present whenever `report.monitor` is - including the run whose every scrape missed, which has no line to draw and read as an unexplained empty chart before it.
A missed scrape is stated by cause, because the two need different fixes (#3120): a failure (`failures`, no 2xx answer) with the engine's `lastError`, and a no-match (`noMatchScrapes`, answered but carrying none of the requested names) naming the names, which `LoadTestDetail` reads from the run's config snapshot (`monitorSeries`).
Each is a blocking `Callout` when nothing was recorded and a warning beside the readings otherwise; a run stored before the engine counted no-matches apart has no `noMatchScrapes`, and its all-failed advice names both causes
