# JMeter `.jmx` Test Plan

Parses a JMeter `.jmx` test plan (JMeter's own `<jmeterTestPlan>`/`<hashTree>` XML dialect) into the Vayu draft model. Issue [#1518](https://github.com/athrvk/vayu/issues/1518).

- **Source:** `engine/src/core/jmeter_import.cpp` (`engine/include/vayu/core/jmeter_import.hpp`)
- **Reader:** pugixml, the one XML dependency in one translation unit - the same "one reader" rule `core::read_document` (JSON/YAML) and `core::openapi_document.cpp` (the YAML half of that) already follow, extended to a third dialect neither of those readers can parse.

## Detection

A `.jmx` file is XML, so it fails both of `core::read_document`'s readers (JSON, then YAML) the same way genuinely unrecognised bytes do. `is_jmeter_document` checks the raw text for `<jmeterTestPlan` within its first 4096 bytes, **before** `parse_import` ever calls `read_document` - the one exception to every other format's "one JSON/YAML read, then dispatch on the parsed document" rule (see the [parser-architecture README](./README.md#adding-a-new-format)).

## The tree walk

A `.jmx` file's `<hashTree>` children alternate a test element (`<ThreadGroup>`, `<HTTPSamplerProxy>`, ...) with that element's own `<hashTree>` of children - JMeter's own serialization shape. The walk pairs them (`for_each_paired_child`) and dispatches on the element's tag name; nothing here is detected by `guiclass` except JMeter's own `HttpDefaultsGui` marker on a bare `ConfigTestElement` (JMeter reuses that one tag for several unrelated config panels).

**`enabled="false"` excludes an element and everything nested under it**, the same way JMeter itself never runs a disabled element's children either - checked once, in `for_each_paired_child` itself, so no individual dispatch site can forget it. Counted as `<Tag>_disabled` (e.g. `HTTPSamplerProxy_disabled`) rather than importing a request or controller the user had turned off as active with no way to disable it again.

**Document order is kept** (issue [#2573](https://github.com/athrvk/vayu/issues/2573)). JMeter runs a plan's elements in the order the tree lists them and descends into a controller where it sits, so a sampler listed before or between controllers runs before the ones after it. Each sampler and each controller folder draft records its position among its parent's kept elements as `order`, one counter per parent across both kinds, and the apply numbers a parent's sub-folders and requests in that one sequence: the sidebar lists them and a recursive run visits them in the plan's order. The counter belongs to the collection being built, so the samplers of two `ThreadGroup`s (which flatten into the same parent) continue one numbering; a disabled element and a setup or teardown group take no position. A plan of controllers only lists them as it always did.

**Nesting is bounded.** A `.jmx` skips `read_document`, so the walk applies `MAX_READ_DEPTH` (100 `<hashTree>` levels) itself, at the one function every recursive edge passes through. A branch nested past it is left out and counted under `nesting_too_deep` in `meta.skipped`; the rest of the file imports. Without the bound a file under the size cap could nest tens of thousands of levels and overflow a worker thread's stack.

- **`TestPlan` and `ThreadGroup`** flatten straight into the enclosing collection - Vayu has no thread-group concept, since a collection already runs every request once. A `TestPlan`'s own `TestPlan.user_defined_variables` becomes collection variables. A `ThreadGroup` that asks for more than one pass by one thread also leaves a `ThreadGroup_profile` count in `meta.skipped` ([Run profile](#run-profile)), so the profile is not lost with the group.
- **`SetupThreadGroup` / `PostThreadGroup`** (JMeter's setUp/tearDown thread groups) look inside for a JSR223 or BeanShell sampler/pre/post-processor and take its script text as `script.setup` / `script.teardown` (concatenated if more than one). Their samplers are never imported as requests - a request in the collection runs on every pass, a setUp sampler once - and are counted instead: see [Setup and teardown groups](#setup-and-teardown-groups).
- **A folder-shaping controller** becomes a Vayu folder, walked the same way, and its members import inside it in source order. `LoopController`, `IfController`, `OnceOnlyController`, `TransactionController` and `ThroughputController` also get their own `control.*` element when the controller could be translated (see the table below). `SwitchController` and the controllers with no element-kind equivalent for their looping or selection (`WhileController`, `ForeachController`, `RandomController`, `InterleaveControl`, `RandomOrderController`, `RunTime`, `CriticalSectionController`, `ModuleController`, `IncludeController`, `RecordingController`) import as a plain folder, and so does a controller that could not be translated (an unparseable `IfController.condition`, a `LoopController` set to JMeter's "forever", a `ThroughputController` in "total executions" style): the members are kept, the logic that shaped the folder is not, and each such controller is counted under `<Tag>_unrecognised` in `meta.skipped` (one count per controller, aggregated per tag) the same way `build_leaf_elements` counts a recognised leaf kind it could not extract enough from, per the "nothing dropped quietly" rule below. `GenericController` (JMeter's Simple Controller) only groups, so it is a plain folder with nothing to count.
- **`HTTPSamplerProxy`** becomes a request; see [Request mapping](#request-mapping).
- **Everything else** (`Arguments`, HTTP defaults, and every extractor/assertion/timer/script kind in the table) attaches to whichever sink is walking when it is met: a sampler's own `<hashTree>` if this parser is inside one ([Request mapping](#request-mapping)), the enclosing folder's or the collection's own `elements` otherwise - the same inheritance a Vayu-authored collection-level element already gets. A `HeaderManager` or a leaf kind met at the collection/folder level is not scoped down to "every sampler after it" the way JMeter's own scoping would place it; this parser does not attempt to resolve JMeter's positional scoping rules.

## Class mapping

| JMeter class | Vayu | Notes |
|---|---|---|
| `TestPlan`, `ThreadGroup` | flattens into the collection | no per-user loop count, no thread count - a load run configures those separately; a non-default profile is counted as `ThreadGroup_profile`, naming the values ([Run profile](#run-profile)) |
| `SetupThreadGroup`, `PostThreadGroup` | `script.setup`, `script.teardown` | only when a JSR223/BeanShell script is found inside; every sampler left out is counted under the group's tag ([Setup and teardown groups](#setup-and-teardown-groups)) |
| `HTTPSamplerProxy` (+ `HeaderManager` in its own `<hashTree>`) | a request, with headers | see [Request mapping](#request-mapping); `HTTPSampler.follow_redirects` / `HTTPSampler.auto_redirects` (either true means Vayu's `followRedirects` is true) carry through; `HTTPsampler.Arguments` become query `params` or a form body by method ([Request mapping](#request-mapping)); `HTTPsampler.Files` (a multipart file upload, [issue #1657](https://github.com/athrvk/vayu/issues/1657)) becomes a `form-data` body row per file - a `HTTPFileArg` with no `File.paramname` is counted as `HTTPsampler.Files` instead, since it names nothing a field could key on and is nested inside the sampler tag itself, so it would otherwise never reach the sibling-tag tally |
| `LoopController` | folder + `control.loop` | `LoopController.loops` of `-1` (JMeter's "forever") has no `control.loop` equivalent - the folder still imports as a plain grouping |
| `IfController` | folder + `control.if` | only the `"${var}" == "value"` / `!=` shape translates into `{{var}} == value`; anything else (a JS expression, `&&`/`||`) is left unmapped |
| `OnceOnlyController` | folder + `control.once` | |
| `TransactionController` | folder + `control.transaction` | named from `testname` |
| `ThroughputController` | folder + `control.throughput` | the percent is read from the nested `<FloatProperty>` JMeter's GUI saves (or a flat `ThroughputController.percentThroughput` string prop). `ThroughputController.style` `0` ("total executions", a cap on a count with no percent) has no `control.throughput` equivalent - the folder still imports and the controller is counted as `ThroughputController_unrecognised` instead of importing a percent the plan never set |
| `GenericController` (Simple Controller) | folder only | groups its members and nothing else, so nothing is counted |
| `SwitchController` | folder only | JMeter selects by list index or a raw variable value, neither of which maps onto `control.switch`'s named-case grammar without inventing case names the plan never declared |
| `WhileController`, `ForeachController`, `RandomController`, `InterleaveControl`, `RandomOrderController`, `RunTime`, `CriticalSectionController`, `ModuleController`, `IncludeController`, `RecordingController` | folder only | members import in source order; the loop condition, iteration source, random or interleaved selection, time limit, lock or reference to another part of the plan is not carried, and each controller is counted as `<Tag>_unrecognised` |
| `JSONPostProcessor` | `extract.json`, one per reference-name / JSONPath pair | JMeter keeps a multi-value extractor's names, paths, default values and match numbers as parallel `;`-separated lists; each pair becomes its own extractor, with the default and the match number (`0` random, `-1` every match) read by the same index (a list that ends early leaves the rest with no default and the first match). Lists are split the way Java's `String.split` does, so a trailing `;` adds nothing. Names and paths of different lengths, or an empty name or path between separators, cannot be paired: nothing is imported and the processor is counted as `JSONPostProcessor_unrecognised` |
| `RegexExtractor` | `extract.regex` | `useHeaders` maps to `field: "headers"`. The pattern is copied as written, and Vayu runs it with RE2 rather than Java's engine: a pattern using a backreference (`\1`) or lookaround (`(?=`, `(?<=`, ...) is not imported: the extractor is dropped and counted as `extract.regex_unmappable`, because RE2 refuses it and a stored extractor could never run ([regular expressions](../../engine/elements.md)) |
| `BoundaryExtractor` | `extract.boundary` | a new kind this issue adds - `leftBoundary`/`rightBoundary`, JMeter has no field selector for one either |
| `ResponseAssertion` | `assert.status` (test field is response code) or `assert.contains` (otherwise) | `Assertion.test_type` is a bitmask (`1` Matches, `2` Contains, `4` Not, `8` Equals, `16` Substring, `32` Or), read in full: the Not bit (`4`) becomes `negate: true` on every emitted `assert.contains`; the pattern kind follows JMeter's own precedence - Equals (`8`) → `mode: "equals"`, Substring (`16`) → `mode: "contains"` (a plain text search), Matches (`1`) or Contains (`2`) → `mode: "matches"` (both are a regular-expression search in JMeter; the same RE2 caveat as `RegexExtractor` applies: a pattern RE2 refuses drops the assertion, counted as `assert.contains_unmappable`; so is a Substring assertion on an empty string, which every response contains, #3055). Several patterns without Or must all hold, so each pattern becomes its own `assert.contains` in the order JMeter lists them, every one with the same field, mode and Not (each is judged and inverted on its own, as in JMeter), and a pattern RE2 refuses drops only itself. An Or assertion (`32`) with more than one pattern means "any of these passes", which no Vayu kind expresses - refused and counted as `ResponseAssertion_or` rather than emitted as ANDed assertions; a single pattern with Or set is just that pattern. A response-code assertion stays one `assert.status` listing every code. A response-code assertion (`Assertion.test_field` is `Assertion.response_code`) with Not set is refused the same way, since `assert.status` has no `negate`. `Assertion.test_field` selects `assert.contains`'s own `field`: `Assertion.response_headers` → `headers`, `Assertion.sample_label` ("URL Sampled") → `url`, absent/`Assertion.response_data` → `body`; any other value (Request Data, Request Headers, Response Message, Document) has no field to land on and is refused rather than collapsed onto `body`. Every refusal here (an unmapped field, an unresolvable response-code list, a Not on a response-code assertion, an unmapped Or) is counted as `ResponseAssertion_unrecognised` except the Or case, which gets its own `ResponseAssertion_or` tally |
| `DurationAssertion` | `assert.duration` | |
| `SizeAssertion` | `assert.size` | only JMeter's Equal operator maps precisely (`op: "eq"`); every other operator code has drifted across JMeter releases and falls back to `assert.size`'s own default (`lte`) |
| `JSONPathAssertion` | `assert.jsonpath` | `INVERT` → `negate`; `JSONVALIDATION` + `EXPECTED_VALUE` → `expected`, else `exists: true` |
| `ConstantTimer` | `timer.think` (fixed `ms`) | |
| `UniformRandomTimer` | `timer.think` (`minMs`/`maxMs`) | `ConstantDelay` is the floor, `+ RandomTime.range` the ceiling |
| `GaussianRandomTimer` | `timer.think` (`gaussian`) | `ConstantDelay` → `meanMs`, `RandomTime.range` → `deviationMs` |
| `ConstantThroughputTimer` | `timer.pacing` | JMeter's rate is samples/minute; `everyMs = 60000 / throughput`. `calcMode == 0` ("this thread only") is `perUser: true`, every other mode `perUser: false` |
| `JSR223Pre/PostProcessor`, `BeanShellPre/PostProcessor` | `script.pre` / `script.post`, imported **disabled** | Groovy and BeanShell are not JavaScript; the element carries the source text as a comment when JMeter's own `script` property is empty |
| `Arguments` (User Defined Variables) | collection variables | merged wherever the node sits in the tree (`TestPlan`, or a bare `Arguments` node) |
| `ConfigTestElement` with `guiclass="HttpDefaultsGui"` (HTTP Request Defaults) | the `baseUrl` variable of the folder or collection it sits in | only when it names a domain; `protocol://domain[:port]` with `${x}` rewritten to `{{x}}` and an empty protocol read as `http`. Its path and its connect and response timeouts reach no request and are counted, each by name, under `HttpDefaults_unmapped` ([why](#http-request-defaults)) |
| `XPathExtractor`, `XPath2Extractor`, `CookieManager`, `CSVDataSet`, `AuthManager`, every listener (`ResultCollector` and its kin) | not mapped | counted by class name - see [Drop counting](#drop-counting) |

## Run profile

Vayu keeps threads, ramp-up, duration and loops on the load run, not on the collection, so a `ThreadGroup` cannot carry them across. Instead of dropping them quietly, every enabled `ThreadGroup` whose profile is not the defaults is counted once under `ThreadGroup_profile` in `meta.skipped`, and the item's `names` hold one line per group with the values as written in the plan, e.g. `Users: 10 threads; ramp-up 5s; duration 60s; 3 loops`:

| Part | Read from | Shown |
|---|---|---|
| threads | `ThreadGroup.num_threads` | always |
| ramp-up | `ThreadGroup.ramp_time` | only with more than one thread (a single thread starts at once) |
| duration | `ThreadGroup.duration` | only with `ThreadGroup.scheduler` on, as JMeter ignores it otherwise |
| loops | `LoopController.loops` inside `ThreadGroup.main_controller` (string or int), `-1` shown as `forever` | always |

The values stay as written, so a `${__P(users,10)}` function call reads as that text. A group at the defaults - one thread, one pass, no duration, or none of the properties at all - has nothing to set and is not counted; a disabled group is counted as `ThreadGroup_disabled` like any disabled element and not as a profile (nothing under it imports). The samplers inside an enabled group import as requests whatever its profile.

The preview shows it as a note, not a warning, since every request imports and only a load test would run with other load than the plan: "1 thread group run profile not imported (Users: 10 threads; ramp-up 5s; duration 60s; 3 loops) - set the load, ramp-up and duration when you start the load test", with up to three groups spelled out and "+N more" after them.

## Setup and teardown groups

A `SetupThreadGroup` or `PostThreadGroup` is counted under its own tag name (`SetupThreadGroup`, `PostThreadGroup`), and the count is the number of samplers inside it at any depth, controllers included - the number of requests to rebuild by hand. A group with no sampler inside and no script that imported is still one loss, so the count is never below 1 for a group that left something out. The samplers are not imported as requests and `meta.requestCount` does not include them. When a JSR223/BeanShell script does import as `script.setup` / `script.teardown`, a scripted sampler that became that script is not a loss, but any other sampler beside it still is and is counted. Samplers are recognised by the JMeter naming (`HTTPSamplerProxy`, `JDBCSampler`, ... any tag ending `Sampler` or `SamplerProxy`, and `TestAction`).

The preview words the count as samplers, not groups, and shows it as an action since requests are missing: "2 setUp samplers not imported - a request runs on every pass, so send them from a setup script instead", and the same for tearDown with a teardown script.

## Request mapping

One `HTTPSamplerProxy` becomes one request:

- **URL.** `HTTPSampler.domain` present → an absolute URL (`protocol://domain[:port]path`, `${var}` rewritten to `{{var}}`; a protocol that is empty or blank, as JMeter saves one left unset, is `http`, the same as an absent one); absent → `{{baseUrl}}` + path, so a sampler that relies on a plan-level HTTP Request Defaults element still resolves once that element's `baseUrl` variable is set.
- **Body.** A sampler carrying `HTTPsampler.Files` → `{mode: "form-data", fields: [...]}`: one file field per `HTTPFileArg` (`File.paramname` as `key`, `File.path` as `src` - sent only once picked or allowed, since it names a file on the exporting machine, `File.mimetype` as `contentType` when present), with any `HTTPsampler.Arguments` folded in beside them as plain fields - a file has no query-string or raw-body form to take instead, so this is the one case where `HTTPSampler.DO_MULTIPART_POST` plays no part in the decision. Otherwise, `HTTPSampler.postBodyRaw` true and at least one argument → `{mode: "text", content: <the one argument's value>}`, whatever the method. Otherwise the `HTTPsampler.Arguments` go where JMeter sends them for the sampler's method ([issue #3191](https://github.com/athrvk/vayu/issues/3191); the method is trimmed and case-folded for the decision): `GET`, `DELETE`, `HEAD` and `OPTIONS` → `params` rows (enabled), which the import joins into the URL's query; every other method (`POST`, `PUT`, `PATCH`, a custom verb) → a body, `{mode: "x-www-form-urlencoded", fields: [...]}`, or `{mode: "form-data", ...}` when `HTTPSampler.DO_MULTIPART_POST` is true, and nothing in the query. A sampler with no arguments gets no body. The engine adds `Content-Type: application/x-www-form-urlencoded` itself for the first shape, and a `HeaderManager` `Content-Type` row wins over it.
- **Headers.** A `HeaderManager` directly inside the sampler's own `<hashTree>` becomes the request's `headers` rows.
- **Elements.** Every recognised extractor/assertion/timer/processor directly inside the sampler's own `<hashTree>` becomes a request-level element, in encounter order.

## HTTP Request Defaults

Variables are the only thing a defaults element hands down: `baseUrl`, read by a sampler that names no domain of its own (`{{baseUrl}}` + its path). The element's **path** and **connect/response timeouts** are counted instead of carried, as `HttpDefaults_unmapped` with one count per setting (`path`, `connect timeout`, `response timeout` under `names`), because neither can be inherited correctly:

- A request has no inherited path. JMeter applies a default path only to a sampler whose own path is empty (a sampler's path replaces it, it is not a prefix), so folding it into `baseUrl` would prefix every other sampler wrongly; deciding per sampler needs JMeter's positional scoping, which this parser does not resolve (see [The tree walk](#the-tree-walk)).
- A timeout is a per-request setting (`timeout`, milliseconds) with no folder or collection level, so honouring a default means stamping the sum of two JMeter timeouts onto each request in the element's scope, again by positional scoping. A blank or `0` timeout, JMeter's "none", is not counted.

The preview shows it as a note: "2 HTTP Request Defaults settings not imported (path, connect timeout) - set them on the requests themselves".

## Drop counting

Every class this parser has no mapping for is counted under its own literal tag name, and every recognised class it could not extract enough from (an empty pattern, an unparsable delay, a controller it could not translate) under that tag plus a suffix (`<Tag>_unrecognised`, `ResponseAssertion_or`, `<kind>_unmappable`) (`meta.skipped`); a `ThreadGroup`'s run profile is the one count that is not a loss of the import's own accuracy but of settings the collection has no place for (`ThreadGroup_profile`, with `names`, see [Run profile](#run-profile)), shown in the import preview the same way every other format's losses are (issue [#1443](https://github.com/athrvk/vayu/issues/1443), "nothing dropped quietly"). JMeter's own class list is open-ended - third-party plugins add more of them - so this is not the closed, enumerable `SkippedItem.kind` set every other format counts against: `ImportTally::items()` falls back to emitting any kind outside its fixed order list (in first-encountered order) rather than silently losing it, and the preview (`import-notices.ts`) renders the raw class name for one with no hand-written label: a `_disabled` class is not shown (it was switched off in JMeter), an `_unmappable` element is shown as dropped, and anything else as not imported.

**A refused element is counted once.** Whichever parser looked at it records its own kind, and the bare tag is added only for a class no parser looked at, so one element is never listed twice in the preview.

An element this parser *does* build is still validated against the live element registry (`Registry::validate`) before it reaches the draft, the same gate a stored request's own write goes through - a mistranslation is dropped and counted as `<kind>_unmappable` rather than reaching `POST /import/apply`, whose write is atomic across the whole tree.
